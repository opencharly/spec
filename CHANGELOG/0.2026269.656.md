# 0.2026269.656 — feat(schema): give kubevirt its own venue value (ssh | kubevirt)

feat(schema): give kubevirt its own venue value (`ssh` | `kubevirt`)

Operator-directed refinement of spec#166's trait-based discriminator, found while
wiring the KubeVirt R10 beds (Phase 6). kubevirt is a **cluster-managed
`VirtualMachine` CR** whose lifecycle an out-of-process plugin owns — not a
host-libvirt domain — so it deserves a first-class venue token rather than sharing
`ssh` and being disambiguated by an auxiliary trait.

## Summary of changes

- **`schema/deploy.cue`** — `#DeployTraits.venue` enum gains `"kubevirt"`; the
  `#DescentDescriptor.transport` doc notes kubevirt shares the `ssh` transport.
- **`spec/descent.go`** — `DescentFromTraits` maps `venue == "kubevirt"` to the `ssh`
  TRANSPORT (a kubevirt guest is still reached over ssh); `host_rooted` stays
  `venue == "shell"`, so kubevirt is unaffected.
- **`deploy/deploy_ops.go`** — `SshVenue` now reads the DERIVED `Transport == "ssh"`
  (so it stays true for kubevirt after that substrate migrates to its own venue value —
  matching its own "vm AND kubevirt" doc, and the transport is what an ssh-executor
  caller needs). `IsVmVenue` is **unchanged** (`SshVenue && ExclusiveVenue`), so
  kubevirt is `false` in both migration states. The `kubevirt` venue value lands on
  `node.Descent` for a consumer bed arm to key on in the `kubevirt-check-beds` batch;
  no new predicate is added here because none has a caller yet (R5).
- **`deploy/deploy_ops_venue_test.go`** — extended to drive the real derivation with
  both the pre- and post-migration kubevirt trait rows.
- **`spec/cue_types_gen.go`** — regenerated (`charly task cue-gen`; the field is
  `type=string`, so only the doc comments change — `TestGenReproducible` passes).
- **`lock/bed_vm_domain_test.go`** — the `TestBedVmDomainsExcludesKubeVirt` fixture
  models the new `kubevirt` venue (`Venue: "kubevirt", Transport: "ssh"`), and the
  libvirt-vm fixture keeps `ExclusiveVenue: true` (matching the traits table).

## Cross-repo ordering — contract FIRST, then producer

The trait table that STAMPS the venue is `candy/plugin-substrate`'s `substrateTraits`
(the producer companion is **opencharly/plugin-substrate#19**). The spec pin and the
plugin-substrate pin are INDEPENDENT, so the safe order is dictated by what each
consumer derives:

| order | consumer on old spec, new producer trait `Venue: "kubevirt"` |
|---|---|
| producer-first | old `DescentFromTraits` hits `default:` → `transport: "none"` — the kubevirt node LOSES its ssh hop ✗ |
| **contract-first (this order)** | the producer keeps stamping `Venue: "ssh"` until it migrates, so the old spec never sees `"kubevirt"`; once both land, `kubevirt` → `transport: "ssh"` ✓ |

So the landing order is **spec#168 (contract) → plugin-substrate#19 (producer) →
sdk / plugin-check / charly pin bumps**. This PR is the CONTRACT half and is safe
alone: with the producer still emitting `"ssh"`, `IsVmVenue` (unchanged) keeps
kubevirt out of the libvirt arm, and the new enum value is simply unused. The
`IsVmVenue` `ExclusiveVenue` guard additionally makes the *reverse* order
non-regressing for the predicate — but NOT for the transport mapping, which is why
contract-first is the stated order.
