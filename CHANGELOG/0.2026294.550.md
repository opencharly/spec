# 0.2026294.550 — feat(schema): carry a runtime LIST through the workflow arg maps

## Summary

`#WorkflowRunRequest.args` was `{[string]: #StrVal}` with `@go(Args,type=map[string]string)` — `schema/workflow.cue:111` on `main` — so **a runtime list could not cross the workflow engine wire at all**. The retired lane model's `--prs a b c` had no spelling on the wire: the caller had to pre-join the list into one string for the callee to re-split, which no generic consumer can do correctly.

This leg adds the shape that carries it — no engine, no lane primitive. The def is `#WorkflowArgVal: #StrVal | [...#StrVal]` (`@go(-)`, so it emits no Go type) — a value is a scalar (`string | number | bool`, the pre-existing `#StrVal`) **or a flat sequence of scalars**. It is applied to the four arg maps on the workflow surfaces, whose generated Go field widens `map[string]string` → `map[string]any`:

| def | schema site | the surface it carries |
|---|---|---|
| `#WorkflowRunRequest.args` | `schema/workflow.cue:153` | what a front-end dispatches a run with |
| `#WorkflowSchedule.args` | `schema/workflow.cue:90` | that run's normalized cron trigger |
| `#PipelineSchedule.args` | `schema/pipeline.cue:163` | the AUTHORED trigger |
| `#PipelineArms.workflow_args` | `schema/pipeline.cue:86` | a `workflow:` sub-step's args |

### Why this shape, and not a `list_args` field or a typed container

A second field (`list_args`) would force every front-end to decide, per value, which of two maps a value belongs in — and every callee to re-merge two maps before it can answer "what is this arg's value". One question, two homes.

A typed container (`args: {prs: {value: [...]}}`) would restructure every existing document and every existing consumer.

Widening the VALUE admits a list with the wire key, the JSON shape and the `args` map all unchanged: a payload that validated before still validates, because the admitted value set only GREW. The one thing that changes is the generated Go field, which is a compile-time change for a caller that BUILDS the request and no change at all for anything that only reads the JSON.

The engine side is what shows this is the right cut: the wire was the ONLY truncation point. `plugin-lobster` resolves args as `map[string]any` (`resolveWorkflowArgs`, over a `#LobsterFile` arg default typed `_`), and its `run.go:67` converts `map[string]string` to `map[string]any` through `stringArgsToAny` — a conversion that exists only because this field was narrow.

### Why four maps and not one (R2)

Those four are ONE mechanism, not four conveniences: an authored `#PipelineSchedule.args` is normalized into `#WorkflowSchedule.args` (`cli.go:402`), which a scheduled run turns into a `#WorkflowRunRequest`; and a `workflow:` step's `workflow_args` reaches the same `resolveWorkflowArgs(map[string]any)` one level down. A run that accepts a list while its schedule or its nested step does not is exactly the half-fix this change would otherwise ship, and the engine's own step type already carries that field as `{[string]: _}`.

The boundary is measured, not asserted. Every other `{[string]: #StrVal}` map left in `schema/` is an ENV map (`env`, `env_default`, and the transport `#StrMap`), which is a string surface by definition. The two input-gate `defaults` maps stay scalar because the gate's own reply field is a string map by contract (`defaultsAsStrings` renders each value to one string). The declaration map `#TaskParamSpec` is untouched: it is shared with `kind: task`, whose params are text-substituted through `${NAME}`, a string surface with a different destination. A list arrives as a runtime VALUE, which is what this leg carries.
