# 0.2026330.1340 — docs(xdg): record how HuggingFace resolves its cache and how to persist it

## Summary

The `xdg` skill said *do not set `XDG_*` in a deploy* but never said **where an application's model
cache goes**, so each pod candy invented its own answer. This adds a measured section for that case.

- **Resolution (measured, not assumed).** In the `openwebui` image (`huggingface_hub` 1.33.0,
  `sentence-transformers` 5.5.1), `HF_HOME` wins when set; otherwise it is
  `$XDG_CACHE_HOME/huggingface` with `XDG_CACHE_HOME` defaulting to `~/.cache`
  (`constants.py:160-167`). The widely repeated claim that HuggingFace **ignores**
  `XDG_CACHE_HOME` is wrong for this version.
- **Persistence.** A model cache is a cache root, so the path is the application's and the
  persistence is a charly `volume:` in the candy. `kit.ExpandPath` (`spec/spec/env_path.go`)
  expands `~`, `${HOME}` and `$HOME` for a candy volume path, so `path: "${HOME}/.cache"` and the
  app's own `expanduser("~")` agree without pinning a variable.
- **Apps that do not follow XDG** get their own documented root (`ollama` → `~/.ollama`,
  `immich` → `~/.immich/models`), and the section says the witness is a runtime check that the
  cache path is a MOUNT POINT, because a bed that never re-creates a container cannot detect the
  regression otherwise.

The concrete defect this documents is `opencharly/pod-openwebui#36`: with only `/opt/data`
persisted, a re-created Open WebUI container re-fetched its 30-file embedding model — 889 MB,
254 s to the first HTTP `200`. Its fix (a `cache` volume at `${HOME}/.cache`) lands in
`opencharly/pod-openwebui`.

```

/x/z
$ charly cmd openwebui "sh -c 'echo HOME=\$HOME; ls \$HOME/.cache'"
```
