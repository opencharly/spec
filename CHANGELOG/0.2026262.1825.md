# 0.2026262.1825 — feat(schema)!: give the dead deploy VM-shape fields a reader; align cpus->cpu

## Summary of changes

`#Deploy` carried VM-shape fields with **zero readers and zero authors** since the initial spec import (`11dcd6d`): authorable, inert. This PR gives `cpu`/`ram` their reader's contract and **deletes the dead surface**.

The reader is `candy/plugin-vm#39`, whose CODE has already merged. A `from:` VM deploy may state its own cpu/ram, inherited along the `from:` chain, so MANY deploys can share ONE `kind:vm` template at different sizes instead of each consumer duplicating the whole template (R3). The reader reads the `cpu:`/`ram:` spellings once plugin-vm bumps its spec pin to the tag THIS leg produces — the wire shape lands here first, the consumer pin bump follows the tag.

Concrete edits (6 files, +159/−61):

- `schema/deploy.cue` — `cpus?:` to `cpu?:` (`@go(Cpus,type=int)`, Go field name unchanged), matching `#Vm`. **`disk_size?` is DELETED** (a template's disk is built once per entity; a per-deploy value cannot resize it). **`variants?:` is DELETED** — added in #86, never implemented.
- `schema/_common.cue` — **`#VmVariant` DELETED** with its `variants:` field (added in #86, never implemented — NOT an initial-import field like cpu/ram/disk_size); the stray blank lines left at EOF are removed too.
- `schema/version.cue` — `#SchemaVersion` bumped; the rationale paragraph corrected: cpu/ram/disk_size were DEAD since the initial import, `variants:`/`#VmVariant` was added in #86 and never implemented; the reader is the already-merged plugin-vm#39.
- `schema/deploy_cpu_shape_test.go` (new) — spec-side gating tests, including the `disk_size` removal gate.
- `spec/cue_types_gen.go`, `spec/version_gen.go` — regenerated by `task cue:gen`.

**No migration-table entry.** All of these were unread and unauthored — proven by executed sweeps: the RENAMED-FIELD reader sweep, the DELETED-SURFACE reader sweep (spec + charly, current + history), and the tree-wide AUTHORED-key classification (all below). A declarative `rename_key cpus->cpu` scoped `under_kind: vm` would ALSO rewrite the LIVE `security: {cpus: "2.5"}` string quota nested in the same body — so the charly-side migration uses a SIBLING `opencharly/plugin-migrate` path-scoped reshaper hook that lands AFTER this leg tags.
