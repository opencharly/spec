# 0.2026327.329 — feat(schemagen): the generator is a module-root command, so a consumer runs it by ref

## Summary

`candy/plugin-builder/params/cue_types_gen.go` is generated from its own `schema/builder.cue`, but that repo carries **no way to run the generation** — no `task:`, no script, no workflow (opencharly/plugin-builder#10). `charly task cue-gen` reports `unknown task "cue-gen" (declared tasks: )` there. So the generated file could not be kept in step with its schema, and the only way out was to copy the pipeline into the consumer.

This moves `internal/schemagen` to **`schemagen/` at the module root**:

- **`internal/` blocks every other module**, so no consumer could ever run or import the generator.
- **A module-root `package main` is runnable by ref**: `go run github.com/opencharly/spec/schemagen@<tag> -mode=params -schema=<dir> -pkg=<pkg> -out=<file>`. A consumer repo's generator task then runs THIS generator — one generator, no copied script.
- `charly task cue-gen`, the reproducibility test (`spec/gen_repro_test.go`), `schema/README.md`, `AGENTS.md` and the two package comments that named the path move with it; the regenerated `spec/vocab_gen.go` carries the new header. `AGENTS.md`'s file list now states the new PROPERTY (a module-root command a consumer runs by ref), not just the removed `internal/` constraint.

**The consumer leg's key claim, measured here — the moved generator reproduces opencharly/plugin-builder's committed params file BYTE FOR BYTE:**

```
$ GOWORK=off go run ./schemagen -mode=params -schema=../plugin-builder/candy/plugin-builder/schema -pkg=params -out=/tmp/pb_params_gen.go
$ diff -u ../plugin-builder/candy/plugin-builder/params/cue_types_gen.go /tmp/pb_params_gen.go ; echo "diff_exit=$?"
diff_exit=0
```

So that repo's generated file is already in step; what was missing is only the ability to regenerate it — which the next leg (a `cue-gen` task in plugin-builder, run by ref against this module) supplies.
