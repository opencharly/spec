# 0.2026257.1817 — fix(deploy): scope FindVMClaimant to the deploy identity + add vm.image_dir

## Summary

Two `spec`-owned changes. `spec` is the **contract module** (proxy-resolved; `sdk` and the plugin candies pin it), so this is the PRODUCER-FIRST landing of a small cross-repo chain — the consumers are open and land in dependency order (named below).

### 1. `fix(deploy): scope FindVMClaimant to the requesting deploy identity`

**RCA (R1).** MANY deploys routinely share one `kind:vm` entity — a 16-bed omarchy suite all `from: omarchy-vm` — and exactly one carries `requires_exclusive: [nvidia-gpu]`. `FindVMClaimant(tree, entity)` scanned the whole tree for `node.From == vmEntity && len(node.RequiredExclusive()) > 0` and returned the FIRST match regardless of which sibling was asking. So **every** VM created from that entity inherited the GPU claim. Observed live: `check-omarchy-iso-vm`, a GPU-free bed, failed `charly vm create` with

```
charly-check-omarchy-iso-vm requires exclusive GPU resource "nvidia-gpu" (gpu vendor 0x10de)
but no matching GPU was found on this host
```

on a host whose only display device is a Cirrus VGA. The bug predates and is unrelated to the 4.0.3 ISO change that surfaced it.

**Change.** `FindVMClaimant` gains a `claimantID`:
- non-empty → IDENTITY-SCOPED: resolve ONLY that exact deploy, compared after `spec.VmDomainIdentity` normalization (deploy key `vm:prod/hybrid` and domain identity `prod-hybrid` both match). A sibling can never hijack.
- empty (the direct `charly vm create <entity>` path, no deploy identity) → the legacy scan, but now returns **ambiguous (false)** when >1 node claims the entity exclusively, instead of an arbitrary map-order winner.

### 2. `feat(config): vm.image_dir`

Adds the `vm.image_dir` field to `RuntimeVmConfig` — the configurable root for built VM disk images, so it is no longer a hardcoded relative literal in the SDK. This is **additive contract surface**: the field is read/written by named consumers, not inert by omission.
