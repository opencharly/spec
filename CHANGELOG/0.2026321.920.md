# 0.2026321.920 — fix(cue): derive #Answer.unanswered from a vocabulary table (D-PAT-3)

## Summary

`#Answer.unanswered` was a three-value inline union carrying a default, which D-PAT-3 forbids ("only
a two-value literal default is written inline; otherwise derive it from one tag table (S4) or one
vocabulary table (S3)"):

```cue
// before
#Answer: {
	expect?:    #Matcher
	unanswered: *"refused" | "granted" | "cancelled"
}
```

The three words are a closed set, so they become a vocabulary table in the shape this module already
uses everywhere else — the table is the words, `<x>Word` is derived from it, and the enum an author
meets is `or(<x>Word)`, so the table and the enum cannot disagree and a new word is ONE row:

```cue
// after
// #Answer.unanswered (D-FLOW-3) — three words, so a VOCABULARY TABLE (S3), not an inline
// union: D-PAT-3 allows an inline literal default only for a two-value set, and a table makes
// the enum and the words unforgeable from each other (a new word is ONE row here).
_answerUnanswered: {
	refused:   {}
	granted:   {}
	cancelled: {}
} @vocab(spec)

_answerUnansweredWord: [for w, _ in _answerUnanswered {w}]

#Answer: {
	expect?:    #Matcher
	unanswered: *"refused" | or(_answerUnansweredWord)
}
```

Semantics are unchanged: `refused` is still the default, and the same three words are accepted.

**Why this blocks every consumer of the schema.** `opencharly/opencharly`'s pre-push gate compares
its schema-pattern census against `design/dpat-baseline.tsv` and fails on ANY new violation ("the
census is lowered, never raised"). A spec commit carrying one therefore cannot be pinned by the
umbrella's wave — which is exactly what happened: the wave advanced `spec`, the gate refused it, and
`spec` had to be held back (opencharly/spec#346).
