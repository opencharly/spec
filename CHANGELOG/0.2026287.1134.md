# 0.2026287.1134 — feat(schema): add the firecracker microVM substrate contract (kind + deploy + state)

## Summary

Registers the **`firecracker` microVM substrate** in the contract. A `kind: firecracker` entity is a microVM a host boots directly under KVM from a rootfs artefact plus a kernel — no libvirt, no domain, no host arbiter lease — and a deploy node names such a template via `from:`. This is the schema leg of the Firecracker + Fireactions integration (the umbrella ledger, `.dsh/ledger/firecracker-fireactions-integration.md`, work items WI-1/WI-2). Closes #226.

**The contract** (`schema/firecracker.cue`, 369 lines, closed):

- **Host surface** — `vmm` (release + digest + the jailer posture, off by default), `kernel` (`from` artefact or `path`, digest, command line, initrd), `network` (TAP or CNI, the egress interface, the forwarding posture, the guest resolver — a stock Firecracker guest image ships none), `containerd` (address/namespace + **`snapshotter: devmapper | blockfile`** + the devmapper pool and its thin-pool profile + typed-open `plugins` + registry mirrors + service form), and `fireactions` (`version`, install, bind address defaulting to **loopback** because the orchestrator's API is plaintext and unauthenticated upstream, GitHub App credential *reference* — never a key — and the `pools`).
- **Per-instance surface** — `image` (artefact + format + disk size + resize), `machine` (vcpu/mem/smt/huge pages/cpu template, `drives`, token-bucket `rate_limits`), `mmds` (V2 with the tree under `latest/meta-data`), `cloud_init` (the shared `#VmCloudInit`), `vsock`, `console`, `snapshot`.
- `schema/firecracker_client.cue` — the host↔plugin internal wire family.
- `node.cue` — `#ResourceKind` += `firecracker`; `#FirecrackerValue: (#Firecracker | #DeployValue)`.
- `substrate_template.cue` + `resolvedproject.cue` — the resolve-to-envelope form and the template-map arm the kernel reads.
- `deploy.cue` — `firecracker_state` + `#FirecrackerDeployState`, on `#Deploy` **and** `#DeployState`.
- `status.cue` + `spec/status_types.go` — the substrate discriminator on both sides.

**`image` is optional, deliberately.** A `kind: firecracker` template is either a *host profile* — the kernel and the host's capabilities, which the instances inherit from — or a complete instance. Only the second names an image, so making `image` required would have made the first unauthorable; the deployed shape's requirement ("a deploy has an image as well as a kernel") is the plugin's `OpValidate`, and the def's header says exactly that. The gate `TestFirecrackerValue_HostOnlyTemplateAccepted` keeps the profile form authorable, and it fails if `image` becomes required again.

**The venue decision, stated because it is load-bearing.** A microVM is reached over SSH, so this reuses `venue: "ssh"` and adds **no new venue value** — and it must **omit `exclusive_venue`**. Claiming an exclusive venue would make `IsVmVenue` (ssh ∧ exclusive) true and misroute the deploy into `charly vm build`/`vm create`, which is exactly the bug `fe624e5` fixed for kubevirt. The def documents this at its head so the next substrate does not repeat it.

Those last two exist because of a defect this round found in my own gates, and it is the reason
the acceptance checks now demand completeness. CUE reports a **missing required field as
incomplete, not erroneous**, and plain `Validate()` allows incompleteness — so a body with a
required field absent unified happily against `#FirecrackerValue` whenever any disjunction arm
stayed possible. The earlier version of these gates would therefore have passed against a def
that rejected every documented shape: a test that cannot fail (R7). Measured, after the fix, on
the very same control:

```
$ <make containerd.image required again> ; go test ./schema/ -run HostOnlyTemplateAccepted
  --- FAIL: TestFirecrackerValue_HostOnlyTemplateAccepted
      a host-only kind:firecracker template (no image) rejected by #FirecrackerValue:
      image.from: incomplete value !=""
```

One gate was **deleted** rather than kept as decoration: "the kernel is still required" cannot be
made to fail through this unification call, because a missing field whose value is a plain struct
reference is not flagged — the test file records that measured limit so the next reader does not
assume a gate where there is none.

`TestFirecrackerValue_SnapshotterEnumRejected` checks **both directions** — `devmapper` and `blockfile` accepted, `overlayfs` and `native` refused — because the point of the enum is that only a snapshotter whose mount is a device or a file can back a microVM root drive. A rejection-only test would pass on a def that rejected everything.

Every test drives the **shipped** schema through `schemaconcat.ConcatSchema(schema.FS, …)` — the same concatenation the loader uses — not a fixture copy, so a gate here is a gate on the artifact that ships.
