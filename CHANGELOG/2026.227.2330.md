# 2026.227.2330 — a lock file that says nothing, and the truncate that keeps it that way

Placeholder CalVer (the pr-validator finalizes it at merge).

`AcquireFileLock` wrote `pid=%d` into every lock file it created. Nothing read it.

## What the measurement showed

Thirteen production call sites across `spec`, `sdk`, `candy` and `charly`. Exactly
**one** needs the file's content — `candy/plugin-box`'s build-activity lock, which
overwrites it with the build CalVer immediately after acquiring — and exactly
**one** reads it back, `candy/plugin-clean`'s retention floor. Same pair. For the
other **twelve** the line was read by nothing.

No test in any repo pinned the content, and `spec/lock` had no test file at all.

## Why a line nobody reads was worth removing

Because it was not inert. A `pid=` line in a lock file is the visual signature of a
**pidfile** lock, and pidfile locks genuinely do go stale — so the artifact taught
a mechanism it does not have, and the wrong mechanism prescribes an action:
hand-deleting a lock file the CLI owns.

The real mechanism is the opposite. The kernel releases an `flock` when the holder
dies while the FILE persists untouched, so **presence proves nothing and absence
proves nothing**. `ps` is the only discriminator.

That is not theoretical. The line misled three independent readers in one session —
two of them people who had, that same day, written down that these are not pidfile
locks. It is not a subtle trap for the careless; it is a reliable one for the
careful.

## The `Truncate(0)` is KEPT, deliberately

With the write gone it reads as dead code, so this entry records why before someone
tidies it away.

`os.OpenFile(O_CREATE|O_RDWR)` does **not** truncate. Without the truncate, a
re-acquired lock retains the *previous holder's* bytes — replacing misleading
content with **stale** misleading content, which is worse, because staleness reads
as currency. Keeping it leaves every non-writing lock genuinely empty, which is the
state that teaches nothing.

## Coverage — capability-creation, not regression

The first tests in `spec/lock`. There is no before/after pair to show, because the
behaviour was never asserted anywhere; a reviewer looking for one will not find it.

| Test | Fails when |
|---|---|
| `WritesNothing` | the pid write returns |
| `TruncatesStaleContent` | `Truncate(0)` is removed |
| `CallerContentSurvives` | the `plugin-box` write-after-acquire pattern breaks |
| `NonBlockingBusy` | the flock is not actually taken |

The last one exists because the first three are content assertions: a change that
broke locking entirely — never taking the flock — would leave all three green.

Both halves mutation-proved, each reverted alone against the **committed** fix:

```
reinstate pid=      -> FAIL WritesNothing ("pid=2790729\n") + FAIL TruncatesStaleContent
remove Truncate(0)  -> FAIL TruncatesStaleContent ("2026.001.0000\n" — the previous holder's)
restored            -> ok  github.com/opencharly/spec/lock
```
