## Summary

**Producer half of opencharly/charly#829**, whose subject is a published-surface defect: a plugin's `schema/*.cue` is published (`charly docs generate` renders it into `reference/plugin/<plugin>/plugin-*.md`), and R4a requires every command a reader is told to run to work with **nothing but the `charly` binary installed** — but no `charly` command can drive the schema→Go pipeline, so pages have had to publish a checkout-relative recipe (a `cd` into a `spec` checkout, `internal/schemagen`, `cue exp gengotypes`).

This head answers the review's block by making the "ONE home" claim **true in this tree**, not by naming a later PR: both re-key edits are same-repo, so they belong here. Nothing is deferred and no PR is parked.

- **`schemaretag` — the tag-normalization contract, now the only one.** `internal/schemagen`'s retag mode calls `schemaretag.Normalize`; its own regexes are **deleted**. `cue exp gengotypes` emits json tags only while every committed `cue_types_gen.go` carries yaml tags, so the pipeline's third step (after `schemaconcat` and generation) is declared once, shared by spec's own generator and the coming `charly`-side verb — a generated file cannot depend on which caller produced it.
- **`cuetoolchain` — the pin's one home, and now the one fetcher.** Version, tarball, URL, per-arch checksum, `Pin()`, plus `Ensure`/`ExtractMember`: an existing binary is accepted only if it **reports the pinned version** (a stale cache is re-provisioned, never served as success), an unpinned arch fails *before* any download, and the checksum is verified *before* extraction so a mismatch leaves nothing behind (the write is atomic: tmp + rename).
- **`bootstrap-cue` re-keyed onto it.** The task no longer carries the version, URL, checksum or the extraction dance inline in shell; it runs `go run ./internal/cuesetup bin`. The inline pin is **deleted**, so there is one declaration of the toolchain rather than one in Go and one in shell.

**Files (8, +546/−46):** `schemaretag/schemaretag.go` (+41) + test (+63); `cuetoolchain/cuetoolchain.go` (+193) + `cuetoolchain_test.go` (+48) + `provision_test.go` (+158); `internal/cuesetup/main.go` (+27); `internal/schemagen/main.go` (+12/−24); `charly.yml` (+4/−22, the task).

**The provisioning tests are hermetic** (an `httptest` server and in-memory tarballs — no network, no pinned release needed): the extractor selects only the `cue` member and leaves no `.tmp`; a checksum mismatch is refused *before* extraction and leaves nothing at the destination; the correct checksum is accepted; an already-pinned binary is reused without downloading; and a binary reporting another version is never served as success.

**Two of my own assertions were wrong before they were right, and both corrections came from running them** — which is the only reason this head can be trusted:
1. the tag expectations: I asserted the transform produced a bare `yaml:"name"` for `json:"name,omitempty"`; it **failed**, and the measured truth is that the first pass copies the json value verbatim (options included) and the second only touches keys still bare — the behaviour that reproduces a committed generated file byte-identically;
2. the stale-cache assertion: I compared **paths** (`got == stale`) to prove the stale binary was not served — but the pin deliberately lives at one path, so a successful re-provision overwrites that same path and the comparison said nothing. It now asserts the **version at the returned path**, and that arm really does exercise the re-provision.
