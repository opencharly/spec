# 0.2026257.1148 — feat(deploy): add keep_on_failure (default false) to #Deploy

## Summary

Add a dedicated, **default-false** deploy/check-bed option `keep_on_failure` to `#Deploy`: whether a **check bed that fails keeps its venue alive** for debugging. Default `false` — a failed (or timed-out) bed **tears its venue down** on every exit path, so a stalled/failed lane can never leak a running VM/container that spins CPU.

### The bug this enables fixing

The eval-lane 16-PR suite stalled: 13 lanes hit the 5-minute post-restart reconnect deadline, and — because the bed runner's failure tail **unconditionally retained the venue** — 16 qemu processes kept running at ~1194% CPU while nothing progressed. There was no way to opt OUT of retention. This adds the option (the consumer fix lands in `plugin-check` + `eval-omarchy`).

### The field

```cue
// #Deploy
keep_on_failure?: bool @go(KeepOnFailure,type=bool)
```

- **Default `false`** (absent ⇒ tear down on failure). Fail-closed: a failed bed never leaves a live venue behind.
- `true` ⇒ retain the venue after a failure for operator inspection (the operator destroys it explicitly).
- Distinct from `ephemeral.keep_on_failure` (that governs the TTL reaper's disposition of an EPHEMERAL deploy); this one governs the CHECK BED runner's failure tail. The two are documented as distinct in the CUE comment to prevent conflation.

Additive optional authored key with **no config rewrite required**, so per the schema-change recipe (step 6: bump only on a wire-key change that requires migration) this does **not** bump `#SchemaVersion` — matching the `parallel?:` precedent (also an additive optional deploy field, no bump).
