# 0.2026241.1322 — perf(refs/container): persistent caches for the status hot path

## Summary

`charly status` was 12.6s warm; the RCA found three repeated-cost sources: (1) 514 `git remote get-url origin` spawns on the per-host config dir (repo identity), (2) ~200 `git config -f .gitmodules` spawns (submodule checks), (3) 2 `podman images` store scans (215K lock opens each). All three are METADATA — the LIVE container state (`podman ps`) is never cached.

- **`spec/cache`** (new): the ONE shared persistent-cache mechanism (R3) — `Read`/`Write`/`Invalidate` with a TTL policy, used by all three caches below. Placement: spec (not sdk) is the correct layer — the consumers are `spec/container`, `spec/refs`, and `spec/spec`, and the dependency direction is sdk → spec, so a spec package cannot import sdk (a cycle). The mechanism is a spec subpackage, the same layer as the consumers.
- **`spec/repo_identity.go`**: `GitRemoteIdentity` cached process-wide per dir (the identity is stable for the process lifetime) — 514 spawns → 1.
- **`refs/git.go`**: `submodulesPopulated` cached process-wide + PERSISTENTLY (the repo cache dirs change only on a re-fetch) — ~200 spawns → 0 warm.
- **`container/local_image_coneb.go`**: `ListLocalImages` cached persistently (the image list changes only on build/pull) with a 5m TTL + user feedback on the first run; `InvalidateImageCache` is the API the build/deploy commands call — wired in the status-caches plugin PRs (plugin-build#feat/status-caches and plugin-deploy-pod#feat/status-caches, the same thematic batch as this PR).
- **`container/image_inspect.go`**: `InspectImageLabels` cached persistently (the labels are image metadata) with a 5m TTL.

The caches live under the charly dir (`~/.config/charly/cache/`). The first run after a TTL expiry re-fetches with user feedback; every subsequent run reads the cache. Measured: `charly status` 12.6s → 0.63s warm.
