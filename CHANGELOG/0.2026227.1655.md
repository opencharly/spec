# 0.2026227.1655 — fix(container): refuse a stale short-name election in the build-scope verdict resolver

> ### ⚠️ Round 5 — a regression THIS chain introduced, and the gate that missed it
>
> Unifying the resolver's two recency orderings into one `moreRecent` comparator
> **made the staleness guard a tautology, and it shipped green.** With both the
> election's sort and the newest-build scan using the same total order, `cands[0]`
> IS the maximum the scan returns — so `NewestBuildRef == Ref` always and
> `RefuseIfStale` had nothing to compare. The guard could never fire.
>
> **Why the suite stayed green is the more useful part.** Every refusal test used
> the two-family label split, where the newest-build scan walks the WIDER union and
> can still differ. None covered a **single-family stale election** — the exact
> scenario the guard's own doc comment names: *"an image built from a
> differently-versioned source tree outranks a newer build"*. A whole class was
> untested, so a dead guard passed.
>
> **The two orderings must differ in their PRIMARY key; the difference IS the
> mechanism.**
>
> - `electionOrder` — primary `labelCalVer`. *Which artifact does this NAME mean.*
>   A short name refers to a box's content, not to whatever was compiled last.
> - `buildOrder` — primary `created`, deliberately blind to the content label.
>   *Which of these was BUILT most recently.*
> - `orderTail` — the shared deterministic last resort. Arbitrary is fine;
>   DISAGREEING is not, and two disagreeing last resorts were the genuine
>   duplication (they refused a pair in which neither was newer).
>
> R3 applies to the tail. It does not apply to two answers that are supposed to be
> able to contradict each other — deduplicating those deletes the contradiction the
> guard detects.
>
> **Coverage: `TestResolveBuiltImageRef_SingleFamilyStaleElectionRefuses`**, written
> before the fix and failing against the unified comparator:
> ```

>     ResolveBuiltImageRef(web) = "ghcr.io/opencharly/web:2026.227.0830", nil — want a REFUSAL

> Each ordering level is now **independently mutation-gated**, one distinct test per
> level — so a future unification cannot pass silently again:

## Summary of changes

`charly check box <box>` could certify an image that was not the one you built, report every step green, and give no sign. This is the resolver half of the fix; the emitter half is `opencharly/sdk`, the call sites are `opencharly/charly`.

Measured 2026-08-15 (day 227): a `check:` step was added to a candy, the box rebuilt as `ghcr.io/opencharly/fedora-nonfree:2026.227.0835` / `:0836`, and `charly check box fedora-nonfree` printed `Image: ghcr.io/opencharly/fedora-nonfree:2026.216.1908` with `5 passed, 0 failed` — the OLD baked plan, the new step absent entirely. Two shapes in `ResolveLocalImageRef` reach that outcome, both traced against the real image store rather than reasoned about:

1. candidates split into a LABEL family (`ai.opencharly.box == <short>`) and a NAME family (trailing repo segment matches); the label family is taken WHOLE and the name family discarded (`cands := labelCands; if len(cands)==0 { cands = nameCands }`). A build whose label disagrees with its own repo name lands in the name family and is dropped regardless of how much newer it is.
2. the election's PRIMARY key is the content-derived `ai.opencharly.version` label with the per-build tag only a tiebreak, so an image built from a differently-versioned source tree (a sibling worktree, a pulled release) outranks a newer build regardless of when either was produced.

Concrete edits, all in `container/local_image_coneb.go` + `spec/image_errors.go`:

- `LocalImageResolution` — the full answer: the elected `Ref`, the `NewestBuildRef` (highest build-tag CalVer across BOTH candidate families), and `Pinned`.
- `ResolveLocalImage` — the single body doing the candidate gather, the ordering, and the ambiguity error. `ResolveLocalImageRef` becomes a thin wrapper returning `.Ref` (R3 — one gather, one ordering).
- `ResolveBuiltImageRef` — resolves, then REFUSES when the elected image is not the newest local BUILD, wrapping `spec.ErrStaleLocalImage` and naming both refs plus the runnable pinned re-invocation.
- `LocalImageResolution.RefuseIfStale` + `newestBuildRef` helper.
- `spec.ErrStaleLocalImage` — new sentinel next to `ErrImageNotLocal`.
- `container/local_image_coneb_test.go` — five tests over a fixture reproducing the measured storage byte-for-byte.

The election itself is UNCHANGED. Every consumption path (deploy, `charly vm build`, builder bootstrap, kube preresolve) keeps the lenient `ResolveLocalImageRef`; only the verbs that pronounce a verdict on an artifact opt into the guard. Changing the primary key globally would change what `charly update` and the deploy paths resolve to — far broader than this defect justifies, and with its own wrong case (a colleague's build from older sources winning). A stale check that errors is recoverable; one that PASSes is not.
