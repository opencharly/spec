## Summary

The validator on opencharly/spec#286 judged the guard correct and raised three observations against it, explicitly as "minor, non-blocking". #286 merged at 07:48:43Z on the validator's PASS, so these three fixes land in their own PR rather than as a second commit on the merged one.

R1 does not let them be filed away: it classifies a finding as blocking when "this change introduces it", and all three are code that #286 introduced. So each is fixed here.

- **The keys a type carries were collected and never read — dead code.** `TypeFields.Keys` was populated by `DeclaredTypes` and read by nothing. It is now read: the rule that judges a withdrawn name's replacement also judges a SCOPED configuration key's replacement against the keys its scoped type carries, which is the configuration-key counterpart of the field rule that was already there. The rule is extracted into `replacementLanded` so it is one named rule rather than an inline block, and it has its own fail-without test — a rule that cannot fail proves nothing.
- **The token rule had two behaviours' worth of code.** The predicate matched a name as a TOKEN, but the line reporter took the first raw substring, so a name whose first substring sits inside a longer word was reported at the line of that substring — a place where the name does not occur as a token. The rule now lives once, in `tokenIndex`, and both the predicate and the reporter read it, so they cannot disagree about which occurrence matched.
- **The file's struct types were walked twice.** `scanGoFile` derived them once to collect the tag positions and again to scan the declarations. It walks them once now.

No behaviour of the guard changes: what it detects and what it reports is the same, except that a reported line now points at the occurrence that was actually matched.
