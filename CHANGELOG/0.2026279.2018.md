# 0.2026279.2018 — fix(exec): source a candy's env.d for non-interactive machine-venue commands (charly#814)

## Summary

Make a candy's `env:` reachable to **non-interactive** commands on a machine venue
(`target: local`, `target: vm`), so a deploy `run:`/`check:` and a `command:` check
probe see the same env an interactive shell would. Fixes #814.

### The defect

A candy's `env:` compiles to `~/.config/opencharly/env.d/<candy>.env`, sourced by a
managed block charly writes into the venue's shell INIT file (`~/.bashrc`). bash sources
that file **only for an INTERACTIVE shell**, so on a machine venue:

- every non-interactive deploy `check:`/`run:` command,
- the check engine's `command:` probe, and
- a plain `charly vm ssh <box> -- '<cmd>'`

ran **without** the candy's env. A candy whose own `check:` asserts its env — the
`dsh-tui` candy's `printenv DSH_TUI_NO_LAUNCHPAD` — therefore failed on a machine venue
even though the deploy wrote its env file correctly. The image/pod path is unaffected
(there the env is a container `ENV`, present to every process), which is why the same
check had never been exercised: under the pod path it SKIPs on an unresolved variable.

### The fix

Prefix each non-interactive rendered command with a POSIX-sh preamble that sources the
venue user's own env.d directory:

```sh
for f in "$HOME"/.config/opencharly/env.d/*.env; do [ -r "$f" ] && . "$f"; done;
```

- `$HOME` is expanded **on the venue** (the snippet runs there), so one constant serves
  every machine venue.
- A glob matching nothing leaves the loop body unrun (the `[ -r ]` guard), so a venue
  with no env.d is unaffected.
- The trailing `; ` lets a caller concatenate its command.

Both the deploy walk and the check engine converge on these **leaf executors**, so
prefixing the shared non-interactive spawn helpers makes the SAME env reachable to a
`check:` probe and a deploy `run:` at once (R3 — one rule, all call sites).

### Placement — opt-in, so the container substrate is untouched

| site | change |
|---|---|
| `ShellExecutor.MachineVenue bool` | new field; `true` for a `target: local` / `host: local` root (`RootExecutorForDeployNode`) and for a re-materialized `shell` `VenueDescriptor`. **`false`** for the throwaway `ShellExecutor{}` a container-jump `NestedExecutor` uses purely as a LOCAL HOST transport — its payload executes INSIDE the container, whose env already comes from the image's `ENV`, so the host's env.d must not leak in. |
| `ShellExecutor` (`run` + `RunCapture`) | prefix the preamble on the **unprivileged** leg only. Deliberately **not** the `sudo` leg: a candy's `env:` is the deploying user's, while `sudo` resets `HOME` to root's — so the user-scoped env is neither reachable nor intended there. `RunCapture` is the leg the check engine's `command:` probe reaches. |
| `SSHExecutor` (`run` + `RunCapture`) | always a machine venue: prefix the unprivileged leg (the guest user's env.d), not the sudo leg. |
| `NestedExecutor.prepareJump` | a `JumpSSH` (nested-in-VM) payload is prefixed **before** the wrap, so it lands inside the guest; a `JumpContainerExec` payload is not. |
