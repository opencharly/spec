# 0.2026330.2134 — feat(staging): content-address the candy staging dir, not its ref

## Summary

`CandyStageDirName` keyed the build staging directory by `<name>.<version>`, so a ref-only change —
the *same* candy content at a new tag or branch — produced a different `COPY` source path and
invalidated every BuildKit layer beneath it. Measured on the openwebui image: **2400 s cold, 90 s for
the same tree, 683 s for the same content at a new ref**.

This addresses the directory by the candy's **content**: `<name>.<sha256[:16]>` over the sorted
relative paths, each regular file's **executable bit** and bytes (symlink targets included; `.git`,
mtimes, owners and the other permission bits excluded — git applies the umask to those, so they differ
between checkouts of identical content). Consequences:

- **Identical content at two refs shares one directory** → the Containerfile's `COPY` source and its
  layer key stay stable, so a ref-only change reuses the cached pixi stage instead of re-executing it.
- **Different content gets a different directory** → two versions never clobber each other; the stager
  already installs atomically (`kit.InstallDirAtomic`, renameat2 RENAME_EXCHANGE).
- **No source dir / unreadable walk** → falls back to the version-keyed name, so a caller never stages
  under an address it could not derive.

The stager (`plugin-build`'s `createRemoteCandyCopies`, `host_prep.go:180`) and the `COPY` source
(`sdk/deploykit`'s `CandyCopySource`, `candy_stage.go:41`) both call this ONE function, so the name is
derived in one place — the change is a single implementation, not a second naming path.

### Spike

| Candidate | Run + result |
|---|---|
| A — keep `<name>.<version>` | the status quo: a ref change re-copies to a new path and invalidates the layers (2400 s cold → 90 s same tree → **683 s new ref**, measured on openwebui) |
| A2 — bind-mount the candy instead of COPY | **not a viable candidate**: it moves the COPY source to a live path outside the image, so no in-image layer key exists to stabilise — stated as a rejection, not spiked |
| **B — content-address the directory** (winner) | the three witnesses above: identical content → one name, different content → different names, no source dir → version fallback |

### The cross-repo proof (producer-first)

`spec` is a Go-module dependency of `charly`, so the end-to-end measurement — two builds of identical
content at two refs, comparing the pixi stage duration against the 683 s baseline — runs at the
consumer's leg: this PR merges and tags, `charly` bumps its `spec` requirement to that tag, the binary
is rebuilt, and the two builds are pasted there. That is the sanctioned producer-first order
(`/charly-internals:git-workflow` B6), not a deferral of this change's own gate: this PR's gate is the
unit witnesses above, which fail without the change.
