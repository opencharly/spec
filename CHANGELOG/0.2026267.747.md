# 0.2026267.747 — fix(calver): rank Go-module tags on the same timeline as plain CalVer

## Summary

Fix the CalVer comparator so the two tag encodings the org uses sort on **one timeline**. A repo mid-migration carries BOTH:

- the **plain CalVer** form `v<YYYY>.<DDD>.<HHMM>` (every non-Go-module repo), and
- the **Go-module** form `v0.<YYYYDDD>.<HHMM>` (the semver-required form for the proxy-consumed root module repos `sdk`, `spec`, `plugin-gh`; semver forbids a leading-zero patch segment, so `0733`→`733`).

`CompareCalVer` compared component-wise, so the Go form's major `0` ranked **below** the plain form's `2026` — the **stale** plain tag won over a **newer** Go-form tag. Measured on the real tag sets:

| repo | stale plain tag (was returned) | newer Go-form tag (correct) |
|---|---|---|
| `plugin-gh` | `v2026.252.1501` | `v0.2026266.2326` |
| `spec` | `v2026.240.1944` | `v0.2026266.2126` |
| `sdk` | `v2026.232.1949` | `v0.2026266.2340` |

This broke any "newest tag" consumer: the docs `extra_repos` resolution (`refs.GitLatestTag` → the `charly docs generate` catalog) pinned `plugin-gh` to a tag from 2026-09-09 and could not see the merged `document`/`issues` work, so the generated page stayed frozen at `github-com-opencharly-plugin-gh-v2026-252-1501/`.

**Fix:** `normalizeCalVer` rewrites the exact Go-module form `0.<7 ASCII digits>.<all-digit HHMM>` to the canonical `<YYYY>.<DDD>.<HHMM>` tuple (re-padding zero-stripped components), applied inside the ONE comparator `CompareCalVer` (`refs.CompareSemver` delegates here). The plain form and any genuine semver (`v1.2.3`, `v0.1.2`) pass through **byte-identical**, so their existing component-wise semantics are unchanged. No schema/API change — a pure comparator bug fix (no cutover).

## How tested

**Unit, real output:**

```
$ go test ./calver/... ./refs/...
ok  	github.com/opencharly/spec/calver	0.018s

```

New tests:

- `calver/calver_parse_test.go` — `TestCompareCalVer` (12 cases incl. the three real mixed-form pairs, `same-tuple-across-encodings`, and the anti-symmetry guard) + `TestNormalizeCalVer` (the exact-form boundary: only the 7-digit Go form is rewritten; plain CalVer, `v1.2.3`, `v0.1.2`, a 6-digit second component, a non-digit HHMM, and a 4-part string all pass through).
- `refs/git_test.go` — `TestGitLatestTag_MixedTagForms`: a **local** git repo (no network) carrying the real `plugin-gh` tag shape, asserting `GitLatestTag` returns the newer Go-form tag, not the stale plain one.

**Non-vacuous:** neutering `normalizeCalVer` to a no-op makes both fail with the exact production symptom —

```
    calver_parse_test.go:43: CompareCalVer("v0.2026266.2326", "v2026.266.2326") = -1, want 0
    git_test.go:368: GitLatestTag = "v2026.252.1501", want v0.2026267.723
```

**Live proof against the REAL tag sets** (the fix, run against api.github.com via `git ls-remote`):

```
spec           GitLatestTag="v0.2026266.2126"   (was v2026.240.1944)
sdk            GitLatestTag="v0.2026266.2340"   (was v2026.232.1949)
```

The plain-form repos are byte-identically unaffected; the mixed-form repos now resolve to their true newest tag.
