# 0.2026250.158 — fix(refs): the WarmUp prefetch honors the persisted latest_tags fallback (the #108 warm-up-hang regression)

## Summary

refs.GitClient.WarmUp (the startup prefetch behind "charly: fetching git metadata for N repo(s) (first run)") regressed in #108: the offline-fallback cutover correctly moved the persisted latest_tags entries from fresh-data-with-TTL to OFFLINE-FALLBACK-ONLY, but WarmUp's cold-check kept consulting only the IN-PROCESS maps - which start empty in every fresh process. Result: every project load re-probed the entire collected corpus over the network.

Measured live on the opencharly umbrella host: a project whose persisted cache already held **316 latest_tags + 279 default_branches entries** printed "fetching git metadata for 193 repo(s) (first run)" on every fresh process and ran 193 repos x 2 git ls-remote ops (~23 s healthy, uncontended). The pre-#108 model served the persisted entry as fresh, so the prefetch found ~1 cold repo and returned instantly - which is exactly why the same bed passed at run 2026.249.2233 ("fetching git metadata for 1 repo(s)" in its deploy-add log) and hung at run 2026.250.0131.

Under concurrent bed runs (the CC-1 wave: multiple charly processes x 10 warm-up workers each), the aggregate ls-remote fanout trips GitHub's throttling threshold (the documented 152-concurrent-ls-remote storm this layer was built to prevent); every throttled fetch then burns its 30 s-deadline x 3 bounded retries, stretching the 23 s warm-up into tens of minutes per process - the observed deterministic hang of two independent binaries at the identical line.

**The fix** restores WarmUp to a UX batch, never a resolution: a repo whose PERSISTED latest_tags fallback carries an entry is prefetch-warm. The #108 freshness contract is untouched - the on-demand LatestTag path still re-probes the network in every fresh process (guarded by the existing offline-fallback tests), and a repo pinned at immutable tags never resolves a latest tag at all, so for those repos the probe was pure waste. A genuinely cold repo (no persisted entry) still prefetches, unit-pinned.
