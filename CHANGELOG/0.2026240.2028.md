# 0.2026240.2028 — feat(vm): close the video device/driver vocabularies against libvirt RNG

## Summary

A follow-on to `#63` (merged), from validating the **rendered** domain XML against libvirt's own
RelaxNG schema instead of reading the documentation.

`#LibvirtVideo.device` and `#LibvirtVideoDriver.name` / `.vgaconf` landed as plain strings.
libvirt's RNG closes all three, so an invalid value was accepted at config time and rejected at
**define** time — with a Relax-NG error that blames `<devices>` rather than naming the attribute.

Transcribed from `/usr/share/libvirt/schemas/domaincommon.rng`:

| field | vocabulary | RNG location |
|---|---|---|
| `device` | `virtio-vga`, `virtio-vga-gl`, `virtio-gpu`, `virtio-gpu-gl`, `vhost-user-vga`, `vhost-user-gpu` | the `<model type='virtio'>` group |
| `driver.name` | `qemu`, `vhostuser` | the video `<driver>` element |
| `driver.vgaconf` | `io`, `on`, `off` | same |

`"qxl"` is the plausible wrong guess for a driver name — it is a valid video **model**, not a
driver — and the schema used to take it. My own test had exactly that mistake in it until the
RNG rejected the output.

## How this was found

Not by reading docs. By rendering the domain and handing it to libvirt's validator:

```
$ virt-xml-validate blob-native-context.xml domain
```

The same method found two more defects, both fixed in the paired plugin-vm renderer PR and
neither visible from the Go structs:

- **`blob=` and `edid=` are `virOnOff`**, not `virYesNo` like `primary=`/`accel3d=` immediately
  beside them in the same element. Rendering `blob="yes"` produced XML libvirt refuses.
- **`<qemu:property type=>` has no `number`** — the vocabulary is
  `string | signed | unsigned | bool | remove`.

## How tested

**The first version of this test was wrong, and the validator was right to block it.** It only
unmarshalled *valid* values and asserted they decode — but `cue exp gengotypes` renders all
three fields as plain Go `string`, so it passed identically with the enums reverted. It proved
nothing about the closure, which is the entire change.

The closure lives **only** in CUE, so the test has to be a CUE test. It compiles the schema
through `schemaconcat.ConcatSchema` — the same single concatenation the runtime and
`task cue:gen` use, so it exercises the schema as it ships rather than a hand-written excerpt —
and unifies concrete values into the definitions, which is the judgement the loader makes on an
authored file.

```
$ go test ./spec/ -run VocabulariesAreClosed -v
--- PASS: TestLibvirtVideoVocabulariesAreClosed
    --- PASS: /device_virtio-gpu-gl_accepted
    --- PASS: /device_vhost-user-gpu_accepted
    --- PASS: /device_qxl_rejected
    --- PASS: /device_virtio-gpu-rutabaga_rejected
    --- PASS: /device_empty_string_rejected
    --- PASS: /driver_name_qemu_accepted
    --- PASS: /driver_name_vhostuser_accepted
```

### The control (B12) — the rejections fail without the change

Reverting the three enums to `string` in `schema/vm.cue`, **tests untouched**:

```
--- FAIL: TestLibvirtVideoVocabulariesAreClosed/device_qxl_rejected
    #LibvirtVideo ACCEPTED {model: "qxl", device: "qxl"} — the vocabulary is not closed
--- FAIL: TestLibvirtVideoVocabulariesAreClosed/device_virtio-gpu-rutabaga_rejected
    #LibvirtVideo ACCEPTED {model: "virtio", device: "virtio-gpu-rutabaga"} — the vocabulary is not closed
--- FAIL: TestLibvirtVideoVocabulariesAreClosed/device_empty_string_rejected
    #LibvirtVideo ACCEPTED {model: "virtio", device: ""} — the vocabulary is not closed
--- FAIL: TestLibvirtVideoVocabulariesAreClosed/driver_name_qxl_rejected
    #LibvirtVideoDriver ACCEPTED {name: "qxl"} — the vocabulary is not closed
--- FAIL: TestLibvirtVideoVocabulariesAreClosed/vgaconf_bogus_rejected
--- FAIL: TestLibvirtVideoVocabulariesAreClosed/vgaconf_yes_rejected
```

All six rejection cases fail; the six acceptance cases still pass, so the test is not merely
rejecting everything. Each rejected value is a plausible slip rather than a random string —
`"qxl"` is a valid video **model** (which is why it is the likely wrong driver name), and
`"yes"` is the neighbouring attributes' spelling.
