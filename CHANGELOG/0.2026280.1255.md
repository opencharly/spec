# 0.2026280.1255 — fix(spec): resolve a local import ref to its PROJECT identity, not the enclosing repo

## Summary

An import ref's identity named its enclosing **repo**, not its **project** — on BOTH ref forms. A namespaced import of a subdirectory project inside the same repo inherited the root's identity, so `walkNamespace`'s repo-identity cycle-break resolved that distinct project as a **REFERENCE mount to the root** — a degenerate self-cycle. Measured consequence: the materialized wire marshaller rejected it with

```
json: unsupported value: encountered a cycle via map[string]*spec.UnifiedFile
```

(the signature of opencharly/opencharly#330) — and once that marshaller is made cycle-safe, the namespace is **silently dropped**, strictly worse than the crash.

`RepoIdentity()` now resolves the **PROJECT** identity on **both** paths — `ProjectRepoIdentity(dir)` resolves a filesystem path (and `RootRepoIdentity()` forwards to it), while the remote branch qualifies the parsed ref by `ParseRemoteRef`'s `SubPath`:

- **remote** `@host/org/repo[/sub][:ver]` → `host/org/repo` **plus `/sub` when a sub-path is present** (`ParseRemoteRef` already exposes it; previously the sub-path was dropped, so a remote subdirectory project collapsed to its repo — the same false back-edge on the other path);
- **local** path → an explicit `repo:` in the project's `charly.yml` is authoritative; otherwise the git `origin` identity **qualified by the project's path relative to the git toplevel** whenever the project is not itself the repo root;
- a repo-root project (a local submodule, or a remote ref with no sub-path) keeps the **bare** identity, so the local↔remote mutual-import short-circuit is unchanged.
