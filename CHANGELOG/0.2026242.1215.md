# 0.2026242.1215 — feat(distro): the installer seed context carries the target disk size

## Summary

`#InstallerSeedContext` gains **`disk_size_bytes`** — the target disk's size, so an
unattended-installer answer template can describe a root partition.

A real installer answer file states partition sizes as **absolute numbers**, not as "the
rest of the disk". archinstall indexes `partition['size']` with no default and offers no
fill-remaining sentinel, so a template that cannot see the disk size cannot describe the
root partition at all.

## Measured, not inferred

The shipping Omarchy 4.0.1 installer aborts in its "Preparing live environment" phase with
a bare `KeyError` when a partition omits a required key — read off a real installer run,
whose output is otherwise hidden behind the ISO's `quiet splash` cmdline.

Its own configurator computes the value from `lsblk -bdno SIZE` on the target:

```sh
disk_size=$(lsblk -bdno SIZE "$disk")
mib=$((1024 * 1024)); gib=$((mib * 1024))
disk_size_in_mib=$((disk_size / mib * mib))

gpt_backup_reserve=$((mib))
boot_partition_start=$((mib))
boot_partition_size=$((2 * gib))
main_partition_start=$((boot_partition_size + boot_partition_start))
main_partition_size=$((disk_size_in_mib - main_partition_start - gpt_backup_reserve))
```

A seed rendered **on the host** has no `lsblk` against a disk that does not exist yet, so
the number has to arrive in the context. Everything else in that arithmetic is constant and
belongs in the distro's template, which is why only the disk size is added here.

## Why bytes as an int

The arithmetic happens in the template, and a template is the wrong place to parse `"40G"`.
Making it an `int` means CUE rejects a suffixed string **at load**, rather than the renderer
failing at execute time inside a guest nobody is watching — the same reasoning the rest of
this schema uses for closed vocabularies.

```
$ go test -count=1 ./schema/ -run 'InstallerSeedContextCarriesTheDiskSize'
ok  	github.com/opencharly/spec/schema	0.013s
```

The test has **teeth in both directions**: it asserts a 40 GiB byte count is accepted, and
that `disk_size_bytes: "40G"` is **rejected** — a schema addition that accepted anything
would be worse than none.

## Rulebook compliance

- **R1 — RCA every anomaly.** The need for this field was established by reading the real
  installer's own parser and its own configurator, not by guessing at a schema.
- **R3 — no duplication.** Only the disk size is added; every other term in the partition
  arithmetic is constant and stays in the distro's template where it belongs.
- **R4 — no workarounds.** The alternative considered and rejected was routing the number
  through the per-distro `answer:` escape hatch, which would make an operator keep it

  stripped schema restored from a backup; the results above are from the committed state.
