# 0.2026288.1655 — feat(exec): the delivery's stable path becomes injectable, so a host-side leg never touches the shared /tmp/charly-plugins

## Summary

Successor to opencharly/spec#245 (auto-closed at the verdict threshold). It carries **only the delivery mechanism and its
tests** — the beds that #245 also shipped are deliberately absent, for the reason given below.

`exec/charly_plugins.go` adds the plugin-tree delivery on both sides of the boundary:

- **`EnsurePluginsInDeployVenue(ctx, ve spec.DeployExecutor, pluginDir, hostVer)`** — the host-side route into a live
  `spec.DeployExecutor`;
- **`EnsurePluginsInGuest(ctx, ssh SSHArgs, pluginDir, hostVer, strategyRaw)`** — the vm-deploy sibling, "at `PrepareVenue`
  time": probe → `tarPluginTree` → `scpInto` → extract → manifest-count verify → `ln -sfn`;
- plus the pure helpers `CountManifests` and `ValidatePluginTree`.

Together these are what a deploy target needs in order to run its project's plugin verbs: a deploy hands its target charly and
**no candy corpus**, so today a plugin-backed step there fails as an unknown command (`opencharly/charly#916`). This change is
the delivery half of that gap.

The diff also adds `+ .check/` to **`.gitignore`**, so a check run's scratch tree is never committed.

## Why no bed accompanies it

`.dsh/skills/check/references/beds-and-r10.md:495` — the **"Contract / library module"** row, which names `spec` — says:

> *"Run the repo's OWN committed module CI … GREEN on the PR head — the module suite IS the gate, because **no bed CAN exist** (a
> bed that cannot fail on the change proves nothing) … A change whose behaviour is observable only at a CONSUMER's live boundary
> names the consumer PR running that bed — the bed rides the consumer change (producer→consumer order, B6), **never the library
> PR**."*

So this repo's gate is its own module CI, and the guest leg's bed belongs to the consumer whose VM bed can exercise it:
**`opencharly/plugin-firecracker#11`**, whose disposable GUEST bed currently fails with `plugin env: unset` because a guest
receives charly and no plugin corpus — the capability this change provides.

**And the host-side delivery leg IS carried here — and it no longer reaches the host's shared published plugin path at all.**
`TestDeliverPluginsToARealExecutor` injects a path under `t.TempDir()`, so `/tmp/charly-plugins` is never touched by any run of the
suite: the DISP hazard that `opencharly/charly#941` records is **removed rather than narrowed**, and this change is what closes it.

**The host-side leg really ran, live.** `TestDeliverPluginsToARealExecutor` drives the delivery end to end against
`ShellExecutor{MachineVenue: true}` — a real executor on this machine, nothing mocked — twice: a cold delivery and the
idempotence re-delivery, which IS the warm path. The manifests are counted on the venue, the modes are stat'd, and the symlink
is read back OFF the venue; the served WORD is asserted by the bed's next step, not here. It fails without the change, because
the warm re-delivery used to skip the publish.

**The guest leg did NOT run here, and says so.** `TestDeliverTheBuiltTreeIntoTheDeployVenue` skips in module CI unless
`SPEC_DELIVERY_TREE` and `SPEC_DELIVERY_HOSTVER` are set; the in-tree guest coverage in `exec/charly_plugins_guest_test.go`
exercises the refusal and the one-rule agreement, not a live guest delivery, which needs a real VM.

**The guest leg now has in-tree coverage** (TestEnsurePluginsInGuestRefusesANonPluginTree and the one-rule agreement test),
so this gap is closed rather than filed; both fail to compile against the base tree, since EnsurePluginsInGuest is new here.
