# 0.2026316.1928 — feat(schema)!: delete the kind:pipeline body defs the owning plugin now declares

## Summary

**Leg 4 of unit 1's five-leg decomposition** (`TODO.md` 2.1, tracker `opencharly/spec#304` row 4). The `kind: pipeline` authored body lives with the plugin that serves it (`plugin-pipeline`'s own CUE module since leg 2, opencharly/plugin-pipeline#63); this deletes the contract module's twins and regenerates.

### What is deleted

From `schema/pipeline.cue`: `#Pipeline`, `#PipelineValue`, and the defs they are built from — `#PipelineRetry`, `#PipelineApproval`, `#PipelineFlow`, `#PipelineArms`, `#PipelineInput`, `#PipelineSubStep`, `#PipelineParallel`, `#PipelineStepBase`, `#PipelineStep`, `#PipelineSchedule`, `#PipelineTrigger`, plus the `_onError` / `_onErrorWord` vocabulary table (`#PipelineFlow.on_error`'s enum). The generated `Pipeline*` Go types go with them (`spec/cue_types_gen.go`), and `spec.KindValueDefs` drops `pipeline`.

**`#PipelineClassRoutes` STAYS.** It is a table over THIS module's own `#ProviderClassNames`, and its extraction lives in `internal/schemagen`'s vocab mode, which no plugin can run and no plugin could read the whole class vocabulary to produce. `plugin-pipeline`'s schema header already records the split: "the contract module keeps exactly ONE def for this kind: #PipelineClassRoutes". The file's header now says that, and why.

### The corpus moved BEFORE the defs were deleted

Deleting a def together with its tests would have been a silent coverage loss: `spec/pipeline_test.go`'s `TestPipelineValueClosedness` (29 cases) and the authored-def cases of `spec/workflow_envelope_test.go` (5 cases) existed only here. They moved to the defs' new home first — `plugin-pipeline#64` (squash `fc2cec31b813b2c5a5d079167c24e488ce5eba3a`), `candy/plugin-pipeline/pipeline_schema_corpus_test.go`, judging the plugin's composed served schema. The move is merged, so this PR deletes only what has a live replacement. The two vocabulary gates that are about `spec`'s own class list (`TestPipelineClassCoverage`, `TestKindAndClassVocabulariesAreDisjoint`) stay.

### The trap this leg had to close, and where its proof lives

`charly`'s corpus sweep selects entity bodies with `spec.KindValueDefs[pn.Disc]`. Deleting `#PipelineValue` from this module would have dropped every pipeline body out of that sweep **silently** — the witness would have shrunk without a single failing test. The selection is now taught to resolve the def through the SAME route the production gate uses (the provider's declared `InputDef` from the composed unit, falling back to `spec.KindValueDefs`), and the provider is connected the way the loader connects a referenced plugin kind. That teaching is a `charly` change and cannot ride a `spec` PR (producer-first, one repo per PR); it is the consumer half of this leg, filed as **opencharly/charly#1125** and opening as a `charly` PR the moment this merges (it must pin this PR's tag, which does not exist until then). **No `charly` tree loses a body while this PR waits:** `charly@main` pins the pre-deletion `spec`, so its sweep still selects by `spec.KindValueDefs`; the pin bump and the selection change land together in that PR. The coordination is posted as HOLDING on this thread and WAITING on charly#1125.
