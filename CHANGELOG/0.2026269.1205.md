# 0.2026269.1205 — feat(vm): add the container_disk source arm (pull a bootable disk from OCI)

## Summary

Adds a **7th `#VmSource` arm, `container_disk`**, so charly can pull a bootable guest disk
out of an **OCI artifact** and boot it through the UNCHANGED libvirt/qemu path.

The motivating corpus is a **Cua Fleet image** — a KubeVirt **containerDisk**: an OCI image
whose layer holds the disk, by default at `/disk/disk.img` (the directory KubeVirt scans).
This arm is what lets charly consume (and, with the companion emitter work, produce) such
images locally, with no KubeVirt required.

Fields:
- **`image`** (required) — the OCI artifact ref; pin a digest for immutability.
- **`disk_path_in_image`** — the in-image disk path (default `/disk/disk.img`), the
  charly-side equivalent of KubeVirt's custom VMI `path:`.
- **`cache`**, **`distro`** — the same shape the `cloud_image` arm already carries.

`#VmBoxSource.kind` gains `container_disk` (plus a `#VmBoxSource.image` field) so a VM box
emitted from a pulled disk records its provenance — the emitter's completeness gate would
otherwise reject it.

**SDD:** the arm is cross-branch-closed — all **18** cross-branch fields
(`url`/`checksum`/`box`/`transport`/`rootfs`/`root_size`/`kernel_args`/`from_vm`/
`from_snapshot`/`libvirt_name`/`disk_path`/`disk_format`/`builder`/`builder_image`/
`installer`/`base_user`/`bootstrap_arch`/`bootstrap_variant`) are `_|_`, and **the reject
test enumerates all 18**. `distro` stays CUE-optional like `cloud_image` (presence is the vm
kind's `OpValidate` business) while a misspelled id remains a closed-`#DistroID` conflict.

### Review-round fixes (this head)

1. **R5 — the two enumerating comments now agree.** `#VmBoxSource`'s comment previously
   claimed the kind space "mirrors `#VmSource`'s arms" while omitting `imported`. Resolved by
   stating what the record actually is — the arms a VM **box** can be built from — and why
   `imported` is deliberately absent (it tracks an externally-managed disk for lifecycle only;
   `charly vm build` is a no-op, so it can never emit the artifact this record describes).
   Regenerated `spec/cue_types_gen.go` carries the corrected comment.
2. **B13/B12 — the cross-branch closure is now fully enumerated.** The arm closes **18**
   fields; the reject test now enumerates all 18, adding `bootstrap_arch` /
   `bootstrap_variant` (the bootstrap arm's build-variant fields) alongside the previously
   added `kernel_args` / `installer`. *Fact-check:* the arm is CLOSED, so `bootstrap_arch`/
   `bootstrap_variant` were already **behaviourally rejected** before this change (verified
   directly: a `container_disk` source carrying either fails validation) — the explicit
   `_|_` markers give the same per-field diagnostic style as the other 16, and the two new
   test cases assert the rejection explicitly.
