# 0.2026276.0 — feat(spec): the kind:pipeline lobster-syntax value, the #Workflow IR, and the workflow engine op envelopes

## Summary

The workflow surface becomes CUE-first and single-source, in three additive pieces:

- **`schema/pipeline.cue`** — the AUTHORED `kind: pipeline` body, in **lobster syntax** and extended with charly's OWN step grammar, so a workflow can use **any charly plugin of any provider class** through the normal core→plugin dispatch. No word is special-cased: a plugin released tomorrow is usable with no change here.
- **`schema/workflow.cue`** — the normalized, engine-agnostic **IR** every consumer lowers from, plus the engine op envelopes. Lobster is one consumer; a GitHub Actions consumer fits the same IR unchanged.
- **`schema/candy.cue`** — `#ProviderClassNames` gains `"workflow"` (additive; the derived capability regex recomputes, so nothing is hand-edited).

**Closure is the point of the authoring def.** `cue exp gengotypes` renders every field as a plain Go `string`, so a decode-only test cannot tell a closed body from an open one. `spec/pipeline_test.go` therefore unifies CONCRETE values into `#PipelineValue` against the **same `schemaconcat` concatenation the runtime gate uses**, and fails if a retired key (`stages:`, `command:`, `skip_when:`, `concurrency:`) is re-accepted or an unknown key is tolerated.

**The exec-arm XOR is deliberately a Go rule, not CUE.** Exactly one of `run`/`pipeline`/`workflow`/`parallel`/`for_each`/`input`/`plan`/`charly` is enforced in plugin-pipeline's `OpValidate`: a nested entity-level disjunction breaks the closedness of the surrounding def and collapses the generated Go type — the same shape, and the same reason, as the `box.cue` `base`/`from` precedent. The corpus asserts that boundary **explicitly** (both zero arms and two arms are ACCEPTED by CUE) so the CUE/Go split is pinned rather than assumed.

**The flow block is declared once and embedded — never re-stated.** `#PipelineFlow` (`id`/`when`/`env`/`cwd`/`stdin`/`timeout_ms`/`on_error`/`retry`) is embedded by all three step defs — `#PipelineStepBase`, `#WorkflowStep` and `#PipelineSubStep` — and by nothing else. The substep previously re-declared its eight keys verbatim, while that def's own comment already claimed it was "Embedded by each step def"; gengotypes FLATTENS the embed exactly as it already does for `#PipelineStepBase`, so the substep's Go fields are unchanged (only their order in the generated struct moves). An earlier revision of this branch also had the `#PipelineArms` comment claim that the flow keys distinguish the authored step from the IR step: both embed the flow block, so they do not. The two fields that actually differ are `approval` (the authored terse union vs the IR's normalized object) and `result`, which is IR-only. §3(b2) is the de-duplication proof; §3(a) re-runs the corpus over the flattened shape.

**A KIND is a word a plugin SERVES; a CLASS is a face it is DISPATCHED through — and the two vocabularies must stay disjoint.**
`schema/pipeline.cue` defines `#PipelineValue`, which makes `schemagen` register `KindValueDefs["pipeline"]`: the host can now closedness-gate a `kind: pipeline` body with zero per-kind code, exactly the `#TaskValue` precedent — and `pipeline` really IS a kind (plugin-pipeline serves it). The IR gets **no** `#WorkflowValue`, deliberately, and the file says so in a NOTE: every `#<X>Value` def is the value gate for an authorable ENTITY KIND, so a `#WorkflowValue` would register `workflow` as a kind that **nothing serves** — the kinds are plugin-served (`#Node` is an open struct and the arm-derived `KindWords` is empty), while plugin-lobster serves the `workflow` PROVIDER CLASS. That is not a hypothetical: an earlier revision of this very branch shipped exactly that def. It is now pinned structurally, not by a comment — see the FAIL-then-PASS gate in §3(c).

**The engine dispatch is `InvokeProvider("workflow", <engine>, <op>)`.** An earlier revision of this branch's comments claimed the engine was reached as `command:<engine>` with "no new provider class" — false against this PR's own diff, which adds the `workflow` class and the four prefixed op selectors. `command:lobster` is a SEPARATE, additional face of the same engine plugin (its CLI), never the dispatch that runs a workflow. Corrected in `schema/workflow.cue`, in `#Pipeline.engine`, and in the `#PipelineClassRoutes` `"workflow"` row.

**`#PipelineClassRoutes` makes "which route reaches this provider class" a DATA fact.** `schemagen` DERIVES `spec.PipelineClassRoutes` from the CUE table (a new `strMapDef` extractor beside `listValues`), and `TestPipelineClassCoverage` fails when a class has no route — so adding a provider class forces the workflow route to be **decided** rather than silently getting none.

**The engine op selectors are PREFIXED** (`workflow-run`/`-resume`/`-schedule`/`-emit`): a bare `emit` collides with `OpEmit` (deploy/step) and `run` with `OpRun`, and `ops.go`'s stated invariant is that no two selectors share a value even across classes.

`resultWire` gains an optional `captured_value` (raw JSON) with `ResultJSONCaptured` / `ParseResultJSONFull`, so a check verb can hand a consumer a structured value to address by dotted path. It is **omitted when unset**, which keeps the wire byte-identical for every existing producer; a test asserts those bytes.

**No schema version.** `charly#754` retired the CalVer stamp and the load-time gate; this change deliberately does not reintroduce either.

### 6. Honest limits of §5 — what this bed does and does not prove

`check-task` is `host: local` with `disposable: true` and no candy: it loads charly's own project through the host gate and walks a real task plan. That is the assembled-toolchain regression witness. So a host-gate probe of the pipeline kind is impossible in charly's own project today. The bed that DOES exercise it is B1 in plugin-pipeline, which is why the plan assigns spec the *assembled* bed — and why that bed is a W6 artifact that runs against this tag once `plugin-lobster` and the cutover exist. What §5 proves is **regression-freedom of the assembled toolchain under this change**, which is exactly what an additive `spec` PR can prove today.
