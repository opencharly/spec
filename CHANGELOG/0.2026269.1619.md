# 0.2026269.1619 — refactor(container): decompose ParseLocalImagesJSON to clear the gocyclo gate

## Summary

Decompose `container.ParseLocalImagesJSON` (spec/container/local_image_coneb.go) so the repo's
`golangci-lint run ./...` gate passes again. The function reached **cyclomatic complexity 31**
(the repo's `gocyclo` threshold is `> 30`), so `main` itself is RED and every spec PR is blocked
at the required `go` check.

**The defect this closes:** spec#169 (the docker NDJSON images-parse fix) folded three engine
output shapes (podman `Names`, docker-inspect `RepoTags`, `docker images --format json`
`Repository`+`Tag`+`Digest`) and three per-row merge steps (names, labels, size/created scalars)
into ONE ~100-line loop body. That pushed `ParseLocalImagesJSON` to complexity 31 — one over the
gate — and the `go` job has failed on `main` ever since:

```
container/local_image_coneb.go:243:1: cyclomatic complexity 31 of func `ParseLocalImagesJSON` is high (> 30) (gocyclo)
```

The fix is a pure decomposition, not a `//nolint`: the loop body is extracted into four named
helpers with single responsibilities, restoring the function to a short "key each row, create or
reuse the entry, merge refs/labels/scalars" loop:

- `imageRowID` — a row's ID across both engine spellings (`Id`/`ID`);
- `imageRowKey` — the dedup key (ID, or the per-row sentinel for an empty/dangling id);
- `imageRowRefs` — the refs across all three engine shapes (names / repoTags / repo+tag+digest);
- `stringArrayField` — the JSON array→[]string element extraction with non-string skipping;
- `mergeImageNames` / `mergeImageLabels` / `mergeImageScalars` — the per-id dedup/merge steps.

Behaviour is UNCHANGED (byte-for-byte same outputs): the existing `TestParseLocalImagesJSON_*`
suite covers every engine shape and passes untouched.
