# 0.2026242.1042 — fix(container): bound and report the local image enumeration

## Summary

Addresses opencharly/charly#475 — **and corrects that issue's root cause, which I wrote and which the measurements below disprove.**

`podman images --format json` walks the whole local store, so its cost scales with the store rather than with what the caller wants. Unbounded, a degraded store is indistinguishable from a hang: no log line, an empty run directory, and only a `podman images` child process as evidence. That is what was reported — a `check-image` step sitting 25+ minutes with nothing naming the cause.

This bounds the call (killing the process group on expiry) and makes the cost legible:

```
listing local images via podman: timed out after 4m0s — the local image store is large
or contended; prune it (charly clean) or retry when builds are idle
```

and, when a completed listing was slow:

```
charly: listed 1170 local images in 9.003s — consider pruning the image store
```

**What this does not do.** It does not make a large store fast. The enumeration is inherently O(store), and the 5-minute cache above it is what keeps consecutive runs cheap. What it fixes is a slow store presenting as a *silent stall*.

## The issue's stated root cause is wrong — measured

charly#475 says the store was *"10,865 images, of which 10,607 were untagged (97.6%)"* and frames the fix as avoiding an unfiltered enumeration. I set out to add `--filter dangling=false` and measured first. Both halves of that plan collapse:

```
$ podman images --all --format '{{.Id}}' | wc -l        ->  12585
$ podman images --filter dangling=true --format '{{.Id}}' | wc -l  ->    402     (3.2%, not 97.6%)

$ time podman images --format json                      ->  9003 ms, 17408384 bytes
$ time podman images --filter dangling=false --format json  -> 13569 ms, 15776571 bytes
```

Filtering dangling images is **50% slower**, because the filter costs more than the 402 rows it removes. The 97.6%-untagged figure does not describe this store.

Where the cost actually is — 1,170 image IDs carrying 12,585 tag names across 177 repositories:

```
   1141  ghcr.io/opencharly/arch
    611  ghcr.io/opencharly/arch-builder
    464  ghcr.io/opencharly/cachyos
    423  ghcr.io/opencharly/fedora-nonfree
    414  ghcr.io/opencharly/fedora
```

I also checked whether retention was blind to them — a plausible cause, since `charlyImageTags` skips images without `ai.opencharly.box`:

```
image IDs with ai.opencharly.box label: 876
image IDs WITHOUT it:                   294
tag names on labelled images:          5565
tag names on UNLABELLED images:          17   <- so retention is NOT blind to them
```

So the store is not full of junk retention cannot see; it is full of accumulated CalVer tags retention simply has not pruned. That is an operational matter, not an enumeration bug — which is why this PR fixes the *legibility* of the slow path and does not pretend to make it fast.

## How tested

New regression guard — a fake engine that never answers, the shape of a saturated store:

```
$ go test ./container/ -run TestDefaultListLocalImages_FailsFastOnHungEngine -v
--- PASS: TestDefaultListLocalImages_FailsFastOnHungEngine (0.20s)
ok  	github.com/opencharly/spec/container	0.203s
```

It asserts more than "it returned": the error has to contain `timed out` **and** `prune`, so the message keeps telling the operator what to do.

**Negative control** — bound removed, `exec.Command` restored:

