### 1. `/charly-image:layer` — a new section: "Supply-chain-pinned downloads (`download:` has NO digest)"

The skill already documented `download:`'s **content-addressed cache**, which is real and is **not**
integrity: the cache is keyed by the URL, so it makes a re-fetch cheap and a flaky CDN harmless, and it
never tells you that what arrived is what you pinned. The verb carries **no checksum field at all**
(`extract`, `to`, `extract_include`, `strip_components`, `mode`, `env`, `cache`) and the renderer emits
`curl -fL --retry 3 -o …`. Two different properties; only the second is supply chain.

The section is placed **after** the `Caching downloads` section and its Android worked example, so that
example stays attached to the `cache:` mount sentence it illustrates — the diff against `main` is a pure
insertion, nothing else in the file moves. It carries the four steps of the shape the org already uses
(`layer-k3s`, `layer-kind`, `layer-nerdctl`, `layer-vscode`, the Strata layer): one `run:` step fetching
into a `cache:` mount; `sha256sum -c` against a digest **pinned in the candy's `var:` block** (auditable in
the diff, not a re-fetched `SHA256SUMS.txt`); unpack in the SAME layer so the archive never becomes a
resident lower layer; and a declarative `check:` beside it asserting the **installed** artifact. Forward
reference: the field itself is `opencharly/spec#397`, and when it lands this section is why it exists.

### 2. `/charly-pod:pod` — one paragraph, a POINTER to the CDI × user-namespace rule

A different rule from the layer note's. The schema reference is where an author reads a pod's shape before
deploying it, so it now says: a pod that injects a CDI device **cannot** run `--userns=keep-id` (the
injection fails with `mount_setattr … EPERM`); the workload runs as **container root under `userns=host`**,
which in a rootless pod IS the invoking host user, and it needs no capability at all;
`plugin-deploy-pod` derives that from the resolved deploy, so a pod does not declare it. The mechanism, the
measured matrix and the two legal shapes stay in `/charly-cdi:cdi`; the deploy-time consequences (the
posture is captured at `deploy add`, so an entity edit does not move a running unit; `cap_drop` is not yet
expressible, `spec#398`) in `/charly-core:deploy`. One statement of why the pointer lives here; no second
home for the reasoning (R2).

**Findings from #400's rounds, all folded in:** the mechanism is not restated in `pod` (it is a pointer);
the digest paragraphs are their own section, not spliced between the `cache:` sentence and its worked
example; the two rules are named as two; and the numbers in this body come from a command, not from a
recollection.
