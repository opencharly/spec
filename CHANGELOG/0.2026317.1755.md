# 0.2026317.1755 — feat(wire): the connect seam returns the connected plugin set it resolved (#1131)

## Summary

The connect seam already knows which built plugin binary serves which plugin — `loadPluginUnit` resolves it, and every run prints it (`plugin <ref>: served from <path> (build <sha256>); source <srcDir>`) — and then throws that mapping away: `#DeployPluginsConnectReply` carried the project dir and nothing else. A `step:` that has only a plugin NAME therefore had to re-derive "which binary is this plugin" by scanning a directory and taking the newest match. That is the defect `opencharly/charly#1131` exists to delete, and its smallest viable surface was argued on that issue by the lane that filed it: carry what the connect already has.

This PR is the contract half of that surface, and nothing else:

- `#DeployConnectedPlugin` (new) — one connected plugin: `key`, `leaf`, `view_path`, `src_dir` (absent for a source-less baked plugin).
- `#DeployPluginsConnectReply.plugins` — the CONNECTED SET, in load order; absent when the deploy referenced no out-of-tree plugin.
- `StepContract.plugin_paths` — the step's OPT-IN: the host hands this step the connected set, as PATHS, in its input under `spec.ConnectedPluginsInputKey` (`"plugin_paths"`). Opt-in because a step's input is validated against the plugin's own usually-closed schema, where an injected key is a hard `field not allowed` unless that schema declares it.

The wire types are CUE-first: `schema/seam.cue` and `protocol/schema/plugin.cue` are the authored source, and `spec/cue_types_gen.go`, `proto/plugin.proto` and `proto/plugin.pb.go` are regenerated, not hand-edited. `spec/provider_carriers.go` (a hand-written carrier, not a schema shape) gains the flag and the ONE shared input-key constant; `exec/executor.go` carries it through the pb→spec conversion.
