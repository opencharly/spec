### Schema surface

- **`#Kindcluster`**:
  - `engine?: #EngineName` — the container engine kind provisions node containers
    with. It maps **1:1 to kind's `KIND_EXPERIMENTAL_PROVIDER`**
    (`podman`/`docker`/`nerdctl`), so engine selection rides the authored
    `#EngineName` vocabulary with no separate selector. This is what makes the
    docker/podman/nerdctl integration free.
  - `node_image?: string` — the digest-pinned `kindest/node:vX@sha256:…`.
  - `nodes?: [...#KindclusterNode]` — topology (`role`, per-node `image`,
    `extra_port_mappings`).
  - `kubeconfig_context`, `default_namespace`, `admission_policy`, and the SAME
    cluster-policy sub-blocks the `kubernetes:` template uses
    (`storage`/`ingress`/`image_default`/`pod_default`/`defaults`) — R3, one
    policy surface for both cluster kinds.
- `#KindclusterValue: (#Kindcluster | #DeployValue)` — the host-side value gate
  for template OR deploy shape.

### RDD (why this shape)

All high-risk unknowns were proven live on this host before the schema was
written: kind works on `docker` (Ready in 16 s), rootless `podman` (13 s), and
rootless `nerdctl` (16 s, after `containerd-rootless-setuptool.sh install`); the
engine word is exactly `KIND_EXPERIMENTAL_PROVIDER`; `kube: addons` is k3s-only
(kind ships kindnet, no Traefik/ServiceLB). Full evidence in the umbrella
`plan/kind-integration.md`.
