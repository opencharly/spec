# 0.2026313.1428 — feat(schemaparams): generate params in-process over the offline compose

## Summary

`spec/schemaparams` no longer shells out to `cue exp gengotypes`. The schema directory is concatenated as before, then composed as ONE CUE module instance through `schemacompose` — the same offline `load.Config` + registry the serve side and the host gate already use — and the Go params are generated in-process from the CUE Go API. Generation and composition now share one resolution path, and the `cue` CLI leaves the generation leg entirely.

Both measured failures in opencharly/spec#298 are closed:

- **F1 — nothing resolved the import.** `schemacompose` gained an exported `ComposeText` that returns the loaded module instance, so the projection composes through the ONE offline registry instead of writing a scratch module and shelling out. A plugin schema carrying `import "github.com/opencharly/spec/schema"` now loads against the contract module the Go binary already links: no published CUE module, no module cache, no `cue` binary.
- **F2 — the emitted Go named a package that does not export the type.** A referenced CUE package is now emitted through the Go package that owns its shapes: `github.com/opencharly/spec/schema` maps to `github.com/opencharly/spec/spec` (`schemaparams/gohome.go`). An import with no registered Go home is a loud error, never a reference to a path that may not compile.

The generator (`schemaparams/gotypes.go`) is a faithful in-process port of `cue exp gengotypes` v0.16.1 — that package is INTERNAL to `cuelang.org/go`, which is why the CLI was shelled out to — so a schema without an import generates byte-identically; both directions are proved below. The one thing not delegated to the local formatter is doc-comment canonicalization: Go 1.27's `go/printer` stopped rewriting a struct field's doc comment, so leaving it to the toolchain would make the same schema regenerate differently on a 1.27 developer box and in the 1.26 CI. The transform now uses the public `go/doc/comment` parser, and generation is byte-identical under both Go 1.26.8 and Go 1.27.3.

The committed `spec/cue_types_gen.go` is unchanged: a clean regeneration is a no-op, and `TestGenReproducible` now compares bytes on every run (it no longer skips when the CLI is absent). The next leg of opencharly/opencharly#950 is the consumer call site in opencharly/plugin-candy (see Change classification); the census is opencharly/opencharly#945.

### Update after the first CI run: the compile arm's module graph

The first CI run failed the `go` job in `TestGenerateImportCompiles` (verdict PASS on the code; this was a test-harness defect). RCA: the temp module was declared with a minimal `require spec` and built with `-mod=mod`, so `go build` tried to EXPAND the module graph and asked the proxy for `gopkg.in/check.v1`'s go.mod, which CI's cache did not hold; `GOPROXY=off` refused the lookup. It passed locally only because this host's cache happened to hold that go.mod. The missed control was the arm's own declaration: a consumer module has a COMPLETE requirement set, not a minimal one. The arm now mirrors this module's declaration (same go directive and requirement set, module path rewritten, contract module added as a local replace) and builds in the default readonly mode, so no expansion is attempted. Reproduced with a cold cache minus `check.v1`:

## Change classification

- **Consumer-visible API change.** `schemaparams.Generate(schemaDir, pkg, cueDir)` becomes `Generate(schemaDir, pkg)`, `GenerateExcluding` loses its `cueDir` argument, and the `GenerateWithCue` pair is deleted. The one call site is `candy/plugin-candy/params.go` in opencharly/plugin-candy, whose `paramsPipeline(schemaDir, pkg, cueDir)` call and CLI-provisioning help text change with its pin bump — the next leg of the producer-first sequence in opencharly/opencharly#950. Nothing in this repo consumes the removed surface.
- **No authored wire key changes.** `spec/cue_types_gen.go` and `spec/vocab_gen.go` are byte-identical to the committed files; a schema without an import generates exactly what it generated before.
- **Generated output for an importing schema changes by design.** The file now imports `github.com/opencharly/spec/spec` and references its types, instead of importing the CUE package path whose Go package exports only `FS`.
- **The generated-file banner is deliberately unchanged.** Byte-identity for the no-import case is the no-regression criterion, and changing the banner would rewrite every committed params file across the org for no semantic gain; the generator is a faithful port of the mapping the banner names, and `schema/README.md` states that reading.
- **The `cue` CLI is off the generation leg, not out of the repo.** `bootstrap-cue` stays as the pinned tool for authoring the schema as a module (`cue eval ./schema`); `cue-gen` no longer depends on it.
- **Going back:** re-pin the previous released contract module, which still contains the CLI pipeline in `schemaparams`.
