## Summary

P1 of the OCI plugin-distribution capability (opencharly/charly#891): the **spec-side contract**
for pulling a precompiled charly plugin from a registry. Producer-first — `plugin-oci` (P2), `sdk`
(P3) and `charly` core (P4) build against this. Every path is `.cue`, `.go` or its own regenerated
Go, so this is a code/config change, not docs-only.

**Round 1 (this head) folds in SPIKE F's four measurements and SPIKE B's runtime-tool requirement** —
contract refinements inside the same cutover — plus the two round-1 validator findings (both
body-truthfulness).

**1. The candy ref grammar is CLOSED.** `#CandyRef` was `^(@.+|[a-z0-9]+(-[a-z0-9]+)*)$`. The `@.+`
arm accepted *any* scheme, so `@oci://host/repo` validated and then reached the **git-only**
`ParseRemoteRef`, which split on the last `:` and returned `oci` as the repo path — a nonsense git
URL, far from the line that made the mistake. It now has exactly three arms: a bare
lowercase-hyphenated name, `@github.com/…`, or `@oci://…`. Because the arms live in ONE def, all 12
`#CandyRef`-typed authored fields across 8 schema files inherit the closure with no second edit, and
`add_candy:` — which carried **no pattern at all** (`string & !=""`) — is now typed `#CandyRef`.

**2. A registry source is representable.** `plugin.source:` and `#PluginRequirement.source?` became
`#PluginSource` = `#GithubRef | #OciRef`, with
`#OciRef =~ "oci://<registry>[:<port>]/<repository>[:<tag>][@sha256:<digest>]"`. A digest, when
present, is authoritative: it is what the consumer verifies and what keys the content-addressed
store (D-STORE-3/4). The two source fields share ONE def, so a peer plugin is reachable by either
route with no second declaration surface.

**3. The program-side discriminator.** `ParseRefKind` (bare / git / oci, both the `@`-prefixed
ref-site and the `@`-less source spelling) and `ParseOciRef` (registry / repository / tag / digest)
classify a ref handed over as a *string* — a CLI argument, a resolved envelope — where a CUE pattern
cannot produce a message; an unsupported scheme is refused by naming the supported arms.
`ParseRemoteRef`'s doc now states its git-only contract and points at the classifier, because its
contract is what let the old arm produce a plausible-looking wrong answer.

**4. The artifact contract.** `#PluginArtifactTransferRequest/Reply` — the `verb:oci`
plugin-push/plugin-pull pair, ref-agnostic so any distribution-spec registry works (including one
charly itself may serve), with a `platform` selection that reports the platforms that *were*
available instead of falling through. `#PluginArtifactMetadata` — the config blob, i.e. the
D-STORE-4 key spelled out (module, revision, go.sum, toolchain, platform) plus the facts a consumer
must check that image-spec cannot express (Round 1 below). `spec/plugin_artifact_consts.go` is the
ONE home for the media types and annotation keys the producer and every consumer must agree on by
name — including the decision that `org.opencontainers.image.created` is **omitted**: a wall-clock
annotation gives identical inputs a different digest, breaking D-STORE-3/4 addressing and D-STORE-6's
"a stored fact must be an input". A test pins that decision so it is not "fixed" back.

**5. The orphaned containerDisk pair is DELETED here.** `#ContainerDiskEmitRequest` /
`#ContainerDiskEmitReply` had no consumer anywhere on `main` (only their own defs, the generated Go and
the changelog that introduced them — the shipped engine is `sdk/deploykit/vm_box_emit.go`, driven from
`plugin-vm`, with `plugin-oci#5` closed unmerged and no `charly vm box publish` command), while this PR
edits their file and would otherwise have declared them dead in a comment. Round 1 filed the removal;
**CONC(a) was right that proven-dead code inside a touched module is blocking**, so round 2 deletes the
pair and its regenerated types, and `spec#231` is closed as resolved by this PR (`Closes #231`).

### Round 1 — SPIKE F's measurements, folded in

- **`platform.libc` is first-class, and `platform` is now a nested block.** image-index v1.1.1's
  Platform Variants table maps `variant` to GOARM/GOARM64/GOPPC64/GORISCV64/GOAMD64 **only** — it
  cannot express libc. Measured: two `linux/amd64` descriptors with **byte-identical** platform
  objects and different libc, under the spec's "first matching entry SHOULD be used", make the second
  **unreachable**. So libc is a charly field (closed set `glibc | musl`) beside the platform facts it
  qualifies, never a `variant` value, and the consumer verifies it hard.
- **`schema_digest` → `served_schema_digest`.** Measured off the wire from a real binary over the
  same handshake `LocalTransport` uses: the file-set digest (`sha256:683a1d9b…`) and the
  served/Describe digest (`sha256:02cb24f7…`) **differ**. The field now declares the SERVED
  (concatenated) body `registerPluginUnitSchema` actually splices — the file-set value is
  unrecomputable where only the binary exists (a deployed container has no `schema/` dir). One rule
  now covers every declared identity fact, stated in the header: **it must be recomputable by the
  consumer from the artifact or the running binary** (an earlier spike candidate reproduced from
  nothing — never declare a digest that cannot be recomputed).
- **`#Plugin` gains `release:` and `digest:`.** Measured today: no identity check at all, so a
  different build is served silently, and a wrong-architecture binary is announced as "served from
  baked binary …" before dying at `exec format error`. `digest:` carries the **index** digest — the
  only platform-independent one (a multi-platform artifact has one manifest per platform, so the
  per-platform digest is derived by selection) — and where a declaration's `digest:` and an
  `#OciRef`'s own `@sha256:` disagree, that is a hard load error: one pin, two spellings, never two
  competing answers.
- **`#PluginArtifactMetadata` gains a REQUIRED `runtime_requires`.** SPIKE B measured a provider
  whose report silently degraded — `exec.Command("zcat", "/proc/config.gz")`, with two kernel
  features printed as `N/A` when `zcat` was absent and `y` when present — and nothing in the
  artifact could say what was missing. The set is projected from the plugin candy's own
  `package:` / `distro:` declaration (the one declaration TODO 6.9 names; this is not a second
  declaration surface, it is the same fact travelling with the artifact), it is REQUIRED, and an
  EMPTY list is a CLAIM ("this provider shells out to nothing") rather than a placeholder — so a
  consumer reports a missing listed tool and never reads an absent list as "needs nothing".
- **Requiredness is now enforced where the prose already claimed it.** `providers!` and `source!` on
  `#Plugin` (all **123** plugin blocks in the authored corpus carry both, so zero blast radius), and
  the identity fields of `#PluginArtifactMetadata` are `!` — a config blob missing an identity fact
  is rejected instead of silently accepted.

### Round 2 — the DESIGN-first reshape, and the two round-1 blocks

- **The compat facts became OPTIONAL DIAGNOSTICS.** DESIGN §8: *"There is no version negotiation.
  Compatibility is the validation of every message (D-PROTO-6)"* — so `protocol` and `calver` are
  advisory facts a consumer MAY report for provenance and never a gate (a `9999.999.9999` binary was
  measured running fine), while what decides placement stays required: `module`/`release`/`digest`
  (D-CORE-4/D-PLUG-4), `platform.libc` and `runtime_requires`.
- **`served_schema_digest` is labelled TRANSITIONAL** in its own doc comment: DESIGN §8.1 publishes a
  plugin release's CUE module as DATA addressed by digest and §4 has core read schemas without starting
  the plugin; until that leg lands, the served body is the only schema identity a consumer can verify.
- **`runtime_requires` records its PUBLISHER rule**: the set is projected from the plugin candy's own
  `package:`/`distro:` declaration and the publisher HARD-ERRORS when the candy declares no package set
  at all — an explicit `package: []` is the only way to claim "no runtime tools", so a missing
  declaration can never quietly become an empty list.
- **The mechanism moves OUT of `spec` and into `sdk`** (D-SDK-1: *"the store and its roots"*; D-SPEC-1:
  `spec` holds generated code and behaviour methods, no mechanism). That is why this PR contains no
  reader/verifier/materializer package: the shared mechanism lands in `sdk`, `plugin-oci` imports it
  directly, and core reaches it through the `verb:oci` dispatch it already uses. The resolution ladder
  this PR's P4 will touch is INTERIM SCAFFOLDING; D-PLUG-4/D-CORE-4's declaration-driven resolution —
  exact match of module/release/digest, prebuilt-by-default, source builds only for `path:` — is the
  target, and the `filepath.Base(plugin.source)` keying fix is design-aligned because it keys by the
  DECLARED module rather than by a directory leaf.
- **`spec/cache`'s store deviation is FILED, not parked: `opencharly/spec#233`** (its root resolves
  `~/.config/charly/cache` against D-STORE-1, and a hand-written mechanism lives in the contract module
  against D-SDK-1/D-SPEC-1). It is not cured here because the migration has ~6 consumers and needs its
  own bed; the sdk roots mechanism created by this cutover is what both stores will resolve through, with
  `spec/cache.StoreRoot()` as the interim shim that resolves the SAME rule — the shim is that issue's
  exit, not a resting place.
