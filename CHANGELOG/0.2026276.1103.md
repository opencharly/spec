# 0.2026276.1103 — feat(spec): the del seam carries the target ancestor chain (the venue) — charly#765

## Summary

`charly deploy del <root>.<member>` loses the nested member's **venue**. The `del` dispatch ships the node but *no ancestor context*, so the host cannot rebuild the `parentExec` chain the `add` half used, and the teardown falls back to `specexec.RootExecutorForDeployNode(node)` — **the operator's HOST** for an in-substrate member carrying no `host:` field. The member's reversible ops then replay against the workstation while its `add` landed correctly in the guest. This is the third variant of the `#627`/`#680` mechanism; it is filed as **opencharly/charly#765**.

This PR is the **first leg of the three-repo producer chain that fixes it** (spec → plugin-fleet → charly). It is the whole spec-side change, and it is deliberately additive: two optional fields on one host↔plugin seam.

| file | |
|---|---|
| `schema/seam.cue` | `#DeployNodeDelDispatchRequest` gains `ancestor_paths` + `ancestor_nodes` (both optional), with the doc comment naming #765 |
| `spec/cue_types_gen.go` | regenerated by `charly task cue-gen` (`TestGenReproducible` is the gate) |
| `spec/seam_roundtrip_test.go` | NEW `TestDeployNodeDelDispatchAncestorsRoundTrip` — the R10 gate for the field |

**Why the wire and not the executor.** `spec.ReconstructParentExec(ancestorPaths, ancestorNodes, derive)` already exists and is exactly what the `add` half uses (`charly/host_build_resolve_target_add.go`, fed by `plugin-fleet/candy/plugin-fleet/walk.go`). The `del` seam simply had no way to carry the two lists. The alternative — shipping a live `DeployExecutor` — is impossible by construction: an executor is process state, and the teardown is a **fresh forked process** (`plugin-check/candy/plugin-check/bed_run.go` runs `step("cleanup-"+childKey, "deploy", "del", …)`), so nothing in-process can carry it. DATA crosses the wire; the host re-derives the executor exactly as it does for `add`.

**The lists are ROOT-FIRST and EXCLUDE the target.** `ReconstructParentExec` pairs paths and nodes by index and walks root-first; including the target would derive the target's own executor — one hop too deep. Both are empty for a top-level or synthetic target (`host`, a bare name, a `vm:` address with no tree entry, a ref-based pod artifact), which is a *requirement*, not a fallback: the host then leaves `RootExecutorForDeployNode` in place and behaves exactly as before.

**No schema version.** These are two optional fields on a HOST↔PLUGIN seam — not an authored-YAML wire-key change, so no `#SchemaVersion` bump is owed (and `charly#754` retired the stamp anyway). An old host decoding the new request ignores the unknown keys; an old plugin simply never populates them.

**What the consumers do with it (the rest of the chain, each its own PR).**
- **plugin-fleet** populates the two lists on the del dispatch from one shared dotted-path walk (`walkDeployNodePath` — one resolution, two consumers, R3) and bumps this spec.
- **charly** reconstructs the chain in `hostBuildDeployNodeDelDispatch` (`spec.ReconstructParentExec` → `DescriptorFromExecutor`) and hands it to `Del` as the venue, then bumps both pins. Its `Add` half already does the equivalent via `EmitOpts.ParentExec`.
