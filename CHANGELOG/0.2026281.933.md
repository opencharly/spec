# 0.2026281.933 — feat(schemaparams): THE schema→Go params pipeline, as one public entry point

## Summary

**Producer leg of `charly#829`**, reshaped by the review into something stronger: ONE public pipeline (`spec/schemaparams`) that **spec's own generator now calls too**, with both of spec's earlier copies deleted — so this commit ends with **one** pipeline inside `spec` rather than a new copy beside an old one.

`schemaparams` sequences the three existing contracts — `schemaconcat` (concatenate the schema directory), `cuetoolchain` (the pin *and* its checksum-verified fetcher), `schemaretag` (the tag normalization) — under the `package <pkg>` + `@go(<pkg>)` header, and runs the pinned `cue exp gengotypes`. The exported surface is FOUR functions: `Generate`/`GenerateExcluding` (provision the pinned toolchain into a caller-chosen directory, `Excluding` taking a CUE file filter — `internal/schemagen`'s `node.cue` exclusion is a parameter, not a copy) and `GenerateWithCue`/`GenerateWithCueExcluding` (take an already-provisioned binary — the seam a test uses instead of downloading one). **No mutable package-level state**: the toolchain is a parameter.

**The same-repo duplication is gone**, which is the review's second finding and it is right that producer-first does not excuse it:
- `internal/schemagen`'s `-mode=concat` and `-mode=retag` are **deleted**; a single `-mode=params` calls `schemaparams.GenerateExcluding(schema, pkg, "bin", excludeParamGen)`. `writeConcat` and `retagFile` go with them.
- `charly.yml`'s `cue-gen` task loses the concat → gengotypes → retag sequence **and** the `cue.mod`/gendir scaffolding that existed only to feed it: one call.
- `spec/gen_repro_test.go`'s `freshTypesGen` used to re-run those deleted modes itself — a second copy of the mechanism it gates, which could not notice the task's path breaking. It now runs the same `-mode=params` entry point the task runs.

**And the pipeline once again EMITS the codegen module the recipe declared** — `schemaparams.go` writes `cue.mod/module.cue` with `language: version: cuetoolchain.Version` into the scratch instance. That is the most consequential line in this diff and it is not cosmetic: the module file is what gives the CUE instance a module identity and a **language version**, and the first version of this pipeline omitted it. The generated Go came out byte-identical anyway *only because this pin's default language version coincides with the pinned one* — an accidental identity that breaks the day a pin moves the default. Restoring it removes the dependence on that coincidence, and the version now comes from the same pin as the binary that reads it.

**A real bug the task caught, with its regression arm.** The pipeline exec'd the toolchain with the TEMP dir as its working directory, so a **relative** `cueBin` — spec's own task passes `bin` — failed: `fork/exec bin/cue: no such file or directory`. It now resolves the path against the caller's working directory first, and `TestGenerateWithCueAcceptsARelativeToolchainPath` fails without that fix. This is exactly why the in-repo consumer had to move in this commit: the duplicate hidden in the task is what would otherwise have kept working while the new path broke.

**Files — all five of mine, from `git diff --numstat origin/main...HEAD`:** `schemaparams/schemaparams.go` (+121), `schemaparams/schemaparams_test.go` (+218), `internal/schemagen/main.go` (+16/−39), `charly.yml` (+7/−20), `spec/gen_repro_test.go` (+11/−25). Nothing else is in the diff: `main`'s own commits came in with the `update-branch` merge and are already in `origin/main`, so they are not part of this PR's change.

Refs opencharly/charly#829, opencharly/plugin-pipeline#35 — chained producer-first: this tags first; then the charly verb wraps it, **deleting the steps it duplicates** (that deletion is what makes this one pipeline rather than four); then a plugin repo's CI can call it, which is what lets `plugin-pipeline` regenerate through the canonical pipeline ([#35](https://github.com/opencharly/plugin-pipeline/issues/35)).

### The emitted `cue.mod/module.cue` — the one finding that was not a paste, restored

The recipe this pipeline replaced wrote `cue.mod/module.cue` into the instance directory:

```
module: "github.com/opencharly/spec/schema/spec-codegen"
language: version: "v0.16.1"
```

The new pipeline did not, and the review is right that this is a behavioural difference in an **emitted artefact** (R8), not a documentation gap. RCA:

- **what consumes it:** the CUE toolchain, to give the instance a module identity and therefore a **language version**, instead of resolving against an implicit default. Nothing in the org reads the file afterwards — it lives in the temp instance dir — so its only effect is on the compile itself.
- **why the generated Go was byte-identical without it:** on this pinned toolchain the default language version coincides with the pinned one. That is exactly the kind of accidental identity that breaks the day a pin moves the default — so the fix is to stop depending on the coincidence.
- **fix, in this commit:** the pipeline writes the module again, with `codegenModule` as a neutral scratch path (the old shell hardcoded a spec-specific one; this pipeline serves plugin candies too) and `language: version: cuetoolchain.Version` — the SAME pin the binary comes from, so the declaration cannot drift from the toolchain that reads it.
- **proven:** `charly task cue-gen` still passes 2/2 with `spec/cue_types_gen.go` and `spec/vocab_gen.go` **byte-identical**, and the new `TestGenerateWithCueEmitsTheCodegenModule` captures the file the generator is handed and asserts both the module path and the pinned language version. Without that arm the module could silently disappear again while every output assertion still passed.
