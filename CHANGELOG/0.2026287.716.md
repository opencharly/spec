# 0.2026287.716 — feat(schema): the deploy venue carries the kubeconfig file (kubernetes substrate)

## Summary

`#Kubernetes` and `#ResolvedKubernetes` carry a `kubeconfig` FILE (opencharly/spec#221, tagged
`v0.2026287.638`), and `plugin-kubevirt` honours it. The `target: kubernetes` deploy path still
could not: its preresolved payload carried a context only, so `kubectl apply -k` could be pointed
at a context NAME and never at the per-cluster kubeconfig an externally-managed cluster is
addressed by.

`#KubernetesDeployVenue` now carries `kubeconfig?: string` -> the apply's `--kubeconfig`, beside the
existing `kube_context?` -> `--context`. Regenerated with `charly task cue-gen`; a clean regen is a
no-op on the committed tree (pasted below).

**Deliberately NOT the sibling `#KindclusterDeployVenue`:** a kindcluster's context is `kind-<name>`
inside kind's own locally generated kubeconfig, which charly creates in place - there is no
per-cluster file for an operator to point at, so the field would have no meaning there. That is a
scope decision, not a deferred follow-up.

Consumers (producer -> consumer, B6): `opencharly/plugin-kube` (preresolver fills it from the cluster
template; `kubectlContextArgs` adds `--kubeconfig`) and `opencharly/sdk`
(`ResolveClusterContextViaExecutor` returns the context only, which is what the `kube:` verb's
cluster resolution reads).

Closes #223
