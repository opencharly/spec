# 0.2026325.913 — feat(schema)!: a kind's owned content (ops.OpContent, the contents flag, owned_content)

## Summary

The contract half of opencharly/sdk#598: a **kind's owned content** (DESIGN §1.1 M1, Content → IR). A node of a plugin kind can be owned by a candy — a `skill:` names its owner — and what it contributes to an image belongs to the kind that defines it (D-PLUG-1). This adds the one kind-agnostic op and shapes for that, so the build kit asks a kind instead of interpreting its nodes. `kind:skill` (opencharly/plugin-harness-kind) is the first user: the skills a composed candy owns are installed at the image user's `~/.agents/skills/<name>/` and labelled `ai.opencharly.skill`. That replaces the skill carriers' `copy: .agents/skills` step, which could never reach its own repo root (sdk#444) and fails every remote import (`"/.agents/skills": not found`, distro-arch#73).

- **The op:** `ops.OpContent` (`"content"`), dispatched only to a kind whose capability declares **`contents`** (`ProvidedCapability.contents`, protocol CUE field 16; `capability.ProvidedCapability.Contents` for compiled-in plugins; read by the host through the new `spec.ContentKindCarrier`, the `ValidatingKindCarrier` pattern).
- **The shapes** (`schema/owned_content.cue`):
  - `#OwnedContentRequest` — `box` (absent = **project scope**, what `charly box validate` sends), the image user (`home`/`uid`/`gid`, required exactly when a box is named — a CUE conditional), `candies` with their absolute `repo_root`, the scope's `images`, and the kind's raw `nodes`;
  - `#OwnedContentReply` — `files`, JSON-valued `labels`, and `diagnostics`;
  - `#ContentFile` — absolute `source`, a home-relative `path` that is never absolute and never climbs out, and a permission `mode`.
- **The envelope:** `content_kinds` (the declaring kind words, also on `#ValidateWordSetsReply` — the host word-set leg plugins already call) and the build-render cache `owned_content`.
- **The labels:** `BakedLabelSet.skills` is deleted — `#BakedLabelSet` declared it TWICE (CUE unifies a repeated field), and both declarations are gone; the generated struct is asserted to carry no `Skills` (`spec/baked_label_set_test.go`). A kind's labels arrive in the new `BakedLabelSet.contributed` (the reader side, `BoxMetadata.skills` and the `ai.opencharly.skill` key, is unchanged).
- **The config:** `spec.Config` gains the generic `PluginKinds` (every plugin kind's opaque nodes, root and namespace) and loses the skill-only `Skills` copy.
- The spec-skill-shelf's "validate-satisfying no-op" `run:` step is deleted: an owned skill node is install content now.

## Change classification

Contract change: a new op, a capability flag, three request/reply shapes, two envelope fields and a baked-label carrier; two fields removed.

**Breaking change + rollback:** `spec.Config.Skills` and `BakedLabelSet.skills` (Go `BakedLabelSet.Skills`) are removed. Their in-org consumers — sdk's deploykit (the deleted label collector) and plugin-box's validate rules — are rewritten onto `Config.PluginKinds` and `OpContent` in the sibling PRs of this cutover, so nothing in the org reads the removed fields after it lands. The on-image `ai.opencharly.skill` label is unchanged byte-for-byte in shape, now written from `contributed`. Rollback: revert this PR together with its consumers' pin bumps — no data migration, and images built either way carry the same label.
