# 0.2026242.1148 — fix(distro): ResolveInherits dropped four fields on every derived distro

## Summary

`ResolveInherits` is a hand-written struct literal — **twice**, once per branch — and it
forgot four fields: `DiskLayout`, `Installer`, `InheritPackages` and `Raw`.

Any distro declaring `inherits:` arrived at its consumer with all four `nil`, and the
consumer took its default path. **No error, anywhere.**

### What this broke — all of it already merged and green

| Consequence | Shipped in |
|---|---|
| The **btrfs subvolume feature does nothing** for any distro with a parent — which is every derivative, the case it was built for | #72 (`#DiskLayout`/`#Subvolume`), plugin-vm#6, plugin-vm#7, charly#476 |
| `source.kind: iso` cannot resolve an installer for a derived distro — `charly vm build` reports *"declares no installer"* against a distro that plainly declares one | how this was found |
| **`inherit_packages`** — the switch the whole distro **tag chain** rests on — dropped from the resolved value, so a consumer reading it post-resolution sees `false` | the omarchy tag-chain design |
| **`Raw`**, the authored body consumers fall back to for anything this projection does not model, became empty for any distro with a parent — turning "not modelled" into "not present" | every `Raw` consumer |

Found by running a real `charly vm build` against an authored `omarchy-vm`, not by reading.
Every gate in the chain was green throughout.

### Inheritance semantics, stated deliberately

- **`DiskLayout` and `Installer` inherit**, like every other optional sub-block already
  handled a few lines above (`BaseUser`, `Pacstrap`, `Debootstrap`, `AlpineBootstrap`,
  `Bootloader`, `Dnf`). A derivative that adds only an installer — an Arch spin reusing
  archinstall — must not have to restate its parent's whole boot chain. A child's own value
  still wins.
- **`InheritPackages` and `Raw` come from the CHILD**, never the parent. `inherit_packages`
  says *"expand MY tag chain through my parent"*, which is a statement about this node, not
  something to inherit. `Raw` is this node's authored body.

## Why this is the second fix of the same shape today

`plugin-distro`'s `resolveDistro` drops the same two new fields, for the same reason —
a hand-written copy of a struct that grew (opencharly/plugin-distro#6). Fixing only that one
would not have helped: `omarchy` declares `inherits: arch`, so the fields survived
`resolveDistro` and were then dropped **here**, one layer down. Two hand-written copies, two
repos, one class of defect.

That is why both fixes ship with a **field-walking parity guard** rather than just the
missing lines.

## How tested

**Four new tests.** The parity pair walks every exported field of `ResolvedDistro` and fails
on any that arrives zero, so a future spec addition cannot be silently forgotten here.

**There is one per BRANCH, deliberately.** `ResolveInherits` has two merged literals,
selected by whether the child declares its own `bootstrap`. A fix applied to only one of
them passes the other test while breaking every child that omits bootstrap — so the second
test asserts it is exercising that branch before checking anything.

```
$ go test -count=1 ./spec/ -run 'ResolveInherits_'
ok  	github.com/opencharly/spec/spec	0.003s
```

**Negative control 1 — restore the drop in both literals** (i.e. `main` as it stands):

Both branches, four fields each — the shipped defect reproduced exactly.

**Negative control 2 — fix ONLY the first literal** (the natural half-fix):


The two remaining tests cover the semantics rather than the plumbing: a child with no
`disk_layout`/`installer` **inherits** the parent's intact, and a child that declares its
own **overrides** — the direction that would be worse to get wrong, because it silently
ignores what the author wrote.

## Rulebook compliance

- **R1 — RCA every anomaly.** The `vm build` failure was chased through *two* layers rather
  than patched at the first one that would have made the symptom go away. Fixing only
  `plugin-distro` would have left this drop in place and the subvolume feature still inert.
- **R3 — no duplication.** The fix is inside the single existing projection; no parallel
  resolution path was added.
- **R4 — no workarounds.** No consumer-side re-reading of `Raw` to route around the
  resolver, no defaulting at the point of use.
- **R5 — delete legacy completely.** Nothing to delete; the guards are what stop the pattern
  recurring on the next field.
- **R7 — prove the gate.** Full `-count=1` suite pasted above from the committed tree, plus
  two negative controls.
- **R10 — fresh disposable proof.** Both negative controls ran against deliberately reverted
  trees restored from a backup; every result above is from the committed state.
