# 0.2026287.1848 — feat(contract)!: retire the build-engine selector — the builder is BuildKit, not an engine

Agent: buildkit-lead
Tracking issue: opencharly/opencharly#481 (relates to — the 13-leg adoption this is leg 1 of)

## Summary

**The image BUILDER stops being a container-engine selector.** The builder is BuildKit — which is not a container engine and cannot run a container, so it can never be a member of the closed `#EngineName` vocabulary (`podman|docker|nerdctl`). A `build:` selector with exactly one legal value is the dual path this cutover deletes, not keeps.

This is **leg 1 of the BuildKit adoption cutover** (the producer leg: every consumer reads these types). It is one theme — *the build engine's identity retires from the contract* — and one module-suite gate proves it.

**Deleted from this contract:**

| surface | file | what it was |
|---|---|---|
| `EngineConfig.Build` | `hostenv/runtime_config.go` | the authored `engine.build` key of `~/.config/charly/config.yml` |
| `CHARLY_BUILD_ENGINE` | `hostenv/runtime_config.go` | its env override |

| `#BuildEnsureRequest.build_engine` | `schema/buildwire.cue` | a wire field whose only meaning was a cross-engine transfer (`docker save \| podman load`) — a shape that cannot exist once there is one builder |

**⚑ The rename belongs in THIS PR, and the reason is a loadability hazard that makes it mandatory here:** a `rename_key` entry (leg 2, in `plugin-migrate`) renames users' configs to the new key — but users' configs are validated against the **closed** ingress schema, so if the entry landed before the schema rename, every renamed config would be **unloadable**. The schema must land first; the entry follows.

**`ResolvedRuntime.BuildEngine` is the load-bearing deletion, and the reason is a safety property rather than a preference:** deleting it breaks nobody *when this PR lands*, because every consumer compiles against **its own pinned `spec`** and meets the deletion only when its own leg bumps the pin. The compiler then **forces** each of the twelve consumer sites to be visited rather than discovered later — a leg that bumps the pin without fixing its sites simply does not build. ### ⚑ What happens to an existing `engine.build:` in a user's config — asked and answered here

**It is inert: silently ignored, not a load failure.** `RuntimeConfig` is parsed with a plain `yaml.Unmarshal` (`hostenv/runtime_config.go`, no `KnownFields`) — the closed-schema gate is the `charly.yml` ingress, not this runtime settings file. That is why **no migration-table entry is owed**, and that is measured rather than assumed: the migration table lives in `plugin-migrate`, whose engine reshapes `charly.yml` and the per-host overlay `~/.config/charly/charly.yml` (`engine.go:497`) and never this settings file. The guarantee is held by a control rather than by prose — `TestResolveRuntime_RetiredBuildKeyIsInert` writes exactly what the retired settings command leaves on disk and asserts the load still succeeds and the run engine still resolves.

### ⚑ One prose claim examined and deliberately NOT changed

`protocol/schema/plugin.cue` (F10 `HostBuild`) says *"the build engine stays in core"*. A reader will ask whether this cutover falsifies it. It does not: the `buildengine-*` host legs are still host-side by design (`plugin-build` reaches them over `HostBuild("buildengine-connect-plugins")`, `buildengine-context-ignore-baseline`), and the claim does not name the retired selector. Examined, accurate, left alone.
