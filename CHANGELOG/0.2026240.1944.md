# 0.2026240.1944 — fix(refs): persistent latest-tag + default-branch cache — charly status 168s -> 89s (#208)

## Summary

Fixes opencharly/charly#208: charly status takes 167-180s warm. Root cause: GitLatestTag and GitDefaultBranch run git ls-remote (a NETWORK operation) for every version-less @github ref the resolver walks — measured at 366 git-remote-https invocations and ~140s of futex wait.

Fix: a TTL-bounded persistent cache (1h, latest-tags.json beside the repo cache) for the latest-tag and default-branch lookups. Tags are immutable and the default-branch NAME is stable, so a stale entry is at worst one tag behind. GitResolveRef (the DownloadRepo freshness check) is deliberately NOT cached — the freshness contract requires seeing the live commit of a mutable branch.

This is a clean rebuild (v2) of the closed PR #56, whose branch had accumulated a bad merge commit pulling in 14 unrelated main commits (PRs #53-61); this branch is live main + ONLY the 3 refs files.

Live timing on the charly repo project (a charly binary built with this spec via a replace directive; warm cache after one cold run):

```
$ rm -f ~/.cache/charly/repos/latest-tags.json
$ /usr/bin/time -f "COLD: %es" <charly-with-fix> status >/dev/null   # populates the cache
COLD: 102.92s
$ /usr/bin/time -f "WARM: %es" <charly-with-fix> status >/dev/null
WARM: 89.41s
```

Before the fix: 167-180s warm. After: 89s — a 47% improvement. The remaining ~89s is the DownloadRepo freshness check, which must stay uncached to honor the freshness contract.
