# 0.2026326.2226 — feat(schema)!: a builder reply MUST name its output — a stale plugin fails at its first message

## Summary

Fixes the root of opencharly/sdk#615 the way DESIGN says incompatibility is expressed — not with a version.

DESIGN.md §4.4: *"There is no version negotiation. Compatibility is the validation of every message (D-PROTO-6): a plugin built against a different protocol shape fails at its first message, naming the field."* `#BuilderResolveReply` was all-optional, so a builder plugin that predates the unified contract still emitted a **valid** reply: the host copied its payload, found no package to install, and shipped an image without the package while the build stayed green (measured on `plugin-builder-aur:v2026.271.2317`).

- **`#BuilderResolveReply` now REQUIRES `output: "package" | "files" | "inline"`.** A reply with no discriminator does not validate, so the host answers `invalid` naming `output` at the first message — no coercion, no negotiation, no version field, exactly as §4.4 prescribes.
- The correspondence the discriminator promises (`package` for a package output, `copy_artifacts` for files, `inline_fragment` for inline) is stated on the definition and enforced by the host on receipt; it is not expressed as a CUE `if` over optional fields because that shape does not survive `gengotypes` (the generated struct collapsed to `any` — measured, not assumed).
- `spec/cue_types_gen.go` regenerated with the repo's own `schemagen` (a clean regeneration; no hand edit).

## How tested

Five new schema tests — four of them fail on the pre-change schema, and the fifth guards a property that only exists after it (an unknown discriminator on a now-required field; pre-change, `output` was not a field at all, so that case was already an error for a different reason):

- the **exact old-style reply** (`{stage: "FROM x AS y", copy_artifacts: [...]}`, no `output`) is rejected under a **concrete** validation — the judgement a received message gets, since a required field is only enforced on a complete value;
- a package output (with `package`), a files output (with `copy_artifacts`) and an inline output (with `inline_fragment`) each pass;
- an unknown discriminator (`output: "binary"`) is a schema error, not a free-form string — a closed vocabulary post-change (stated above, so the claim matches what the case can show).

- **R1:** the finding is sdk#615; the mechanism chosen is DESIGN's own (§4.4 + D-PROTO-6), not an invented version counter — an earlier draft of this work proposed a `ContractVersion`, which contradicts §4.4 and was dropped.
- **R2:** one way to express incompatibility: message validation. No second compatibility path is added.
- **R3:** no workaround: the reply is not coerced when `output` is absent, and there is no fallback branch.

- **R6:** `git status` clean before the push; branch off fresh `origin/main`; no force-push.
- **R7:** the tests fail without the change (the old-style reply passes validation before it, and the new cases do not exist).
- **R8:** no live service involved.
- **R9:** nothing installed; `go` runs against the tree.
- **R10:** the class gate is this repo's own CI (gofmt/build/vet/tests), run above; the schema regeneration is part of it.
- **R11:** touches **D-PROTO-1** (the reply is a generated protocol message), **D-PROTO-6** (every message is validated on receipt against its definition — this is the definition that makes an outdated plugin's message invalid) and **D-IR-1**'s builder leg (the reply is the IR's builder input). No DESIGN text changes: §4.4 already states the rule this change makes enforceable.
