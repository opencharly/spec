# 0.2026329.803 — feat(seam): the pod-lifecycle reply carries the service command's output

## Summary

`charly service status` exits non-zero on a healthy deployment that declares a run-to-completion
service, because it propagates the init tool's aggregate exit code: `supervisorctl status` returns 3
when ANY process is not `RUNNING`, and a declared one-shot that has finished is exactly that. The
caller cannot tell the two situations apart, because the rows are printed host-side
(`pluginDeployTarget.Shell` prints `reply.Output`) while the one-shot declaration lives in the
image metadata only the calling plugin reads (`restart: no`, `start_sec: 0`, `exit_code: "0"`).

This adds the one field that closes the gap — `output?: string` on `#PodLifecycleReply` — so the
host captures the op="service" stdout, the caller prints it once, and the caller judges the rows
against the declared services it already resolves for that verb (opencharly/charly#1271).

`exit_code`'s population widens from op="cmd" to op="cmd" and op="service"; every other op's reply
stays empty and keeps printing host-side. No authored wire key changes, so no migration is implied.

**The shape's DESIGN projection is filed, not argued.** No host-build seam reply shape is
projected into `DESIGN.md` today (§4.5 covers the plugin protocol's `#Request`/`#Reply` envelope
and names no seam reply) — the pre-existing `exit_code` has the same standing. That gap is
opencharly/opencharly#1276, filed with the grep evidence, and this PR says so in
`## Filed issues` rather than asserting the gap away.
