# 0.2026250.200 — fix(refs): the bounded git-op runner survives a descendant that outlives the killed git (the 194-repo metadata-warmup hang)

## Summary

The deterministic 194-repo git-metadata hang is fixed at its proven mechanism: `runGitOp` in `refs/git.go` — the centralized git layer EVERY charly command, loader, and plugin uses — bounded each network git subprocess with a context deadline, but the deadline was **dead code whenever a descendant outlived the killed child**. `exec.CommandContext` kills only the direct `git` process; `git-remote-http(s)` inherits the stdout/stderr pipe write-ends and — stuck in its own libcurl read (libcurl has no default response timeout) — never closes them, so `cmd.Output()` sees no EOF and blocks **forever** despite the fired context.

This is the `check-cross-local-http` freeze: the loader's cold `WarmUp` (194 repos × 2 ops, 10 workers) hit one stalled connection during the burst → one worker goroutine wedged at the pipe wait → `wg.Wait()` never completed → the run froze at `fetching git metadata for 194 repo(s) (first run — may take a moment)...`. The old passing run (2026.249.2233) had a warm cache, so no warmup ran at all — hence "passed before, hangs now" with the same bed. The mechanism was reproduced live with a minimal probe: a 1s deadline on `git ls-remote` against a never-responding server left `cmd.Output()` unreturned after 8s, with `git remote-http` visible reparented to PID 1 holding the pipes.

The fix (two bounds on the same runner):
1. **`cmd.WaitDelay = gitOpWaitDelay`** (5s production, test-shrunk) — after the process exits, the pipes are force-closed and the wait ends; the deadline becomes real (the error reports the timeout; the existing bounded retry then re-resolves, so a transient stall still recovers exactly as the r9 contract intends).
2. **`GIT_TERMINAL_PROMPT=0`** (stripping the operator's own value) — an auth-challenged repo (a private or renamed `@github` import answers 401) otherwise blocks invisibly on an interactive `/dev/tty` username/password prompt — invisible because `runGitOp` captures stderr — for the full deadline ×(retries+1) per op; in a 194-repo cold warmup that reads as a hang. With prompts disabled the challenge is an immediate permanent failure whose error the caller can report. A deliberately configured askpass helper still works (`GIT_ASKPASS` untouched).
