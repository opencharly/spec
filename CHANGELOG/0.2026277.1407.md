# 0.2026277.1407 — feat(schema)!: #WorkflowResumeRequest.approve is tri-state, so a rejection reaches the wire

## Summary

`#WorkflowResumeRequest.approve` becomes **tri-state**, so that a *rejection* can reach an engine at all. Four commits, and the first is the whole change.

### The defect — a "no" that could not be said

```cue
approve?:      bool     // with `json:"approve,omitempty"` this is a LIE
```

A plain optional `bool` under `omitempty` makes `false` **byte-identical to an absent field**. The envelope's answer arms are `approve` / `response` / `cancel`, so **"the human rejected this gate" and "no approval answer was given at all" were the same wire value** — a rejected approval had no encoding, and the approval half of a resume was unreachable.

This is not a feature request. The engine had already detected it and worked around it, in a comment that states the collapse as if it were the design:

```
$ grep -n -B3 'state.Approved = in.Approve' candy/plugin-lobster/run.go
	// The wire request cannot distinguish "approve: false" from "approve omitted" (CUE
	// `approve?: bool`), so the decision is read by which field the caller used: a
	// response is an input answer, `cancel` is a cancellation, and anything else is an
	// approval decision whose value is `approve`.
	switch {
	case in.Cancel:
```

An engine inferring a human's decision from *which field the caller happened to set* is the defect, made explicit. The maintainer settled the contract — **tri-state**, and `cancel` stays what upstream lobster means by it, an **abort**, not a rejection:

```
--approve yes  ->  approve = true     approved
--approve no   ->  approve = false    REJECTED — distinct from absent
--cancel       ->  cancel  = true     ABORT — says nothing about acceptability
(neither)      ->  approve absent     no answer given
```

### The change — one annotation, and the wire key does not move

```cue
approve?:      bool @go(,type=*bool)
```

That is the recipe's own **pointer / tri-state arm** (`references/schema-change-recipe.md`, step 2) and the spelling the repo already uses for exactly this purpose — `schema/box.cue:61` `enabled?: bool @go(,type=*bool)`, `schema/deploy.cue:249` `disposable?: bool @go(,type=*bool)`. It is an **annotation, not a type change**: the CUE type stays `bool` and the **wire key stays `approve`**.

`check-lobster-app` composes `plugin-lobster` (project-local) with `@github.com/opencharly/plugin-task/candy/plugin-task:v2026.276.1230`, so the engine under test is the one assembled from **this** tree, and `check-lobster-local` is torn down and rebuilt from scratch on every run.

The observable is narrow on purpose: **a resume that carries a token but NO decision.** Before this change the engine's catch-all `default:` arm read that request as an approval whose value was the zero `bool` — i.e. a **rejection** — so it silently *cancelled and destroyed* the pending gate. After it, the request is refused **by name** and the gate survives. That difference is what the bed asserts, and it is the reason the change exists.

The field on the wire, all three states:

| caller intent | wire JSON | engine reads |
|---|---|---|
| approve | `"approve":true` | `*Approve == true` → proceeds |
| reject | `"approve":false` | `*Approve == false` → cancelled |
| **no answer** | key **ABSENT** | `Approve == nil` → **refused by name** |

`omitempty` on a pointer omits only `nil`; a pointer to `false` is **not** omitted. Rejection and no-answer are therefore distinct documents — which is the whole point, and what a plain `bool` could not express.
