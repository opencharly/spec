# 0.2026249.1948 — feat(ir): the uniform ordered member tree — the dual Children/Members maps die (Cutover C task 0, IR half)

## Summary

The deploy node carried a DUAL member representation: `Children` (nested-inside venue) vs `Members` (brought-up alongside) — two maps whose classification was CHOSEN BY A BRANCH (the loader's root-kind test, `BuildFleetNode`'s `dn.Target == ""`). One authored shape, two meanings: the R3 violation the nested-capture plan's Cutover C task 0 rebuilds.

This PR is **Cutover C task 0's IR half**: the dual maps are REPLACED by ONE uniform ordered member tree per node.

### The type design (before → after)

Before (dual maps, classification stored as tree branches):

```go
Children map[string]*Deploy `yaml:"nested,omitempty"` // nested-inside venue
Members  map[string]*Deploy `yaml:"peer,omitempty"`   // brought-up alongside
```

After (one uniform ordered member tree; the class is DERIVED from position):

```go
// on Deploy:
Member []Member // the ONE ordered member list — authored order preserved

// the singular entry type (#Member in schema/deploy.cue):
type Member struct {
    Name     string // the tree key (dot-free — validateDeploymentName)
    Position string // "deploy-level" | "in-substrate" — stamped by the fold
    Node     *Deploy
}
```

Alongside-vs-deploy-into is DERIVED FROM POSITION (deploy-level vs in-substrate), never stored as a branch: the pure derivation surface lives in spec/member_tree.go (`Alongside`, `InSubstrate`, `DeployLevelMembers`, `InSubstrateMembers`, `MemberByName`, `HasMembers`). The fold (sdk half of task 0, next in the wave) stamps `Position` from the authored depth alone — a sibling of the kind key is deploy-level; an entity key inside the kind body is in-substrate; the root-kind branch DIES.
