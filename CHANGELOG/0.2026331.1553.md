# 0.2026331.1553 — fix(merge): carry defaults.buildkit through the unified merge

## Summary

`mergeBoxConfig` — the per-field, dst-wins `BoxConfig` merge inside `MergeUnified` — copies every `defaults:` field by hand, and **`Buildkit` was not in that list**. So a project that authored `defaults.buildkit` had the block validated by the `#NodeDoc` gate and then **silently dropped** by the loader's walk→materialize merge: the build drive always saw `Defaults.Buildkit == nil` and rendered the sdk defaults instead (opencharly/charly#1306).

One field, one test:

```go
// defaults.buildkit — the project's buildkitd daemon settings. MISSING from this list
// until now ...
if dst.Buildkit == nil {
    dst.Buildkit = src.Buildkit
}
```

`dst wins if set` is preserved: a root document that states the block keeps it.

## How tested

```
$ GOWORK=off go build ./...        # exit 0
$ GOWORK=off go vet ./...          # exit 0
$ test -z "$(gofmt -l .)"          # exit 0
$ GOWORK=off go test ./...         # PASS (merge, spec, schemaparams, schemaretag, storeroot, ...)
```

`TestMergeUnified_CarriesDefaultsBuildkit` merges a `defaults.buildkit` from an imported document into an empty root and asserts the values survive, then asserts root-wins.

**Red arm** — the field removed from the merge again:

```
--- FAIL: TestMergeUnified_CarriesDefaultsBuildkit (0.00s)
    merge_unified_test.go:132: the authored defaults.buildkit was dropped by the merge
FAIL
```

**How it was found:** a live project authored `max_parallelism: 2, reserved_space: 50GB, max_used_space: 60GB, min_free_space: 7GB`; `charly box validate` said OK and the build succeeded, but the daemon config the drive wrote carried `max-parallelism = 4` and `100GB/100GB/10GB` (the sdk defaults). A plain `yaml.Unmarshal` into `spec.UnifiedFile` DID populate `Defaults.Buildkit`, which located the drop in the merge rather than in the schema or the decoder.

### Spike

**RCA claim:** the authored block survives validation and decoding but not the loader's merge.

**Candidates:**

- **A. Add `Buildkit` to the per-field merge (chosen).** Instrument: the new test merges it and asserts the values; the red arm above is the pre-change behaviour. **Works.**
- **B. Make `MergeUnified` replace the whole `Defaults` struct when src states the block.** **Spiked**: implemented as `if src.Buildkit != nil { *dst = *src }` and run against the suite (`-count=1`):
  ```
  --- FAIL: TestMergeUnified_CarriesDefaultsBuildkit (0.00s)
      merge_unified_test.go:143: the root document's buildkit must win:
        &{MaxParallelism:2 ... ReservedSpace:50GB MinFreeSpace:7GB}
  FAIL
  ```
  An import's `defaults` **overwrote the root document's `MaxParallelism: 9`** — it breaks the per-field `dst wins if set` rule the rest of `BoxConfig` relies on. Eliminated by measurement.
- **C. Have the drive read the block from the project envelope instead of the merge.** **Spiked** with an identity/value probe on `ProjectConfig()`, which is what builds the envelope:
  ```
  $ go test ./spec/ -run TestZZCandidateC -v -count=1
  PROBE uf.Defaults.Buildkit=<nil> cfg.Defaults.Buildkit=<nil> sameStruct=false
  ```
  The envelope's `Defaults` is a copy of the SAME merged value, so a second reader sees the same `nil` — C cannot recover what the merge dropped, and it would put a second reader beside the one merge (R2). Eliminated by measurement.

**Winner:** A. **RCA verdict:** confirmed — the merge was the only place the block disappeared. The field list is now marked hand-maintained with its failure mode named, so the next new `BoxConfig` field cannot be added silently.
