# 2026.227.1157 — the build-scope verdict resolver refuses a stale short-name election

`charly check box <box>` could certify an image that was not the one you built,
report every step green, and give no sign. This is the resolver half of the fix
(the superproject and sdk halves land alongside).

## The defect, measured

Reproduced on 2026-08-15 (day 227): a candy edit added a `check:` step, the box
was rebuilt as `ghcr.io/opencharly/fedora-nonfree:2026.227.0835` / `:0836`, and
`charly check box fedora-nonfree` printed
`Image: ghcr.io/opencharly/fedora-nonfree:2026.216.1908` and `5 passed, 0 failed`
— running the OLD baked plan, with the newly added step absent entirely. A green
verdict with the right-looking step names, proving nothing about the artifact
under test.

Root cause, in this package. `ResolveLocalImageRef` partitions candidates into a
LABEL family (`ai.opencharly.box == <short>`) and a NAME family (the ref's
trailing repo segment matches), then takes the label family WHOLE and discards
the name family — `cands := labelCands; if len(cands) == 0 { cands = nameCands }`.
The fresh build carried `ai.opencharly.box=fedora.fedora-nonfree` (the emitter
labelled with the namespace-qualified box key while tagging the ref with the leaf
name — fixed in the sdk half), so it landed in the name family and was discarded
wholesale; the older bare-labelled images were elected, and among them the newest
tag was `2026.216.1908`.

The election's own ordering keeps the same failure reachable even with consistent
labels: its PRIMARY key is the content-derived `ai.opencharly.version` label, with
the per-build tag only as a tiebreak. An image built from a differently-versioned
source tree — a sibling worktree, a pulled release — therefore outranks a newer
build regardless of when either was produced. Both shapes are live on a
multi-worktree host; both were observed in the same `podman images` capture.

## `container.ResolveBuiltImageRef` — the guard

New: `ResolveLocalImage` returns the full answer (`LocalImageResolution`: the
elected `Ref`, the `NewestBuildRef` — the highest build-tag CalVer across BOTH
candidate families — and `Pinned`). `ResolveLocalImageRef` and the new
`ResolveBuiltImageRef` are both thin wrappers over that one body, so there is one
candidate gather and one ordering (R3).

`ResolveBuiltImageRef` resolves and then REFUSES when the elected image is not the
newest local BUILD, wrapping the new `spec.ErrStaleLocalImage` and naming both
refs plus the pinned re-invocation. It is for the verbs that pronounce a VERDICT
on a built artifact; every consumption path (deploy, `charly vm build`, builder
bootstrap) keeps the lenient election unchanged.

Refusing rather than silently re-electing the newest build is deliberate. Changing
the election's primary key would change what `charly update`, `charly vm build`,
and the pod deploy path resolve to — a far broader behaviour change than this
defect justifies, and one with its own wrong case (a colleague's build from older
sources winning). A stale check that errors is recoverable; one that PASSes is not,
so the ambiguity is surfaced and the operator names the artifact.

Two escapes, both pre-existing and now documented in `--help`: a full ref, or the
`<box>:<calver>` pin. The pin is why the R10 bed sequence is untouched — a bed
builds `box build <image> --tag <run-tag>` and checks `<image>:<run-tag>`.

## Coverage

`container/local_image_coneb_test.go`, over a fixture reproducing the measured
storage byte-for-byte:

- `TestResolveBuiltImageRef_RefusesStaleElection` — the regression gate. Fails on
  the pre-fix body (returns `…:2026.216.1908`, nil), and asserts the refusal names
  both refs and the runnable re-invocation.
- `TestResolveLocalImageRef_LenientFormStillElects` — pins the deliberate split:
  the lenient election is unchanged.
- `TestResolveBuiltImageRef_PinnedInputPassesThrough` — the escape hatch, and why
  beds never reach the guard.
- `TestResolveBuiltImageRef_ConsistentLabelsElectNewestBuild` — with the sdk
  label fix in place the guard does not fire; one family, newest build wins.
- `TestResolveBuiltImageRef_SiblingAliasIsNotANewerBuild` — guards the guard: a
  sibling deployment's `<deploy-name>:<calver>` alias is not "a newer build of
  this box", or every bed host would refuse every untagged verdict.
