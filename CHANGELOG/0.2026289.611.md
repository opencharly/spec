# 0.2026289.611 — feat(schema): the wire `CandyModel` carries the skills it owns

Add the owned-skill names to the wire CandyModel, closing the build-contract gap

#CandyModel is the schema's own declared BUILD model ("the plan steps + resolved
package/service/env/route sections a plugin ... reads WITHOUT holding the live
*Candy"), and skill.cue says a skill's `owner:` is "the build-time association
that decides which images carry it". So the build model could not answer, on its
own, which skills a candy carries: it carried the candy's IDENTITY and not its
skills.

The asymmetry was visible in the reader. CollectSkills (sdk/deploykit) already
takes `layers map[string]CandyModel` -- and uses it for allCandyNames -- but reads
the owner association from cfg.Skills and filters by s.Owner. The wire model was
in the signature and not in the answer.

WHY NAMES AND NOT THE BODIES. A skill's identity is its top-level node name (the
key of Config.Skills, map[string]json.RawMessage); its `owner` names the candy.
The bodies travel through Config.Skills and the marketplace generator, so
projecting them here would create a second source for content this model does not
resolve. Owner-qualified NAMES are the association, and the association is what
the build decides.

WHAT THIS PR IS, IN THE PRODUCER-FIRST CHAIN. The field belongs in the contract,
and the contract cannot be consumed until it is tagged:

  1. spec   -- add `skills?:` to #CandyModel                          <- this PR
  2. sdk    -- loaderkit/scan_candy.go:194 populates it (`m :=
               spec.CandyModel{Name: name, SourceDir: sourceDir}`)     <- needs the tag
  3. charly -- advances sdk; the ai.opencharly.skill label path completes

Step 2 is a different repo and cannot precede the tag: sdk requires spec at a
pinned version. So this PR is the contract half, and sdk is its named consumer.

WIRE CLASSIFICATION (per this repo's AGENTS.md). This adds an OPTIONAL field to a
WIRE shape. It does NOT alter an AUTHORED key -- users do not write `skills:`
inside a `candy:` node; the `skill:` nodes are separate top-level entities -- so
`charly migrate` is not implicated and no version machinery is needed. Declared
here because the repo's rulebook requires the classification to be declared.

THE EDIT, only where the schema says it belongs. The field lands in
#CandyModel's existing "OCI-label-collector surface" group (with security/hook),
because CollectSkills projects into the ai.opencharly.skill label for exactly the
same reason CollectSecurity/CollectHooks read their fields there. The #Def stays
closed.

THE COVERAGE, AND WHY TestGenReproducible WAS NOT ENOUGH. TestGenReproducible
compares the committed generated file against a fresh cue-gen, so it passes with
or without the field -- both sides regenerate consistently. That proves the
PIPELINE is reproducible, which is a different claim from "the model carries the
association". spec/candymodel_skills_test.go is the coverage this change needs,
and it asserts three things in the order a consumer depends on them: the field
EXISTS, its WIRE KEYS are the authored snake_case names `skills`, and it
ROUND-TRIPS as a list of names.

  MUTATION — the test fails without the change:

    arm 1, with the schema change:   go test -run TestCandyModelCarriesOwnedSkillNames ./spec/
                                     ok  github.com/opencharly/spec/spec  0.014s

                                     FAIL  github.com/opencharly/spec/spec  [build failed]

  Both arms, honestly: arm 2 fails at BUILD, because the test references the field
  at compile time. That is the hard failure mode. The reflection and round-trip
  assertions are what catch the subtler defect a compile check cannot — a field
  with a correct Go name and a wrong wire key, which would compile and silently
  not cross the boundary. The restoration after arm 2 was verified byte-exact
  (`cmp` against saved copies for both files), and cue-gen on the restored tree is
  a no-op with TestGenReproducible passing.
