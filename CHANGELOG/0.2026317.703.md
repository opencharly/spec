# 0.2026317.703 — feat(schema)!: delete the kind:pod body defs the owning plugin now declares

## Summary

`opencharly/spec#304` unit 3, **leg 2 of 3**. Leg 1 moved the `kind: pod` body into the plugin that actually serves the kind — `opencharly/plugin-substrate#32`, squash `937a9b0`, tag `v2026.317.0614` — and this leg deletes the contract's copy.

- `schema/pod.cue` loses `#Pod`; `schema/node.cue` loses `#PodValue: (#Pod | #DeployValue)`.
- **`#PodSidecar` STAYS, and it is the CONTRACT's.** It is this kind's keeper: `#ResolvedPod` (`schema/substrate_template.cue`) cites it and the kernel reads that envelope, so a def a kernel-facing contract shape references cannot live in one plugin's CUE module. The one deletion here is the one that has a live replacement.
- The generated Go follows the def: `spec.Pod` and the `PodSpec = Pod` alias in `spec/charly_names.go` are gone. A second `charly task cue-gen` is byte-identical: `KindValueDefs` 9 → 8, `#<Word>Value` defs 10 → 9, top-level kind-body defs 13 → 12.
- **Why the pod gate still gates:** leg 1 made the plugin DECLARE `InputDef: "#PodValue"` on the `kind: pod` capability, and the host resolves a kind's value def from the provider's DECLARATION (`kindValueDefPath`) out of the COMPOSED unit (base & every served plugin unit), consulting `spec.KindValueDefs` only as the compatibility fallback. Deleting the base def without that declaration would lose the gate **silently** — the old plugin declares nothing, so the path falls back to a deleted `KindValueDefs` entry and the gate returns without gating. That is why this leg must not be merged alone, and why the legs are ordered plugin-first.
- `spec/pod_test.go` is the deletion gate: `#Pod`/`#PodValue` absent, no `pod` entry in `KindValueDefs`, `#PodSidecar` and `#ResolvedPod` present **and still wired** (a probe carrying one sidecar entry still validates through the envelope), with `#CandyValue` as the positive control so the absences cannot pass vacuously. Every other test in this module passes identically with the defs re-added, which is exactly why the gate is a test and not a comment.
- Two prose surfaces the deletion made FALSE go in the same phase (R5): `.agents/skills/pod/SKILL.md` and the `charly.yml` skill-shelf comment both still pointed at the `PodSpec` Go type. They now name the plugin's own `schema/pod.cue` for the authored body and the contract's `#ResolvedPod` / `#PodSidecar` for what the kernel reads.

## Change classification

**Breaking change + rollback:** `kind: pod` bodies are no longer validated against a def in this module — the host gates them against the plugin's DECLARED `#PodValue`, resolved from the composed unit. Rollback is a revert of this one squash: the defs come back, `KindValueDefs` regains `pod`, and the plugin's declaration simply stops being consulted (the base map is still the fallback), so a revert restores the pre-leg-2 gate exactly — with the caveat that the revert must land WITH the consumers' pins going back, because a reverted base def beside a bumped `plugin-substrate` would re-introduce the twins that leg 1 removed.
