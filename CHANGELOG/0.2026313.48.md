# 0.2026313.48 — feat(cuemodule): export the CUE module declaration to Go consumers

## Summary

`schema.FS` carries the schema package, but not the CUE module that owns it. `cue.mod/module.cue` sits at this module's root — outside `schema/`'s `//go:embed *.cue` tree — so a Go consumer that embeds the schema and composes it as a **module instance** cannot read the one fact it cannot derive: the pinned `language.version` that governs evaluation.

This adds `package specmodule` at this module's root (`github.com/opencharly/spec`): one embedded file, `specmodule.FS`, carrying `cue.mod/module.cue` at the path CUE's loader requires. A consumer overlays it at `<root>/cue.mod/module.cue`, overlays `schema.FS` at `<root>/schema/`, and loads `./schema` from there.

Why this unit exists at all — the two alternatives, and why each is wrong:

- **Restate the declaration in the consumer** (module path + `v0.16.1`): a second home for a declaration only this module may make.
- **Compose the files without the module**: the loader then applies the consumer's toolchain default language version; the declared pin never governs, which is exactly the drift it exists to prevent.

`cue_module_test.go` gates the consumer-visible facts: exactly one file at the loader-required path, parseable as a module file, declaring this module path and `language.version` `v0.16.1`.

`ConcatSchema` is untouched and stays the gen pipeline's path. The two README claims that named it as the RUNTIME path now describe what does not move — the declaration's export, and the body the concatenator returns — because the consumer leg (charly) replaces that runtime path with this import. Neither sentence asserts that a consumer already composes the module: that leg lands after this merge, and the prose is scoped to what this head makes true.
