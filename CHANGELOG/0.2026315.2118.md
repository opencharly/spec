# 0.2026315.2118 — feat(storeroot): resolve the four charly roots in the contract module, where the host may import them

## Summary

`charly` core cannot reach the org's ONE cache-root resolver. The four roots and the single
`CHARLY_CACHE_DIR` override have exactly one implementation, and it lives in
`github.com/opencharly/sdk/storekit` — a mechanism kit that `charly`'s own boundary law forbids the
plugin HOST from importing. So core composed its own `.cache` path (`charlyDaemonPids` built
`$XDG_CACHE_HOME/charly` and `$XDG_RUNTIME_DIR/charly` by hand), and therefore could not see
`CHARLY_CACHE_DIR` at all, nor the detached `buildkitd` a relocated install puts there.

**This PR is leg 1 of 3 of the resolution recorded in opencharly/charly#1119: move the resolver to
the surface both sides may import.** A root is a contract before it is a mechanism — the host and
every plugin it serves must agree on WHERE the shared trees are, or a plugin writes into a tree the
host never sweeps — so the resolver belongs in the contract module, and the mechanism kit
re-exports it instead of keeping a second copy.

Scope, stated exactly:

- `spec/storeroot` now owns `Root`, `RootConfig`/`RootCache`/`RootState`/`RootRuntime`, `Dir` and
  `CacheDir` — moved from `sdk/storekit/roots.go`, same identifiers, same strings, same error
  text, same fallbacks.
- The store-ADDRESSING helpers stay where the store is: `StoreDir` and `NamedStores` are not root
  computation (they join a store name onto the cache root and test the OCI `oci-layout` marker), so
  they remain in `sdk/storekit` and now inherit the cache root from here.
- Leg 2 (`opencharly/sdk`) makes `storekit/roots.go` a re-export and bumps this tag; leg 3
  (`opencharly/charly`) points `charlyDaemonPids` at this package, which is what makes that repo's
  import-purity gate pass **as written**.

## Change classification

**Additive contract surface.** A new package; no existing symbol, type, field or file of this repo
moves, so every current importer of `github.com/opencharly/spec` compiles against this head exactly
as against `70528371bf06c226ba689eee2ee34e35af0fdc5f`. Nothing in `schema/`, `proto/` or the
generated Go changes, so no authored wire key moves, no `charly migrate` is owed, and there is no
`#SchemaVersion` machinery to bump (it was deleted by `CHANGELOG/0.2026270.938.md`).

**Breaking change + rollback:** nothing breaks for `spec`'s consumers — the diff is two NEW files
and zero modified ones, so no import path, exported type or generated artifact moves. The
deliberate consequences land in the sibling repos and are declared there: `sdk`'s
`storekit/roots.go` stops computing and starts re-exporting (its public API is unchanged: `Root`,
the four consts, `Dir`, `CacheDir`, `StoreDir`, `NamedStores`), and `charly`'s `charlyDaemonPids`
gains behaviour it did not have — it follows `CHARLY_CACHE_DIR`, and through `Dir(RootRuntime)` it
now includes the state root when `XDG_RUNTIME_DIR` is empty instead of dropping the runtime root
entirely (the resolver's documented fallback; it can only WIDEN the set of daemons the idle guard
follows). Rollback for THIS repo is one inverse commit: revert `96f9eb4`. Because legs 2 and 3
depend on this tag, their rollback is the pin — `sdk` and `charly` return to the previous
`github.com/opencharly/spec` version and their code reverts with it. There is no data migration in
either direction: the roots resolve to the directories they always did.
