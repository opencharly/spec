# 0.2026262.957 — fix(refs): honor CHARLY_REPO_OVERRIDE at the fetch LEAF, not just one caller

## Summary of changes

**RCA + root fix: `CHARLY_REPO_OVERRIDE` was honored at a CALLER, not at the fetch LEAF.**

`CHARLY_REPO_OVERRIDE` is the documented "verify an uncommitted tree before you push" mechanism (`spec/proc.RepoOverrideEnv`): it points an `@github` repo ref at a local working tree so an uncommitted candy/charly.yml change can be built and evaluated by ANY consumer before it is pushed. It was enforced in exactly ONE place — `sdk/loaderkit.EnsureRepoDownloaded` (the loader-side orchestration).

But the standalone generators call the fetch **leaf** (`spec/refs.DownloadRepo`) **directly**:
- `plugin-marketplace` (`charly marketplace generate`) — `readkinds.go:37` → `candywalk.CollectEntitiesRemote(roots, refs.DownloadRepo)`
- `plugin-docs` (`charly docs generate`) — `sources.go:152`
- `charly/charly/internal/pluginsgen` — `main.go:102`

None of them goes through `EnsureRepoDownloaded`, so **every one silently ignored the override** and fetched the pinned REMOTE ref even when the developer had set an override pointing at their live tree. That is the R4 hole: a mechanism whose whole purpose is to test uncommitted work, bypassed by the consumers that need it (I hit it regenerating the marketplace corpus from a skill branch: the override was set, and the generator still read the pinned tag).

**Fix (root, one implementation):**

- Move the override parse to `spec/proc` (next to `RepoOverrideEnv`) as `proc.RepoOverrideDir` — its natural home, shared by both sides.
- Enforce it in `spec/refs.DownloadRepo`, the fetch LEAF, so EVERY caller inherits it. The override tree is used verbatim and never migrated (migration would mutate the dev's tree).
Concrete edits (2 code files + tests, spec repo):

- `proc/repo_override.go` — add `RepoOverrideDir`; its `canonicalRepoPath` helper delegates to the ONE canonical `spec.NormalizeRepoSpec` (no second copy of the auto-prefix rule), and the comparison canonicalizes **both sides** (so a bare `owner/repo` `repoPath` matches a bare entry and vice versa — a one-sided compare silently ignored that form).
- `refs/git.go` — `DownloadRepo` consults the override first, before any cache/fetch.
- `proc/repo_override_test.go`, `refs/git_test.go` — regression coverage (incl. the bare/bare case).

**Consumer leg — landed and its ordering caveat.** `sdk/loaderkit.RepoOverrideDir` delegating to `proc.RepoOverrideDir` is **already merged** as `opencharly/sdk#266`. That PR did NOT bump the `github.com/opencharly/spec` require (it merged before this producer tagged), so `sdk` `main` currently fails to build (`undefined: proc.RepoOverrideDir`) — the cross-repo ordering violation. The heal is a **follow-up `sdk` PR bumping its spec pin to this PR's merge tag**, which I will open the moment this tags. Landing order: **this PR (spec) merges + tags FIRST → then the sdk pin-bump PR**.
