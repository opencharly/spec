# 0.2026255.1250 — feat(ops): export ParseResultJSON — the decoder beside the ResultJSON encoder

## Summary

Export **`ops.ParseResultJSON`** — the decoder for the `{status,message}` verb wire — beside the `ops.ResultJSON` encoder that already builds it.

**Why (R3):** the wire shape is declared once in this package (`resultWire` + `ResultJSON`), and that encoder's own doc comment says it exists *"so every verb plugin (and ServeCheckVerb) emits the SAME {status,message} shape (R3)"*. There was **no decoder**, so consumers hand-rolled the shape — `plugin-adb`'s `replyStatus` declared an anonymous `{Status, Message}` struct: a second declaration of a contract surface this package owns. `opencharly/plugin-adb#8`'s validator review caught exactly that duplication and asked for the decoder to move beside its encoder.

**Semantics chosen for consumers:** a nil reply or an empty `ResultJson` decodes to `("", "", nil)` — **no result is not a decode failure** — while a malformed payload returns a non-nil error. `status ∈ "pass" | "fail" | "skip"`.

Two focused tests: `TestParseResultJSONRoundTrip` (both directions — `pass` **and** `fail`, because the non-pass direction is the one that gates a consumer's tail) and `TestParseResultJSONEmptyAndMalformed` (nil → empty, no error; empty payload → empty, no error; malformed → non-nil error). Encoder and decoder therefore cannot drift apart silently.
