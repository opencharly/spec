# 2026.230.1242 — project scope becomes a contract: two constants and the function that applies them

Publishes the two environment names that carry charly's PROJECT SCOPE, and the one
function that hands that scope to a child process:

```go
const (
	ProjectDirEnv  = "CHARLY_PROJECT_DIR"
	ProjectRepoEnv = "CHARLY_PROJECT_REPO"
)

func ChildProjectEnv(inherited []string, projectDir string) []string
```

They live beside `UnifiedFileName`, the manifest filename they select, because they answer
the same question: which project's `charly.yml` is this process operating on.

## Why the names need to be shared rather than literal

They were string literals in the charly CLI. That was survivable while only the CLI read
them — but `sdk/deploykit` now has to STRIP both from a spawned charly child's environment
and set one explicitly (the packaging child must run under the project that owns the candy
being packaged, not the parent's). Two modules writing the same two names from separate
literals is exactly the drift this contract module exists to prevent, and the two are
mutually exclusive in the CLI, so getting one name right and the other wrong fails at
runtime rather than at compile time.

## Why the FUNCTION, not just the constants

Exporting the names alone would have left every caller to reimplement the same filter, and
review found that reimplementation already existed in three places — `sdk/deploykit`'s
`charlyChildEnv`, `candy/plugin-mcp`'s `childCharlyEnv`, and the literals in the CLI's own
tests. The operation is not "strip a variable"; it is "hand a child a COHERENT project
scope", and coherence is the part that is easy to get wrong: the pair is mutually exclusive
in the CLI, so a caller that strips one and leaves the other makes the child exit on
`--repo and --dir are mutually exclusive` instead of running. That invariant belongs to the
contract, not to each caller, so it ships as one function with its own tests.

`ChildProjectEnv` matches variable names EXACTLY (`strings.Cut` on `=`, then `==`), never by
prefix — `CHARLY_PROJECT_DIR_LOOKALIKE` is a different variable and survives. A regression to
a bare `strings.HasPrefix` would silently eat it, so a test pins it.

Coverage: four tests in `spec/load_directives_childenv_test.go` — both names stripped,
unrelated variables preserved, an explicit dir set without the repo surviving beside it, an
empty dir leaving no scope at all, and the lookalike-name case above.

## Scope of the behaviour change

Additive at the module surface: nothing existing changed shape or semantics. The behaviour
that moves is the DUPLICATED filter in the consumers, which collapse onto this function —
`sdk/deploykit` in opencharly/sdk#142 and `candy/plugin-mcp` in opencharly/charly#309, both
in the same landing chain as this commit.
