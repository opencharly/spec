# 0.2026287.1221 — feat(schema): microVM artefact arms — a raw/ext4 rootfs and a kernel in the VM-box contract

## Summary

Adds the **microVM artefact arms** to the VM-box contract, and the in-image layout record that lets one image carry two files. Closes #228.

A microVM's root drive is not one of the existing disk-image arms: the producer that works on a device-less host — `mke2fs -t ext4 -d <tree> <file>`, measured as umbrella ledger probe **P3** on a host with no loop device, no device-mapper and no privileged container — yields a **file**, and the VMM boots it together with a **separate kernel**. Neither had a provenance arm, and the delivery vehicle (`sdk/deploykit.EmitVmBoxAt` → an OCI image whose labels carry `#VmBoxMetadata` on `ai.opencharly.vm.box`) could describe only one file at one fixed path.

**The five files in the diff, each accounted for:**

| File | Change |
|---|---|
| `schema/vm_box_metadata.cue` | `#VmBoxSource.kind` += `rootfs`, `kernel`; their arm fields (`format`, `disk_mib`, `sha256`, `release`, `cmdline`); the new `#VmBoxArtifacts` def; `#VmBoxMetadata.artifacts?` |
| `schema/vm_box_metadata_test.go` | **new** — five CUE gates over the arms, the layout record and the metadata shape |
| `spec/vm_box_labels.go` | `VmBoxLabelMap["Artifacts"]` — the entry the repo's own completeness gate demanded |
| `spec/vm_box_metadata_test.go` | the label round-trip test gains a microVM-shaped second case |
| `spec/cue_types_gen.go` | **generated** by `charly task cue-gen` — never hand-edited |

**What each artefact carries, and why it is not duplicated.** *What a file is* lives on `#VmBoxSource`: a `rootfs` records the image whose tree was materialised, its `format` and the size it was built at (the deploy needs the size to decide whether the delivered filesystem must grow — a truncated file alone does not grow the filesystem inside it); a `kernel` records its digest, its release and its **command line**, which for a TAP network is where the guest's address is delivered (`ip=<guest>::<host>::<mask>::<iface>:off`) and therefore belongs to the artefact rather than to each deploy that boots it. *Where a file is* lives on `#VmBoxArtifacts` — `rootfs_path` and `kernel_path`, and nothing else, so no fact is stated twice (R2). The disk-only shapes keep today's path conventions untouched (`/disk.qcow2`, `/disk/disk.img`), which stay constants in the reader.

**Wire compatibility.** Every added field is optional, following the file's own convention for optional nested records — a value with `omitempty`, exactly as `source` does — so an artefact published before this change keeps parsing (gated below).
