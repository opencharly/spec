# 2026.240.1550 — fix(box): make openrc selectable via #Box.init

## Summary

The `spec` leg of batch **B1 — service-render correctness**, and its last piece.

The build vocabulary defines **three** init systems — `supervisord`, `systemd`, and `openrc`, the
last a first-class entity with its own `service_template`, `management_command` set and
`unit_path_template` — but `#Box.init`'s enum listed only two:

```cue
init?: "supervisord" | "systemd"
```

So a box could not select `openrc` at all: `init: openrc` failed schema validation against an init
charly fully implements.

That was invisible until now for a specific reason. Before `opencharly/sdk#175`, `#Box.init` reached
**nothing** — all three `ResolveInitSystem` call sites passed a hardcoded `""` — so the enum's
contents could not matter. Now that the field is actually read, an unselectable vocabulary word is a
live inconsistency between what the vocabulary defines and what a box may ask for.

The doc comment states the invariant the enum has to hold — *every value must be an init the build
vocabulary actually defines* — so the next init added to `charly.yml` has a stated reason to appear
here too, rather than being omitted the way `openrc` was.

## How tested

### Coverage that fails without the change

`schema/box_init_test.go` compiles the **shipped** schema the way consumers do
(`schemaconcat.ConcatSchema` over the embedded FS) and unifies a `#Box` against each init:

```
--- PASS: TestBoxInitAcceptsEveryVocabularyInit
--- PASS: TestBoxInitStillRejectsAnUnknownInit
--- PASS: TestBoxInitDocumentsItsInvariant
ok      github.com/opencharly/spec/schema
```

Reverting only the enum, with the tests in place:

```
--- FAIL: TestBoxInitAcceptsEveryVocabularyInit
    box_init_test.go:48: #Box.init rejects "openrc", which the build vocabulary defines
    as a first-class init: a box cannot select an init charly implements
```

The second case is what keeps the first honest: widening by loosening the type to `string` would
make it pass while silently accepting typos, so `sysvinit`, `runit`, `Systemd` and `""` are asserted
to stay rejected.

```

Regeneration is **reproducible** — a second run produces the identical tree, and the only generated
change is the doc comment flowing onto `Box.Init`:

+ // init — pin the box's init system instead of letting composition auto-detect it.
+ // Every value here must be an init the build vocabulary actually defines …

```

They fail deliberately rather than passing vacuously. Confirmed environmental by a control run on

where the 17/0 result above comes from. Not a defect, and nothing to fix.

## Not covered

- **No test mechanically checks the enum against charly's vocabulary.** `schema/box_init_test.go`
  (added in the second commit) asserts the enum accepts every init the vocabulary defines *by name*,
  and that it still rejects unknown ones — but it cannot read `charly.yml` to derive that list,
  because `spec` does not and should not import charly. A third case therefore pins the doc comment
  itself, since that comment is the only thing telling the next init's author to come here. The
  mechanical cross-check belongs in charly's `TestEmbeddedVocab_*` family, which already reads that
  file.
- **`init: openrc` is not exercised.** OpenRC is explicitly out of scope for the cstream program, so
  this leg makes it *selectable* and consistent, without claiming it is proven on a live image.
