# 0.2026307.1209 — feat(clirequest): carry the child's working directory (unit 1 of #819)

## Summary

**Head `5dea399fc393d4ad922934ece491133870847fee` — 2 files, +23 lines, no deletions.** `#CliRequest` gains one optional field:

```cue
// #CliRequest (schema/seam.cue)
dir?: string @go(Dir)
```

`dir` is the working directory for the `charly <argv>` child the host runs on a plugin's behalf. **Empty inherits the caller's cwd — which is what every caller gets today — so the field is additive and opt-in.**

**Why it has to exist.** "The current project" is not a stable referent in this codebase. A consumer that shells out on behalf of an **imported** project needs the child to read *that* project, while its own process cwd is the importer's. Measured on **opencharly/charly#819**:

```
$ ./charly/bin/charly check run charly.check-task      # from the umbrella
  FAIL … charly task list enumerates the declared tasks … [task-list-declared]
       stdout: expected to contain "check-task-smoke"
       (got: hooks, map, org-map, pins, policy-b, prune, self-test, skills, sync, verify)
```

The bed is declared in the *charly* repo; invoked qualified from the umbrella, its `${CHARLY_BIN} task list` step read the **umbrella's** project, so the assertion passed vacuously instead of testing the bed's own project. There was no way to ask for the other directory, because the wire type carried none — `#CliRequest` had `argv`, `capture`, `combined`, `best_effort`, `env` and nothing else.

**Generated, never hand-written.** `charly task cue-gen` produced the Go field from this CUE edit:

```go
// spec/cue_types_gen.go
Dir string `yaml:"dir,omitempty" json:"dir,omitempty"`
```

## This is unit 1 of a tracked three-repo cutover

`opencharly/charly#819` is the tracking issue and stays open until the last unit lands:

1. **`spec` — this PR.** `#CliRequest` carries the directory. *(landed here)*
2. **the host cli seam** — honour it when running the child (today it has nowhere to put it).
3. **`plugin-check`** — set it from `spec.UnifiedFile.BedScope(entity).RootDir`, applied to the bed's step requests, while `bedSetup` keeps the **root** project for bed resolution.

That split is deliberate and it is not scope-shrinking: an earlier attempt to do unit 3 alone, by passing the namespace root into `bedSetup`, was **disproved by a live run** — `"charly.check-task" is not a disposable check bed` — because `bedSetup`'s `dir` serves *both* resolution and the run's project dir. The wire type is the head of the chain because nothing downstream can carry the directory until it does.

**No consumer in this PR, stated plainly.** The field is inert until unit 2. It is optional, so no existing caller changes behaviour, and `TestGenReproducible` plus the full suite confirm nothing else moved.
