# 0.2026249.1030 — fix(refs): a cached DOWNLOAD path is only valid while its content exists

## Summary

**RCA (R1, measured):** the candy-scan fetch-fixpoint's `EnsureRepo` returned `(path, nil)` for a repo whose cache dir **does not exist** — the probe showed `exists=false, err=nil`. The `GitClient.Download` cache serves `repoPath@version` paths from a **persisted** map for the whole TTL — a wiped/evicted repo-cache dir is returned as a valid path, the scan proceeds to `ScanRemote` and fails "remote candy not found at <dead path>". That is the **same class** the sdk #219 materialized-tree cache fixed with component drift detection: **a cache result is only valid while its content is valid** — here enforced by a content check on the cached path.

**The fix:** `Download`'s cached-hit requires `dirUsable(path)` (the dir exists). A dead path is a miss → the downloader repopulates it. Only the path-carrying downloads map gets the content check (the tag/branch caches hold non-path values). The check is a plain `os.Stat`, deliberately NOT `IsRepoCached`/`submodulesPopulated` — the hot path (every status fan-out) must not pay the git-subprocess completeness check per hit.

**Outdated code removed:** the stale "5m TTL" doc sentence (the code uses `ResolveRefTTL` = 1h today, the one-default seam documented in the const block).
