# 0.2026265.2108 — feat(cache): generalize spec/cache into the ONE keyed Store

## Summary

Generalize `github.com/opencharly/spec/cache` from a TTL-only single-file cache
into the ONE keyed **Store** whose validity lives IN the entry, so a single
storage mechanism serves every cache policy the tree needs. This is the shared
mechanism the loader's materialized-tree cache (`sdk/loaderkit`) and a plugin
HTTP client (`plugin-gh`) fold onto instead of hand-rolling a third and fourth
copy (R3).

**Validity lives in the entry, never in the mechanism.** Three interchangeable
modes, one layout:

- **TTL** — `Entry.Resolved` + `FreshTTL` (the status hot path: image list,
  image labels, submodule verdicts, substrate probes).
- **Components** — `Entry.Components` + `FreshComponents` (content-addressed /
  identity validity: a GitHub blob keyed by SHA, the loader's walk envelope).
  No time validity: valid while the inputs are unchanged.
- **Validator** — `Entry.Validator` (an upstream revalidation token, e.g. an
  HTTP ETag) for a mutable upstream that must not re-fetch while unchanged.

**One storage layout** (`Store`): a directory of one JSON entry per key, keyed
by `sha256(key)`; lock-free atomic reads (tmp + rename publish); a per-key
advisory flock with a double-check on the `Fill` miss path (concurrent
first-missers compute once); Docker-style prune by entry cap. `StoreDir(name)`
names a store under `~/.config/charly/cache/<name>/` (`CHARLY_CACHE_DIR`
overrides the root); `OpenNamed(name)` is the one-shot open idiom;
`HashHex`/`KeyDigest` are the shared components helpers. `Fill` is the
compute-once primitive (a hit never calls it); a caller that must REVALIDATE a
mutable upstream reads the entry, revalidates, and puts the refresh.

**Consumers migrated onto the Store in THIS change, old API deleted (R5):**
`spec/refs` (submodule-populated verdicts) and `spec/container` (image list,
image labels). The former top-level `Read`/`Write`/`Invalidate`/`File` API is
gone, and the three store-open sites share `OpenNamed` (no copy-paste). The
loader (`sdk/loaderkit`) and `plugin-gh` fold onto the same Store in their own
producer-ordered changes — the package doc states exactly this scope. The
cache-file layout change is disposable local state (no migration entry; cache
state is not authored config).

New `cache/cache_test.go` pins each behaviour (each fails without it):

- `TestTTLValidity` / `TestComponentsValidity` / `TestValidatorRoundTrip` — the
  three modes.
- `TestFillComputesOnceUnderConcurrency` — 16 goroutines, ONE fill: the per-key
  flock serializes first-missers.
- `TestFillReturnsExistingWithoutCallingFill` — a hit never runs fill.
- `TestPruneReclaimsOldest` — the entry cap reclaims the oldest.
- `TestInertStoreNeverErr` — an empty dir degrades to compute-without-caching.
- `TestDeleteRemovesEntry` / `TestOpenNamedResolvesUnderRoot` / `TestHashHex` —
  the new exported API (Delete, Dir via OpenNamed, HashHex).
- `TestKeyDigestStableAndOrdered` — the components digest is order-independent.

`TestImageCacheTTLExpiry` / `TestSubmoduleCacheTTLExpiry` backdate through the
Store's `PutEntry` seam; `TestInvalidateImageCache` asserts the cleared Store is
empty; `TestImageCacheStoreDirIsNamed` asserts `imageCacheStore().Dir()`.
