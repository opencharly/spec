# 0.2026294.929 — feat(schema): admit the pooled fan-out arm (`lanes:`) on #PipelineArms

## Summary

`#PipelineArms` is a CLOSED struct, so a `kind: pipeline` step could not carry the `lanes:` arm that
`opencharly/plugin-lobster#8` serves — a pooled fan-out over a runtime collection, with `batch_size` as
the pool width. The width was already authorable; the arm key was not, and the refusal is the CUE gate,
before any engine is reached (`opencharly/spec#263`). The two `cue vet` runs under *How tested* are
that exact refusal and its removal, on one fixture and one command.

What this change is:

- `schema/pipeline.cue` — `#PipelineArms` gains `lanes?: string & !="" @go(Lanes)` beside `for_each`,
  sharing the companion defs that already exist (`item_var`, `index_var`, `batch_size`, `pause_ms`,
  `steps`); the companion group's comment names both arms. `#PipelineSubStep` deliberately does NOT
  gain it: a lane body is non-recursive by the same rule a `for_each` body is, and a case below pins
  that.
- `spec/cue_types_gen.go` — regenerated by `charly task cue-gen`. The Go is generated from the CUE,
  never hand-written, and a second run on the committed tree changes nothing.
- `spec/pipeline_test.go` — the closedness corpus gains the accept case (a `lanes:` step with its
  companions), a reject case for `lanes` inside a non-recursive substep, and a reject case for an
  empty operand. The accept case fails on the base schema with the exact error the field produced.
- The schema header named `plugin-pipeline`'s `OpValidate` as the home of the exec-arm XOR. That rule
  lives in `sdk/workflowkit.ValidatePipeline` (`plugin-pipeline` calls it before lowering); the header
  now says so, corrected while the arm list it enumerates was being changed. No behaviour depends on
  the sentence.

Diff: 3 files, 33 insertions, 7 deletions, one commit, head `78fc451`.

Scope: this admits the AUTHORED surface only. `sdk/workflowkit.ValidatePipeline` is a SECOND gate over
the same words — its `execArms` list and its loop co-field rules know `for_each` and not `lanes`, so a
lowered step is still refused there. That is a different module, measured under *How tested* and filed
as `opencharly/sdk#439`; it is not in this diff.
