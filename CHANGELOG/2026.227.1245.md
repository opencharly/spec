# 2026.227.1245 — the stale-temp sweep looks where temps are actually created

`SweepStaleTemps` globbed a hardcoded `/tmp` while every creator resolves through
`os.TempDir()`, which honours `$TMPDIR`. On any host that exports the variable
the sweep therefore scanned a directory no temp had ever been created in and
reaped nothing — silently, since it is best-effort by design and never errors.

Measured on one such host: **201 stale `charly-localpkg-` trees under `$TMPDIR`,
zero under `/tmp`.** Those are `--dev-local-pkg` bed build stages, the single
biggest thing the sweep exists to reap.

Member three of the check-verb correctness batch (members one and two:
`opencharly/charly` `CHANGELOG/2026.227.1157.md` and `2026.227.1230.md`).

## Two sites, one hardcode, and the second is the dangerous one

Both in `proc/cleanup.go`, fixed together (R3 — the same wrong assumption in the
same family; fixing one would have left the sweep half-blind):

- **`SweepStaleTemps`** globbed `"/tmp/" + prefix + "*"`. It now walks
  `sweepRoots()`.
- **`openedFilesByAnyProcess`** filtered `/proc/<pid>/fd` targets by a hardcoded
  `"/tmp/"` prefix. This is the sweep's guard (a) — "some process has this open".
  On a `$TMPDIR` host it recorded NOTHING, so every temp the sweep did reach read
  as unheld. The hardcode does not merely stop the sweep reaping; it removes a
  liveness guard from whatever it does reach. That is the half that could delete
  a live build, which is precisely the incident `temphold.go` was written for.

`sweepRoots()` returns `os.TempDir()` first — the one resolution every creator
uses (`proc.MkdirTempHeld("", …)`, `os.MkdirTemp("", …)`) — plus `/tmp` when
`$TMPDIR` points elsewhere, so leftovers created before the variable was set are
still reaped instead of stranded permanently. The per-entry guards (same uid,
older than the safety floor, not open, not flock-held) are identical for both
roots, so the extra root only ever reaps what the sweep already had license to
reap.

## Scope: host temp roots only

The `/tmp/...` literals elsewhere in the tree are CONTAINER- and GUEST-side
absolute paths — `/tmp/aur-pkgs`, `/tmp/charly-pkgs`, the `/tmp/downloads` and
`/tmp/npm-cache` cache mounts, `sdk/deploykit`'s venue tarballs. They are correct
as written, are not created by a host `os.MkdirTemp`, carry no sweepable prefix,
and must NOT be `$TMPDIR`-ified: the host's temp dir has no meaning inside a
container. Only the two host-side sites above were wrong.

## Coverage

The suite already discriminated, but only by accident of environment: the two
pre-existing sweep tests fail on a `$TMPDIR` host and pass without it, so on a
default runner they say nothing about this defect. Two new tests set `TMPDIR`
themselves and therefore fail on the pre-fix body wherever they run:

- `TestSweepStaleTemps_HonoursTMPDIR` — creates a sweepable, backdated, unheld
  temp the way real creators do (an empty dir argument), then asserts the sweep
  reaps it. It also asserts the premise it rests on (that `os.MkdirTemp("", …)`
  landed under the set `TMPDIR`), so a future change to that would fail loudly
  rather than make the test vacuous.
- `TestOpenedFilesByAnyProcess_HonoursTMPDIR` — holds a descriptor open under the
  set root and asserts the fd walk records it. This process's own fd is visible
  in `/proc/self/fd`, so it is deterministic rather than timing-dependent.

Both pre-existing sweep tests are untouched: they were HONEST — red because the
code was wrong — and were not adjusted to match the hardcode.

## Gate

`go test ./...` for the whole module in BOTH environments — with `TMPDIR`
exported and under `env -u TMPDIR` — green in each. Before this change the same
two runs disagreed: `proc` failed with the variable set
(`TestSweepStaleTemps_UnheldCreatorIsSwept`,
`TestSweepStaleTemps_ReleasedTempIsSwept`) and passed without it. A fix that only
passed under one environment would have reproduced the defect, so both runs are
the gate. `golangci-lint run ./...` 0 issues; `gofmt -l` empty.
