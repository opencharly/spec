# 0.2026240.1618 — feat(service): portable lifecycle fields + the unit_options escape hatch

## Summary

The `spec` leg of batch **B2 — service-schema expansion**. Purely additive: every field is optional
and its absence renders exactly as today.

### Four portable lifecycle fields on `#CandyService`

Each is expressible by **at least two** of the three inits. That is the admission rule, and it is
what keeps a single-init knob out of the shared schema:

| field | systemd | OpenRC | supervisord |
|---|---|---|---|
| `type` | `Type=` | `command_background` for forking | `startsecs=0` approximates oneshot |
| `requires` | `Requires=` | `depend(){ need … }` | — (ignored) |
| `restart_sec` | `RestartSec=` | `--respawn-delay` | — |
| `watchdog_sec` | `WatchdogSec=` | `--healthcheck-timer` | — |

`requires` is a **hard dependency**, distinct from `after:`'s ordering — OpenRC's template already
emits `need localmount`, so the concept exists there today with no way to author it.

`restart_sec`/`watchdog_sec` accept `"5s"` or a bare `5`, matching `stop_timeout`'s existing shape
rather than inventing a second convention.

### One escape hatch for everything init-specific

```cue
unit_options?: {[string]: {[string]: string | [...string]}}
```

Keyed **init-name → directive → value**. It exists so `#ServiceRenderContext` does not grow a field
per init-specific knob.

That struct's own doc calls it *"the data an init system's service_template renders against"* — a
kind-**agnostic** envelope. Putting `NotifyAccess`, `Slice`, `KillMode`, `RuntimeDirectory` and a
hardening block into the one struct all three inits render from would make it systemd's typed shape
wearing a generic name — the leak the boundary law names. With this map, a **fourth** init needs no
schema change, exactly as the `openrc` init entity needed no Go change.

A directive value may be a scalar **or** a list; a list emits the directive once per element, which
is what systemd expects for repeatable directives like `RuntimeDirectory=` or `ReadWritePaths=`.

### Both structs, together

`#CandyService` and `#ServiceRenderContext` gain the fields in the same change. A field on the entry
that never reaches the context is unreachable from any template, so the pair is asserted together
rather than trusted.

## How tested

### Coverage that fails without the change

The diff adds **8** test cases: 5 subtests in `TestCandyServiceAcceptsPortableLifecycleFields`, plus
3 standalone tests. Reverting **only** the two schema files to the parent commit, with the tests in
place — **7 of the 8 fail**:

```
$ git checkout HEAD~1 -- schema/candy.cue schema/init.cue
$ go test -count=1 ./schema/
--- FAIL: TestCandyServiceAcceptsPortableLifecycleFields (0.05s)
    --- FAIL: TestCandyServiceAcceptsPortableLifecycleFields/type (0.01s)
    --- FAIL: TestCandyServiceAcceptsPortableLifecycleFields/requires (0.01s)
    --- FAIL: TestCandyServiceAcceptsPortableLifecycleFields/restart_sec_as_a_string (0.01s)
    --- FAIL: TestCandyServiceAcceptsPortableLifecycleFields/restart_sec_as_a_bare_int (0.01s)
    --- FAIL: TestCandyServiceAcceptsPortableLifecycleFields/watchdog_sec (0.01s)
--- FAIL: TestCandyServiceUnitOptionsTakeScalarsAndLists (0.01s)
--- FAIL: TestServiceRenderContextCarriesTheSameFields (0.01s)
FAIL    github.com/opencharly/spec/schema       0.143s
```

**The eighth, `TestCandyServiceTypeIsConstrained`, passes on the old schema too** — `#CandyService`
is closed, so an unknown `type:` field is rejected there for the wrong reason. It is a *forward*
guard, not a discriminator: it fails only if someone later widens `type:` to a bare `string`, which
would silently let a typo render an invalid `Type=` directive. Stating that plainly rather than
counting it as coverage for this change.

`TestCandyServiceUnitOptionsTakeScalarsAndLists` puts a scalar and a list side by side in one map, so
the disjunction is exercised rather than assumed from reading the CUE.

All validate against the **shipped** schema, compiled the way consumers compile it
(`schemaconcat.ConcatSchema` over the embedded FS).

## Not covered — the consumer legs, in order

1. **`sdk`** — carry the five fields through `BuildServiceRenderContext` (the pure entry→context
   projection), so they reach a template at all.
2. **`plugin-init` + `charly`** — render them: systemd `Type=`/`Requires=`/`RestartSec=`/
   `WatchdogSec=` plus a `unit_options.systemd` range; OpenRC `need`/`--respawn-delay`/
   `--healthcheck-timer`. Until then these fields are authorable and inert, which is why this leg
   claims nothing about rendered output.
3. **B2's third item, `wait_for:`**, is deliberately **not** in this leg. Nine hand-rolled
   `while [ ! -e "$SOCKET" ]` loops exist today (labwc, kde-selkies ×2, chrome-cdp, wayvnc ×3,
   swaync, waybar, waybar-labwc, sway) and R4 forbids the sleeps and magic numbers they carry, but
   each init needs a genuine lowering (systemd `ExecStartPre=`, supervisord a rendered pre-exec,
   OpenRC `depend(){ need … }`) and the honest gate is deleting real duplication with those beds
   staying green. That is its own unit of B2.
