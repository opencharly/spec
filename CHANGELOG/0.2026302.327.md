# 0.2026302.327 — fix(report): a step renders on ONE line, so a reader can pair its status with its id

## Summary

The text report is a LINE format: a reader pairs each step's status with its id by parsing
one line per step, and the report states its own step count in the rollup it prints
underneath. `renderStep` wrote a step's text and its message VERBATIM, so a step whose text
carried a newline SPANNED several lines and its id bracket landed on a line of its own. The
report's step lines then disagreed with the report's own rollup, and a reader that checks
the two refuses the WHOLE report and credits nothing from it.

**Where it was found.** opencharly/layer-docs-site#13's R10 bed, `charly check run
check-docs`. All five of its check phases SKIP — *"the child's report could not be read: 21
step line(s) against the 22 step(s) its own rollup counted"* — and the run exits 3. The base
tree of that repo, WITHOUT the change that found it, produces the identical skip with the
identical numbers and the identical exit code, so the defect is pre-existing and lives HERE,
in the producer of the format.

**What lands.**

- `OneLine` — the one flattening rule for the report: every run of whitespace, a newline
  included, becomes one space. A step's keyword, text, id and message all go through it.
- `renderStep` writes the flattened fields, so a step is exactly one line and its status and
  its id are on the SAME line.
- The TAP reporter flattens the same way — a test point is one line too. Its diagnostic
  block is `%q`-quoted, so a multi-line message cannot break a point.
- The JSON and JUnit reports are STRUCTURED and carry the step's text as data; they keep the
  text verbatim, and the JUnit attribute is XML-escaped by the encoder.
- `truncate` cuts on a CHARACTER boundary. It used to cut on BYTES, so a multi-byte rune
  could be cut in half and the report carried invalid UTF-8 — a line a reader cannot
  decode, in a report whose whole value is that a reader can read it. The 200 limit now
  counts characters rather than bytes.

## Change classification

A bug fix in a library: the report format's producer now guarantees the shape the format's
consumers parse. It removes nothing that was usable and adds no new surface beyond one
exported helper, so no cutover machinery applies — the report's contract is unchanged in
NAME and in FIELD, and only the shape of a rendered step's text is corrected, to the shape
the readers already require. The gate is this module's own; the merge gate is the org-wide
`charly/pr-validator`.
