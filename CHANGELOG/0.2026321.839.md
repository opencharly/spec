# 0.2026321.839 — feat(needsolver): the ONE solver for every need and use (P09)

## Summary

**D-CAP-3 asks for "one solver" and there was none.** A `need:` names a capability it must be handed;
a `provide` names one it can hand out; nothing in the contract resolved the two. §8.2 says which
provide binds and D-CAP-1 says what happens when none does — but both were prose a human had to apply.

`needsolver` is that one solver, and it decides **which** provide a need is bound to:

```go
func Resolve(wants []Want, provides []Provide) ([]Binding, error)
func Union(sets ...[]Want) []Want          // D-CAP-6
```

| row | what the code does |
|---|---|
| **D-CAP-1** | a `need:` with no visible provide **fails the load**, and the error names the capability *and* the site that asked for it; a `use:` takes its `default:` or goes without — **not** an error |
| **D-CAP-3** | exactly one provide binds; **two visible provides are an error naming both**, because §8.2 says *"a provide is fixed: nothing replaces it"* — a second one is a defect, never a preference |
| **D-CAP-6** | `Union` is a **set**, so the same authored entry reached by two paths (a candy required by both the box and the deployment) is one entry, and a missing secret is reported once |

**This package lives in `spec`, not `sdk`, and that is a measured decision rather than a preference.**
D-CAP-3 says the HOST performs the solve; `charly/AGENTS.md`'s IMPORT-PURITY gate says core may import
`spec/*` + proto and **never** an sdk mechanism kit. Those two rows collide for any solver placed in
`sdk` — which is exactly the defect filed as **`spec#348`** while landing P06. `spec` is where the one
implementation of a host-performed cross-cutting concern belongs; `sdk` can re-export it the way
`sdk/storekit` already re-exports `spec/storeroot`.

### What it deliberately does not do, and why that is the contract

- **It does not deliver a binding.** D-CAP-4: bindings are *state*, delivered by the type owner's
  `bind`. Deciding *which* provide a need binds to and *delivering* it are two acts with two owners.
- **It does not gather visibility.** §8.2's five sources — the stack, the containing nodes, the
  alongside nodes, the registry, the grant — are only knowable by the caller, which is the one holding
  the tree. The solver resolves **the set it is handed**, and a test pins that a provide the caller did
  not make visible cannot bind.

```console
--- PASS: TestTheSolverOnlySeesWhatItIsHanded (0.00s)
ok  	github.com/opencharly/spec/needsolver	0.003s
```

**R7 — the halves that matter, and they are behavioural rather than compilation.** Each test drives a
rule to both sides:

- `TestAnUnboundNeedFailsAndNamesWhatWasSearched` vs `TestAnUnboundUseTakesItsDefaultOrGoesWithout`: the
  **same absence** must fail for a need and pass for a use. A solver that treated them alike would pass
  one and fail the other, so neither test can be satisfied by a stub.
- `TestTwoVisibleProvidesFailNamingBoth` asserts the error contains **both** origins — a solver that
  picked one arbitrarily would bind successfully and fail this.
- `TestTheSolverOnlySeesWhatItIsHanded` resolves the identical want to failure and then to success by
  changing only what the caller made visible — so it fails if the solver ever invents visibility of its
  own.
