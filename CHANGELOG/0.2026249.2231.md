# 0.2026249.2231 — fix(refs): the persisted latest_tags cache is an offline fallback, never fresh data

## Summary

The persisted `cache: git: latest_tags` cache (the per-host charly.yml) is re-contracted as an **OFFLINE FALLBACK, never fresh data** — the root fix for the plugin-resolution staleness anomaly: a fresh run minutes after `v2026.249.2212` was tagged still resolved `plugin-deploy-pod` to the stale `v2026.242.0932` ("latest tag").

## Root cause (R1)

`GitClient` loads the persisted `latest_tags` map at construction and served any entry younger than `LatestTagTTL` (1h) as fresh — so every new process within the TTL served a tag list up to an hour old. `GitLatestTag` itself sorts by CalVer correctly (fetch-order was never the bug); the 1h persisted-TTL reuse was. The original TTL rationale (the 152-concurrent-`ls-remote` throttling storm) is a WITHIN-ONE-PROCESS batch problem the in-process cache already solves; cross-process, resolution correctness outranks throttling (tags in this org land minutes apart).

## New contract

- In-process cache (1h TTL): unchanged — the batch-dedupe layer.
- Persisted `latest_tags` entries load into a separate `persistedTags` map and are served ONLY when the network fetch fails (offline tolerance, loud stderr line). A fresh process with a reachable network ALWAYS re-probes.
- `save()` writes the union (fresh values winning) so a save that never fetched a repo preserves its fallback entry.
- `ClearCache`/`CacheStatus`/`WarmUp` updated to the split model (fallback entries don't count as warm).
