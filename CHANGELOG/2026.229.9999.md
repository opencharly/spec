# 2026.229.9999 — StreamLoad: one tarball-free image-transfer primitive

<!-- PLACEHOLDER CalVer: the pr-validator regenerates this stamp at merge. -->

## Why

Three copies of the same `podman save | podman load` pipe existed in the tree
(`container.TransferImage`, `kit.TransferToRootful`, plugin-vm's `streamLoadAndTag`) and
a fourth was about to land for the new container-venue delivery verb `charly box load`.
The only thing they ever differed in was how the LOAD side is reached — a local engine, a
sudo engine, an ssh hop, a `podman exec`. That difference belongs at the call site; the
pipe does not.

## What landed

`container.StreamLoad(save, load *exec.Cmd)` — the single primitive. Callers supply their
own command pair. `TransferImage` becomes a caller; so does `kit.TransferToRootful` in the
sdk, and both venue bindings above it.

The unified body takes the strictest behavior of the three: both sides started before
either is waited on, both errors surfaced with the failing side named, and the load side's
stdout routed to stderr (`podman load`'s "Loaded image:" line is diagnostic, not a value
any caller parses).

Its doc records the hazard every caller must respect: `podman load` can exit 0 on a
TRUNCATED stream, so a green return is NOT proof of an intact image. A caller that cares
must probe afterwards — `deploykit.TransferImageToVenue` does.

## Proof

`TestStreamLoad_PipesPayload` asserts the bytes actually MOVE; the failure tests assert a
failing save side and a failing load side are each surfaced and named. This path had NO
test coverage before.

The coverage discriminates, proven by perturbation: unwiring `load.Stdin = pipe` leaves
the destination empty and fails the payload test; reverting restores green.
