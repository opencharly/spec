# 2026.229.1400 — the distro vocabulary becomes one CUE source; the Go copy is deleted

Placeholder CalVer (the pr-validator finalizes it at merge). Chosen after `2026.229.0947`,
with no filename or tag collision.

`hostenv.distroIDToFormat` was a hand-written Go map of 13 distro ids → package format. The
CUE schema separately needed the same id space to type a VM source's `distro:`. Two lists,
no gate between them, and SDD's rule is that schema-shaped Go is GENERATED, never
transcribed — so the duplication was the defect, not the thing to add a drift test around.

## One source, four projections

`schema/distro_vocab.cue` declares `#Distros`, one row per distro with three traits, and
`task cue:gen` projects it:

| generated | replaces |
|---|---|
| `spec.DistroFormats` | the hand-written `hostenv.distroIDToFormat` |
| `spec.DistroSSHUnits` | `vmshared.sshUnitForDistro`'s hardcoded `switch` |
| `spec.DistroInits` | `if distro == "alpine"` in the cloud-init renderer |
| `spec.DistroIDs` | — (derived from `#Distros`' own keys) |

`#DistroID` is derived from those keys too (`or([for id, _ in #Distros {id}])`), so the
closed field type and the trait tables cannot disagree: there is no second list to update.

**A distro's traits are data.** A Go `switch` on a distro name is the same duplication in a
less checkable form — it cannot be enumerated, cannot be validated, and silently defaults for
every id it does not name. That default is what rendered Arch package names and a
non-existent sshd unit onto Debian-family guests.

## What this makes possible

`init: openrc` is now an enumerable property of a distro rather than a branch. The superproject
entry for this CalVer uses it to declare OpenRC as a first-class init system beside systemd and
supervisord.

## `distro:` on a VM source

Typed `#DistroID` on both distro-bearing arms (`cloud_image`, `bootstrap`), so a misspelled id
is a unification conflict at author time — verified: `distro: ubunut` fails validation.

It stays `?`-optional in CUE deliberately, and the reason is worth recording because two
stronger-looking options were tried and reverted:

- A `!` required marker is not reported by the host's value gate, which is closedness-only
  **by design** (`charly/provider_kind_invoke.go` documents that as permanent, with the
  history of a kernel-side concreteness fix that was overruled by the boundary law).
- Making it a plain non-optional field does not add enforcement either — it only makes an
  absent value fail the `applyCueDefaults` DECODE with `cannot convert non-concrete value`,
  a worse error in a worse place.

PRESENCE therefore lives where the repo already says concreteness belongs: the kind's own
`OpValidate` capability. See the superproject entry.

## Not attempted

No migration fills this field. An earlier cut of this change did — it inferred the distro from
the image URL — and that is the same guess in a new location, which is what this whole cutover
exists to remove. A config that omits `distro:` now gets a validation error naming the entity
and listing the valid ids. Two published repos (`distro-arch`, `distro-fedora`) need the field
added and re-tagging before their consumers' pins can move; that is producer-before-consumer
ordering, not something a guess should paper over.
