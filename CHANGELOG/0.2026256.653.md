# 0.2026256.653 — fix(lock): queue and report on a contended flock instead of failing at 2m0s

## Summary

A blocking `AcquireFileLock` gave up after **2 minutes and named nobody**. Measured in a real check bed (run `2026.255.2310`, the `check-githubrunner-pod` image-build step):

```
charly: error: command "build": building githubrunner: acquiring build lock for githubrunner:
flock /home/atrawog/.cache/charly/locks/image-abNcNfNcNaeN.lock: lock held by another process for > 2m0s
```

The holder was a **peer cold-building the SAME image** — a legitimate hold (a cold image build measured up to ~26 min in the beds: `pod-immich-ml/cachyos` image-build 1529 s), not a stuck one. The correct behaviour is to QUEUE: the peer finishes, and the waiter then cache-hits. Any two concurrent check beds that share an intermediate therefore turned into a hard failure of one of them, at a bound shorter than one cold build.

### What changed

- **`lockTimeout` 2m → 30m.** The bound must exceed the longest LEGITIMATE hold or a healthy peer is reported as a failure. 30 m covers the longest measured cold build (~26 min) with headroom and **stays bounded** — the deploy-del guard (never an unbounded flock) is untouched.
- **`flockBounded` reports WHILE it waits.** Every `lockWaitReportInterval` (30 s) a waiting acquire prints to stderr what it is waiting for, who holds it, how long it has waited, and when it will give up. Without this a legitimate minutes-long queue is indistinguishable from a hang — this is the difference between a *reported* wait and a silent stall.
- **The timeout error NAMES the holder and the next step**, resolved from the KERNEL, not from the lock file:
  ```
  flock <path>: still held by pid 12345 (/usr/local/bin/charly box build cachyos) after 30m0s —
  that process is still running; wait for it to finish and retry (the kernel releases the lock when it exits, so there is nothing to clean up)
  ```
  `/proc/<pid>/fdinfo/<fd>` carries the locked file's inode AND the lock (`lock:\t1: FLOCK ADVISORY WRITE <pid> <maj:min:ino> 0 EOF`), so a waiter matches the inode, resolves the pid, and reads its command line. This is deliberately **not** a pid line written into the lock file: the file stays content-free (the removal those `WritesNothing`/`TruncatesStaleContent` tests pin shut), a dead holder can never be named (the kernel drops its flock on exit), and a waiter that has merely OPENED the file is never mistaken for the holder (it has no `lock:` line). Where `/proc` cannot answer (non-Linux, kernels without fdinfo locks) the description degrades to `another process (holder not identifiable on this platform)` — the WAIT is unaffected.
- **Regression-guard rename:** `TestAcquireFileLock_FailsFastOnContendedLock` → `TestAcquireFileLock_BoundedOnContendedLock` (the bound still terminates, but "fast" stopped being true once the normal hold became minutes) with the doc comment updated.
- New tests: the timeout names the holder + the bound + the next step; the waiter reports while waiting; the kernel-side lookup positively resolves the holding pid; the description falls back to text for an unheld lock.

### Follow-on (NOT in this PR)

The consumer is **opencharly/charly** (`charly/go.mod` requires `github.com/opencharly/spec`) — the new semantics reach charly's own sibling build lock (`charly/plugin_loader.go`'s plugin-binary `AcquireFileLock`) only through a **spec pin bump, which lands as its own charly PR** (together with the call-site message hardening).
