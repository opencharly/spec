# 0.2026296.1338 — feat(kubevirt): host_devices, the schema half of nested virtualisation

## Summary

`#KubevirtDevices` gains `host_devices` — a list of the new `#KubevirtHostDevice`
(`device_name`, optional `name`). It is the schema half of nested virtualisation: a KubeVirt guest
gets its own `/dev/kvm` **only** through `spec.domain.devices.hostDevices`, and a guest without
`/dev/kvm` cannot run a VM at all. A CPU feature (`svm`) alone is not enough.

## Why it is needed — measured, not assumed

The `blacksmith-*`-labelled Ubuntu runners stand in for real Blacksmith runners, and Blacksmith
documents KVM / nested virtualisation as supported **by default on its x64 Linux runners**
(<https://docs.blacksmith.sh/blacksmith-runners/overview#do-blacksmith-runners-support-kvm-or-nested-virtualization>).
Our fleet does not meet that bar today.

Host side — ready, measured on a `virt-launcher` pod on `quant-dev`:

```console
$ kubectl exec virt-launcher-… -- sh -c 'cat /sys/module/kvm_*/parameters/nested; \
    grep -m1 vendor_id /proc/cpuinfo; ls -l /dev/kvm'
nested=1
vendor_id : AuthenticAMD
crw-rw---- 1 qemu qemu 10, 232 /dev/kvm
```

All three nodes advertise `devices.kubevirt.io/kvm: 1k`.

Guest side — nothing reaches the guest:

```console
charly-ci-runner-2vcpu-1   /dev/kvm: No such file or directory   vmx/svm in cpuinfo: none
charly-ci-runner-8vcpu-1   /dev/kvm: No such file or directory   vmx/svm in cpuinfo: none
charly-ci-runner-32vcpu-1  /dev/kvm: No such file or directory   vmx/svm in cpuinfo: none
```

The rendered VMI explains both: `cpu: {cores: 8, model: host-model}` (a migratable model, so
`svm` is dropped) and a `devices:` block with no `hostDevices`. `cpu.model` was already
expressible; `hostDevices` was not. This unblocks it.

## Shape

```cue
host_devices?: [...#KubevirtHostDevice]

#KubevirtHostDevice: {
    device_name: string   // the resource the device plugin advertises, minus `devices.kubevirt.io/`
    name?:       string   // the label inside the guest; KubeVirt defaults it to device_name
}
```

Typed rather than typed-open like `disks`, because both fields are meaningful and `device_name`
is required. The device vocabulary stays the cluster's, not ours — `kvm` today, anything a device
plugin advertises tomorrow.
