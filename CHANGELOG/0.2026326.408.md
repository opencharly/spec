# 0.2026326.408 — feat(schema)!: #Builder drops the authored copy_artifact/copy_binary

## Summary

This completes the plugin-owned install contract of opencharly/sdk#608 in the schema. **`#Builder` drops the authored `copy_artifact` and `copy_binary`, and the `#Copy` definition only they used.**

Why this is needed after opencharly/spec#420:
- opencharly/sdk#613 (merged, `v0.2026326.342`) made what a builder copies into the target the builder plugin's own knowledge. Its payload and tool binary come back in its `#BuilderResolveReply` (`copy_artifacts`, `copy_binary`).
- As of sdk `v0.2026326.342` (sdk#613), no code reads the authored fields. Every read of either name in sdk's `origin/main` is a read of the plugin's reply (the liveness sweep below). `#Builder` still accepted them. (charly's `main` pins the older sdk `v0.2026325.921`, which did read them, but charly adopts this spec only together with the new sdk, in its own leg of this chain.) A builder node authoring `copy_artifact:` loaded and was then silently ignored. That's the same defect class this chain deleted `#AUR.replace` for: a field the install never applies.
- This chain introduced it (spec#420 kept the fields while sdk#613 stopped reading them), so it is fixed here, not filed.

Changes:
- `schema/builder.cue`: `copy_artifact`, `copy_binary` and `#Copy` are removed. The reply's `copy_artifacts`/`copy_binary` strings in `schema/buildwire.cue` stay; they are what the plugin produces.
- **A claim I wrote is withdrawn.** The comment above `copy_artifact`, added in spec#420, called it "the ONE install contract every builder shares", read by the image render and the apply path. That was false once sdk#613 landed, and it goes with the field.
- `#BuilderPackage`'s comment and the unified test's comment now cite `#BuilderAlt` under **D-PLUG-2**. They cited D-IR-7, a different requirement (DESIGN.md: D-IR-7 is "a manager word's work is done at its time").
- `spec/cue_types_gen.go` is regenerated (`charly task cue-gen`).
