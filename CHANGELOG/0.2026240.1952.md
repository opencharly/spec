# 0.2026240.1952 — feat(vm): the full GPU configuration surface on #LibvirtVideo and #LibvirtGraphics

## Summary

The schema leg of **B6 — the full QEMU/libvirt GPU configuration surface**. Spike 3 proved a
virtio-gpu guest can host the cstream stack, but only by hand-injecting `<qemu:override>` XML,
because charly could not express most of what libvirt already accepts. This opens that surface —
the whole space, not the two knobs cstream needs.

### `#LibvirtVideo` modelled 5 of ~15 attributes

Measured against `libvirtxml.DomainVideoModel` / `DomainVideoAccel` / `DomainVideoDriver`. Two of
the gaps are the reason the spike needed hand-written XML:

- **`device`** — `model: virtio` emits plain `virtio-vga`, which has **no GL at all**, so
  `virtio-gpu-gl` was simply unreachable.
- **`blob`** — virtio-gpu blob resources; a native-context or venus guest cannot work without them.

Also added: `ram`, `vram64`, `vgamem`, `edid`, `accel2d`, `render_node`, `resolution{x,y}`,
`driver{name,vgaconf,iommu,ats,packed,page_per_vq}`, and `alias`.

### `#LibvirtGraphics.gl` was a bare string

libvirt models `<gl>` **per graphics type** (`DomainGraphicSpiceGL`, `DomainGraphicEGLHeadlessGL`,
`DomainGraphicDBusGL`), each with `rendernode=`. A scalar could only ever reach spice's `enable=`
attribute and had **no way to express `rendernode=`** — the attribute that points virtio-gpu at a
specific host DRM node, and therefore the entire reason a GPU-in-VM candy touches `<gl>`.

`<acceleration rendernode=…>` on the video device is **not** the substitute: libvirt documents that
one as vhostuser-driver-only. It is modelled here for completeness with a comment saying so.

`dbus` joins the type enum — a real libvirt graphics type the enum simply omitted — with its own
`address` / `p2p`.

### `qemu_override` — one seam, not a field per knob

`qemu-system-x86_64 -device virtio-vga-gl,help` lists exactly `blob`, `drm_native_context`,
`hostmem`, `max_hostmem`, `venus`. Only the first is now a libvirt element; the rest have none, and
rutabaga adds more. So the seam is shaped like libvirt's **own** override element:

```yaml
libvirt:
  devices:
    video: [{model: virtio, device: virtio-gpu-gl, blob: true, alias: ua-gpu}]
  qemu_override:
    ua-gpu: {drm_native_context: true, hostmem: 4G}
```

A new GPU knob is a YAML line, never a schema change — the same opaque word-keyed shape B2 used for
`unit_options:`.

**Keyed by user alias**, because libvirt refuses an override against its own auto-assigned
`video0`. The device declares the alias; emission is conditional on it, so a VM that does not use
the seam renders byte-identically to before the field existed.

## Two codegen hazards, both of which fail SILENTLY

Neither produces an error. Both are pinned by tests.

**1. A pattern-constrained key emits an empty struct.** Writing the key as `[=~"^ua-…"]` made
`cue exp gengotypes` emit:

```go
QemuOverride struct {
} `yaml:"qemu_override,omitempty"`
```

— so every override would decode into nothing at all. The key is typed `[string]`; the `ua-` prefix
is enforced on the `alias` field instead and reaches these keys **transitively** (a key that is not
`ua-`-prefixed can never equal a valid alias, and the renderer then names it as unmatched, which is
the better message anyway).

**2. A `_|_` cross-rule degrades the WHOLE struct to `any`.** The natural way to say "`<gl>` does
not exist on vnc" is `if type == "vnc" { gl?: _|_ }`. It type-checks in CUE and produced:

```go
type LibvirtGraphics any /* TODO: IncompleteKind: _|_ */
```

gengotypes evaluates the definition with `type` still abstract, so every branch stays unresolved,
the field kinds reduce to bottom, and it gives up on the struct. **That still compiles** — every
graphics block would silently decode into an untyped map. The existing `if firmware == …` rules on
`#Vm` are safe only because they TIGHTEN fields to concrete values rather than to bottom.

Those per-type rules therefore move to the renderer's `mapGraphics` (the plugin-vm leg), which is
the exact point where the field would otherwise be dropped and where the message can name the
reason. The schema carries a comment saying why, so the next author does not helpfully add the CUE
rule back and silently turn the type into `any`.

## The breaking change, and what carries it

`gl:` changes shape, so `#SchemaVersion` is bumped (placeholder CalVer; the pr-validator re-stamps
it to merge time). The matching migration entry is the **plugin-migrate** leg: the scalar sits at
`vm.libvirt.devices.graphics[].gl`, a field inside a **list element**, which none of the four
declarative key-transform ops can reach — so it needs an `apply:` reshaper hook, exactly as
`installTemplateToPhases` did.

`gl:` has **zero authors** in the org corpus, so no in-tree config needs migrating — but the hook
is required for any config outside it, and the policy is unconditional.

The sweep, executed over every submodule's committed HEAD (`git -C <sub> grep … HEAD`, which reads
the object store, so the 109 submodules whose worktrees are currently absent are covered too):

```
$ for p in $(git config -f .gitmodules --get-regexp 'submodule\..*\.path' | awk '{print $2}'); do
    git -C "$p" grep -n -I -E '(^|[[:space:]{,])gl:' HEAD -- '*.yml' '*.yaml' | sed "s|^|$p/|"
  done
submodules total=344 searched=344 worktree-absent=0
hit count: 0
```

That pattern matches `gl:` in block form, flow form (`{gl: …}`) and after a comma, so it is not
narrowed to the scalar spelling. **Positive control**, same loop and same 344 HEADs, for a key that
does exist — otherwise a zero could just mean the sweep never ran:

```
accel3d: hits across the same 344 HEADs = 7
```
